Volcano 核心功能：从 Gang 调度到队列资源管理

分布式训练、MPI 和批处理作业往往由多个相互依赖的 Pod 组成。它们需要协调启动，也需要与其他团队共享有限的 GPU 和 CPU。Volcano 为 Kubernetes 提供面向批处理和高性能计算的调度能力，核心包括作业管理、Gang 调度、队列资源管理和可扩展的调度策略。

本文以官方文档为依据，梳理各组件的职责与组合方式。功能和配置会随版本变化，部署前应对照所用版本的文档。本文资料核对于 2026-10-28。

Volcano 解决什么问题

Kubernetes 默认调度器主要为单个 Pod 选择节点。一个分布式训练作业可能需要四个 Worker 同时具备运行条件。如果只安排了三个，已占用的 GPU 可能一直等待第四个 Worker。多团队共用集群时，还需要决定资源如何分配，以及空闲份额如何借用和归还。

Volcano 在 Kubernetes API 之上引入作业、PodGroup 和队列等概念，并通过独立调度器处理这些约束。它适合批处理、AI 训练和 HPC 等场景。是否使用某项功能取决于所安装的版本和调度器配置。

图中展示的是典型 Volcano Job 路径。其他工作负载也可以通过集成方式使用 PodGroup 和 Volcano 调度器，具体支持范围取决于控制器与版本。

三个关键对象

对象 作用 主要关注点
Volcano Job 描述批处理作业及其任务 任务副本、最小可用数、失败策略
PodGroup 把相互关联的 Pod 作为调度单元 最小成员数、队列、调度状态
Queue 管理多个作业的资源分配 份额、上限、借用和回收

Volcano Job 控制器负责维护作业和 Pod 的生命周期。调度器依据 PodGroup 和 Queue 等状态进行调度。Job、PodGroup 和 Queue 解决的问题不同：Job 描述工作，PodGroup 表达成组约束，Queue 管理资源分配。

Gang：先满足最低运行规模

Gang 插件检查一个作业能否满足 minAvailable。达到约束后，调度器才能提交这一组分配。如果作业有四个 Worker，minAvailable 设为 4，那么调度器需要找到四个满足约束的位置。若设为 3，最低运行规模就是三个，并不表示所有四个副本必须同时调度。

Gang 约束针对调度分配。Pod 绑定后，镜像拉取、容器启动和应用通信仍可能失败。Gang 也无法保证所有进程同时进入应用层的就绪状态。使用前需要为 Pod 设置准确的资源请求，并考虑节点亲和性、污点和 GPU 等条件。

Queue：共享资源与隔离

Queue 用于多租户资源管理。队列可以设置 CPU、内存和设备等资源维度的额度。capability 表示使用上限；deserved 表示竞争时应得份额；guarantee 表示保留资源。具体语义和可用字段应以所用插件及版本为准。

例如，两个队列各有 8 张 GPU 的应得份额。队列 A 暂时没有作业时，队列 B 可以在策略允许时借用空闲 GPU。当 A 提交作业后，调度器可以依据回收策略处理 B 超出份额的资源。回收可能驱逐正在运行的 Pod，作业需要有检查点或重试机制。

capacity 插件直接配置各资源维度的应得份额，proportion 插件根据队列权重计算份额。官方文档要求两者互斥使用。队列份额也不等于 Kubernetes Namespace 的 ResourceQuota：前者参与 Volcano 的调度分配，后者负责 Kubernetes API 层面的配额限制。

抢占和回收

机制 作用范围 典型用途
preempt 同一队列内 让高优先级作业获取低优先级作业占用的资源
reclaim 队列之间 在符合策略时收回其他队列借用的资源

驱逐对象是否可被回收，还受队列、作业和插件规则约束。开启对应 action 不代表所有任务都能被驱逐。官方文档还提示，enqueue 如果阻止 PodGroup 入队，可能没有 Pending Pod 触发 preempt 或 reclaim。应结合实际配置测试资源紧张时的行为。

调度器：Action 和 Plugin

调度器周期性打开调度会话，按照配置的顺序执行 action。Action 负责调度流程，plugin 提供排序、约束判断、节点过滤和评分等策略。

Action 作用
enqueue 判断作业是否满足入队条件
allocate 为任务过滤、评分并分配节点，结合 Gang 约束提交
preempt 处理队列内抢占
reclaim 处理队列间资源回收
backfill 处理没有资源请求的 BestEffort Pod

常见插件包括 gang、priority、predicates、nodeorder、drf 和队列资源插件。predicates 负责节点可行性判断；nodeorder 参与节点评分；drf 用多维资源份额辅助公平分配。插件分组和顺序会影响策略组合。以下只是展示配置结构，不应直接视作生产配置：

actions: "enqueue, allocate, backfill"
tiers:
  - plugins:
      - name: priority
      - name: gang
  - plugins:
      - name: predicates
      - name: nodeorder
      - name: proportion

这里没有启用 preempt 和 reclaim，因此不能把它当作抢占或回收配置。修改生产配置前，应先查看安装版本的默认 ConfigMap 和插件文档。

作业示例

下面的作业定义两个副本，要求两个 Pod 满足 Gang 约束。容器使用 sleep 模拟工作，便于观察调度；它不代表实际训练程序。

apiVersion: batch.volcano.sh/v1alpha1
kind: Job
metadata:
  name: gang-demo
spec:
  schedulerName: volcano
  queue: default
  minAvailable: 2
  tasks:
    - name: worker
      replicas: 2
      template:
        spec:
          restartPolicy: Never
          containers:
            - name: worker
              image: busybox:1.36
              command: ["sleep", "600"]
              resources:
                requests:
                  cpu: "1"
                  memory: "256Mi"

前提是集群已安装 Volcano，default 队列存在，调度器启用了相应 Gang 策略。提交后可以查看作业、PodGroup 和事件：

kubectl apply -f gang-demo.yaml
kubectl get jobs.batch.volcano.sh
kubectl get podgroups.scheduling.volcano.sh
kubectl describe podgroup gang-demo
kubectl get pods -o wide

PodGroup 名称及事件应以集群实际输出为准。若一直等待，先检查队列状态、Pod 资源请求、节点可用量和调度事件，再检查亲和性、污点及插件配置。示例未在本文中声称经过集群实测。

拓扑与扩展能力

大规模训练不仅需要足够的 GPU，还需要合适的通信拓扑。Volcano 提供网络拓扑感知调度能力，可通过 HyperNode 描述节点之间的层级关系，并结合插件选择部署位置。这是尽力优化或约束调度的能力，具体效果取决于拓扑数据、策略配置和可用资源。

节点打包、亲和性和设备拓扑是不同层次的问题。应先确认目标是减少资源碎片、让 Worker 靠近网络拓扑，还是选择设备内部的 GPU 组合。不要仅凭启用一个插件就假定所有拓扑约束都已满足。

何时使用

当作业需要多 Pod 协同、多个团队共享加速器，或需要按队列实施借用与回收时，Volcano 值得评估。对于普通无状态服务，默认调度器可能已经足够。引入 Volcano 后，还需要维护控制器、调度器、CRD 和策略，并为抢占后的作业恢复做验证。

建议从一个小规模测试集群开始：先验证 Gang 无法满足时的等待行为，再验证队列借用和回收，最后加入优先级、拓扑和真实训练作业。每一步都记录版本、配置、事件和作业恢复结果。
