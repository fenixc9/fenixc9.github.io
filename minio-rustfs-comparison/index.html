MinIO 与 RustFS 对比：架构、容量利用率、容错与迁移

MinIO 与 RustFS 都提供兼容 S3 API 的对象存储。两者采用相近的对象级纠删码架构。相同纠删组宽度、相同校验分片数下，它们的理论容量利用率相同。

对选型影响更大的差异来自项目维护、故障恢复、S3 行为边界和迁移能力。以本文核对的版本为例，16 盘纠删组默认都是 12 个数据分片加 4 个校验分片，理论容量利用率为 75%。RustFS 使用 Rust，并不会自动提高这个比例。

本文资料核对截止 2026-10-28。研究范围是 MinIO 开源社区代码与 RustFS 1.0.4。本文没有部署集群，也没有进行统一性能或故障测试。

RustFS tag 1.0.4，commit 46337942d55f3a8e6a97b147ca98d9ea8115555d 1.0.4 正式版发布于 2026-10-25

MinIO 的历史部署经验仍有参考价值。但社区版当前需要使用者自行安排构建、补丁评估和维护。商业 AIStor 的当前特性与支持承诺属于另一项选型，本文不将它们计入社区版。

RustFS 已有正式版本。评价它时应检查当前版本的实现和能力边界。1.0 版本号本身也不能证明某项业务已经具备长期生产运行的条件。MinIO 仓库、RustFS 1.0.4 发行说明

2. 架构：存储池、纠删组与磁盘

两者都按存储池（pool）、纠删组（erasure set）和磁盘（drive）组织数据。一个对象落在一个纠删组中。集群增加存储池和纠删组后，可以承载更多对象。

S3 客户端
  → 负载均衡或直接访问节点
  → S3 鉴权、策略与请求处理
  → 对象锁与存储池定位
  → 根据对象名定位纠删组
  → 数据分片、校验分片和对象元数据
  → 本地磁盘 / 远端节点磁盘

后台扫描与修复也在对象及其分片上工作。

这条路径表示共同的逻辑模型。两者的网络协议、并发调度和具体 API 实现仍有差异。

维度 MinIO 社区版 RustFS 1.0.4
实现语言与并发 Go、goroutine、GC Rust、Tokio 异步运行时
服务组织 节点同时提供 S3 服务和本地、远端存储访问 服务层、应用层、storage、ecstore、rio/io-core；节点间使用 gRPC/tonic
对象保护边界 一个对象位于一个纠删组 同类模型
纠删组宽度 多盘组支持 2–16 盘；单盘走独立路径 同样的范围与单盘例外
对象元数据 xl.meta；系统配置另存于内部命名空间 xl.meta / filemeta；具有部分 MinIO 格式导入能力
容量扩展 增加存储池，支持再平衡和存储池退役 已有扩容、再平衡和存储池退役流程

两者的对象存储路径都没有要求额外部署外部元数据库。但元数据仍然需要存储、读取和保持一致。磁盘访问、对象锁和元数据处理也会消耗资源。MinIO 分布式设计、RustFS 架构

写入与读取

正常写入先完成鉴权和策略检查。存储层取得对象锁，定位存储池与纠删组，再编码和写入分片。写入必须满足对应对象的写 quorum，才能完成提交。

读取先选择有效版本的元数据。存储层再读取所需分片。遇到缺片或校验失败时，系统尝试使用其他有效分片重构数据。

纠删码解决缺失分片的恢复问题。客户端可见的一致性还依赖版本选择、对象锁、失败提交处理和持久化规则。只证明若干分片能够解码，不足以证明并发覆盖、删除和 LIST 的行为都符合业务要求。

RustFS 当前使用哪种编码

RustFS 1.0.4 的新写入使用 rustfs-erasure-codec 提供的 GF(2⁸) Reed–Solomon Vandermonde 编码，算法标识为 rs-vandermonde。

它还保留 reed-solomon-simd 的 GF(2¹⁶) 后端。该后端用于读取和修复 RustFS 自身的早期格式。因此，Cargo 中存在某个 SIMD 依赖，不能说明所有新写入都使用该后端。RustFS 纠删码契约

MinIO 所查源码依赖 klauspost/reedsolomon。两者同属 RS 编码，但具体实现的吞吐和 CPU 开销仍需测试。语言选择不能替代性能数据。

扩容与再平衡分开处理

RustFS 的扩容文档要求把新存储池追加到所有节点一致的 RUSTFS_VOLUMES 中。旧存储池的顺序需要保留。各节点重启后应用完整拓扑。

新增容量可以接收新写入。旧对象仍在原存储池，需要另行运行 rebalance。扩容验证至少要分别检查新容量识别、重启期间可用性、旧对象迁移速度和前台 p99 延迟。RustFS 扩容、再平衡

3. 存储比：利用率和占用倍数要分清

设一个纠删组有 n=k+mn=k+mn=k+m 块盘。kkk 表示数据分片数，mmm 表示校验分片数。

忽略元数据、校验帧和文件系统开销后，容量利用率为：

η=kk+m\eta=\frac{k}{k+m}η=k+mk​

物理占用倍数为：

A=k+mkA=\frac{k+m}{k}A=kk+m​

相对于原始逻辑数据的冗余开销率为：

r=mkr=\frac{m}{k}r=km​

12+4 布局的校验分片占总物理容量的 25%。相对于逻辑数据，它多占用约 33.33% 的空间。两个比例使用了不同的分母。

布局 总盘数 理论容量利用率 物理占用倍数 丢失分片的数学恢复上限
3 副本，作为比较基准 — 33.33% 3.000× 2 个副本，实际仍取决于放置与可用性
4+4 8 50% 2.000× 4
8+4 12 66.67% 1.500× 4
12+4 16 75% 1.333× 4
10+6 16 62.5% 1.600× 6
8+8 16 50% 2.000× 8
14+2 16 87.5% 1.143× 2

表中假设磁盘等容量、对象足够大、未启用压缩，且只保存单站点数据。这些数值可用于同配置比较。故障期间的可读、可写条件还需要单独计算。

两者的默认校验数一致

源码中的 MinIO DefaultParityBlocks() 与 RustFS default_parity_count() 使用相同的基础规则：

每个纠删组的盘数 默认校验分片数 示例
1 0 单盘无纠删冗余
2–3 1 3 盘为 2+1
4–5 2 4 盘为 2+2
6–7 3 6 盘为 3+3
8–16 4 8 盘为 4+4；12 盘为 8+4；16 盘为 12+4

所以，默认容量利用率需要结合纠删组宽度计算。8 盘默认是 50%，16 盘默认是 75%。MinIO 仓库部分旧设计文字仍写默认一半校验，本文以固定提交中的函数实现和 storage-class 文档为准。MinIO 默认值源码、RustFS 默认值源码

这张表描述健康写入的基础配置。降级写入可能按可用性策略提高新对象的校验数。已有对象保留自身布局。修改全局 EC:m 配置也不会立即重编码所有历史对象。

相同 16 盘、相同 12+4 配置时，两者的理论存储比相同。改成 14+2 可以提高利用率，同时降低可恢复的分片丢失上限。

保存 100 TB 数据需要多少磁盘

以下算例使用十进制 TB/PB。20% 空闲是容量规划假设。

  • 100 TB 有效数据采用 12+4 编码，约需 133.33 TB 物理空间。
  • 再保留 20% 物理空闲，约需 166.67 TB 原始容量。
  • 1 PB 原始容量采用 12+4 编码，理论可保存 750 TB 数据。保留 20% 原始空闲后，业务数据预算约为 600 TB。
  • 两个独立站点各保存一份完整的 12+4 数据，100 TB 有效数据共需约 266.67 TB 编码空间。每站再留 20% 空闲，总计约需 333.33 TB。

这些数字都没有计入元数据、历史版本和文件系统等额外开销。更完整的粗估可以写为：

Craw≈D⋅v⋅A+H1−fC_{\mathrm{raw}}\approx\frac{D\cdot v\cdot A+H}{1-f}Craw​≈1−fD⋅v⋅A+H​

其中，DDD 是有效数据量，vvv 是版本与完整副本的规划系数，AAA 是纠删码占用倍数。HHH 表示元数据、校验和文件系统等额外开销，fff 是预留空闲比例。

异构盘还可能受到纠删组内较小磁盘的限制。实际可用容量不能一律按所有磁盘标称容量之和乘 75% 估算。

4. 容错要按纠删组和故障域计算

对正常 EC 对象，两份源码中的基础 quorum 规则相近：

Qread=k,Qwrite={k,k>mk+1,k=mQ_{\mathrm{read}}=k,\qquad Q_{\mathrm{write}}= \begin{cases} k,&k>m\\ k+1,&k=m \end{cases}Qread​=k,Qwrite​={k,k+1,​k>mk=m​

数据分片与校验分片各占一半时，写入多要求一个分片，用于避免对半分区分别提交。实际操作还需要满足元数据版本、锁和网络等条件。零校验布局有独立处理路径。MinIO quorum 源码、RustFS quorum 源码

布局 读 quorum 写 quorum 基础门槛允许缺失的分片：读 / 写
12+4 12 12 4 / 4
8+8 8 9 8 / 7
4+4 4 5 4 / 3

假设一个 16 盘纠删组均匀分布在 4 台机器上，每台机器贡献 4 块盘：

  • 12+4 布局失去一台机器，就失去 4 个分片。此时已到该对象的恢复边界。同组再丢失一个有效分片就会超限。
  • 8+8 布局失去两台机器后，还剩 8 个分片。它达到基础读 quorum，但达不到 9 分片的写 quorum。
  • 集群即使共有 100 台机器，也必须逐个纠删组计算。全局故障机器的比例不能代表某个对象的剩余保护能力。

这个例子以明确的分片分布为前提。实际部署还要检查机架、电源、交换机和机房等相关故障域。单机多盘 EC 能抵御部分磁盘故障，但无法提供整机服务高可用。

5. 小对象的实际开销可能远高于编码比例

对象级存储会引入分片校验、对象元数据、目录、inode 和文件系统块取整。对象只有 1–4 KiB 时，固定成本可能超过数据本身。大对象下的 1.333× 占用倍数不能直接套到海量小对象。

两者都支持把小分片内联到 xl.meta。内联可以减少文件数量和 I/O 次数。它仍然需要保存元数据，也不会把所有小对象合并成一个大顺序文件。

两份源码的内联策略有实际差异：

  • MinIO 默认以每分片 128 KiB 作为门槛。开启版本的场景使用该门槛的 1/8。
  • RustFS 1.0.4 默认按数据分片数缩放门槛。开启版本的场景再除以 8。显式配置可以指定固定的每分片门槛。

RustFS 默认的每分片门槛可以表示为：

T(k)=min⁡(⌈256 KiBk⌉,128 KiB)T(k)=\min\left(\left\lceil\frac{256\,\mathrm{KiB}}{k}\right\rceil,128\,\mathrm{KiB}\right)T(k)=min(⌈k256KiB​⌉,128KiB)

这是内联判定门槛。对象最终占用还包括校验帧、边界取整和元数据。策略差异需要通过实际空间统计来评价。MinIO storage-class 实现、RustFS storageclass 实现

测试时应同时记录 S3 逻辑字节、文件系统已分配字节、inode 数量和各盘空间变化。du 的已分配空间与 apparent size 要分开记录。历史版本、未完成的 multipart、删除标记和清理延迟也应分别核算。

如果启用压缩，应按真实内容测试。文本、Parquet、图片和已压缩备份的压缩效果可能相差很大。

6. 性能比较需要固定工作负载

Rust 可以减少 GC 对执行过程的影响。但缓冲管理、内存分配、数据拷贝、磁盘和网络仍会限制性能。仅凭实现语言无法判断整套 S3 服务的吞吐与尾延迟。

工作负载 主要瓶颈 应比较的指标
大对象顺序 PUT/GET 网络、磁盘带宽、编码、拷贝 GiB/s、CPU/GiB、降级吞吐
1–64 KiB 小对象 元数据、IOPS、锁、内存分配 obj/s、p99、每对象物理字节
大 bucket LIST 与版本枚举 元数据读取、合并、目录布局 首屏与翻页 p99、内存峰值
修复与再平衡 跨盘读取、重构、后台调度 恢复时间、前台 p99、网络流量
加密与 multipart KMS、校验、缓冲、分片管理 CPU、常驻内存、重试与尾延迟

比较时要固定硬件、网络、纠删组宽度、校验数、持久化设置和加密配置。客户端位置、并发模型和缓存状态也要一致。

历史 MinIO 压测可以提供测试设计思路。旧版本、旧硬件的结果不能直接与 RustFS 当前宣传指标比较。本文没有得出两者性能胜负的实测结论。

RustFS 在线兼容矩阵注明，其数字对应 2026-08-09 的快照。本文直接统计 1.0.4 源码中的清单，忽略空白和注释，得到：

unimplemented 21

这些是清单行数。本文没有执行这些测试。不同清单还包含有意排除或范围不同的用例，因此不能直接相除得出 S3 兼容率。1.0.4 兼容性矩阵、可执行清单

当前矩阵仍列出若干限制：bucket access logging 的相关兼容用例尚未通过；ownership controls 没有 handler；POST 表单上传 checksum 行为尚未完整通过。ACL 授权属于有意不支持的行为。multipart 的部分边界行为不在默认兼容性检查范围内。

站点复制具有独立的恢复边界

RustFS 的站点复制文档明确说明，复制是异步的。一个站点写入成功，不表示远端已有该版本。站点复制也不提供 DNS 故障切换、流量路由或应用恢复编排。

部署方案需要单独定义复制延迟、RPO、RTO 和切换流程。RustFS 站点复制

8. MinIO 迁移到 RustFS：API、盘格式与回滚分开验证

S3 API 兼容、磁盘格式可读和原地回滚是三个独立问题。RustFS 1.0.4 的互操作契约列出了明确边界。

数据或操作 RustFS 默认发行构建的声明边界
未加密 MinIO xl.meta，含 inline、multipart、版本和删除标记 支持相应格式读取；仍需验证实际源版本和样本
桶元数据和部分 IAM 配置 有导入实现与测试样本；覆盖范围需要逐项检查
MinIO SSE-S3、SSE-KMS、SSE-C 对象 默认构建不能直接读取
专用 rio-v2 构建 部分静态 KMS 与 SSE-C 迁移能力有条件支持；不在默认或 full 发行构建中
KES、MinKMS、KMS plugin 封装的 MinIO SSE 对象 不在上述直接读取范围内
已 transition 到远端 tier 的元数据 契约列为未由测试样本证明
把 RustFS 写过的盘集交回 MinIO 不支持；内部系统目录等格式存在分歧

因此，普通发行镜像不能被视为所有 MinIO 数据的原盘替代品。RustFS 写入后的盘集，也不能直接当作可随时交回 MinIO 的回退副本。RustFS 互操作契约

优先评估通过 S3 API 读取源对象，再写入独立目标。源端正常解密，目标端按自身配置加密。工具是否保留全部版本、对象锁、桶策略、删除标记和生命周期，需要分别验证。

如果需要原盘接管，应先使用隔离副本测试。验证范围应包括源版本、加密对象、全部历史版本和桶元数据。回退依据应是未被目标写入的源盘快照。

9. 选型建议与验证顺序

以下建议是基于当前资料的工程判断。性能、实际空间放大和故障恢复时间仍待实测。

场景 建议
新建自托管 S3，要求持续维护的开源方案 优先对 RustFS 1.0.4 做 PoC，再验证故障和长期负载
已有稳定 MinIO，业务依赖重、迁移窗口小 固定可复现产物，盘点加密和 API 依赖，制定维护与迁移计划
唯一数据副本、强合规或严格可用性要求 要求恢复证据、明确责任方和足够运维资源
海量小对象，主要关注容量成本 测量真实对象分布和物理空间放大
希望原盘读取 MinIO 加密存量 先检查构建与 KMS 限制，优先验证 API 迁移

最小 PoC 可以按以下顺序执行：

  1. 固定源码或镜像摘要。统一纠删组宽度、EC:m、TLS、加密、版本和持久化配置。
  2. 测试 4 KiB、64 KiB、1 MiB、64 MiB 和 1 GiB 对象。再加入真实大小分布。分别测 PUT、GET、Range、LIST、DELETE 和 multipart。
  3. 记录逻辑字节与每盘实际分配字节。单独统计历史版本、未完成 multipart 和系统元数据。
  4. 在隔离环境模拟同一纠删组的磁盘或节点离线。再测试网络分区和进程中断。检查 quorum 边界、覆盖与版本读取。
  5. 更换磁盘，记录修复完成时间。进行全量内容校验。记录修复期间前台 p99 延迟。
  6. 分别验证扩容、再平衡、存储池退役、重启和升级。
  7. 使用实际业务客户端验收。覆盖 SDK、预签名 URL、IAM/STS、Object Lock、KMS、生命周期和复制。

每项记录实际版本和通过情况。压测工具执行成功，只能证明该负载下的运行结果。掉电持久性、数据恢复和复杂 API 兼容需要独立证据。
