Codex 为什么能一直干下去？通俗理解 Goal 的实现机制

让 AI 帮忙改代码，经常会遇到这样的场景：它分析了一轮，给出几个发现，然后停下来。你看完只能再说一句：“继续。”

如果任务是修一个明显的小错误，这样已经够用。但如果任务是“把接口延迟降下来，同时保证测试通过”，第一轮通常只是找到问题，后面还要修改、测量、排查回归，甚至推翻原来的方案。

Codex 的 Goal 就是为这类工作准备的：把要达到的结果保存到会话里，让程序在合适的时机自动开启下一轮工作，直到完成、被暂停，或者遇到预算与阻塞条件。

理解它，可以抓住四件事：记住目标、安排下一轮、检查完成证据、控制消耗。

本文依据 2026 年 10 月 14 日查阅的官方文档和公开源码整理，源码固定在提交 76ed3b48。这是一份实现机制解读，没有进行本地运行实验；不同版本的命令界面和停止细节可能变化。

先看一个具体任务

假设你给 Codex 设置这样的目标：

/goal 将结账接口的 p95 延迟降到 120ms 以下，使用现有基准测试验证，并保持正确性测试全部通过。

这里的 p95 可以理解为：把请求耗时从小到大排列，95% 的请求耗时不超过这个值。

这个目标包含两个必须同时成立的条件：接口足够快，功能也要正确。下面是一段假设的工作过程，用来解释机制，并非实际测量结果：

轮次 做了什么 当前能否结束
第一轮 运行基准测试，发现数据库查询占用时间较多 还没修改，不能结束
第二轮 优化查询，p95 从 180ms 降到 135ms 有进展，但还没达到目标
第三轮 增加缓存，p95 降到 110ms，但正确性测试失败 性能达标，功能不达标
第四轮 修复缓存问题，重新测量并通过正确性测试 证据支持完成，可以结束

Goal 要维持的，就是这条贯穿多轮工作的要求：不能因为做出了一点改进，就把原来的目标算作完成。

官方将它描述为一个附着在会话上的持久目标。它适合路径需要边做边判断的任务，例如性能优化、疑难排障和多步骤迁移。官方说明：Using Goals in Codex

第一件事：给目标建一张可以保存的任务卡

一个目标要跨轮次存在，就需要有地方记录它。

Codex 在 SQLite 数据库里保存一条目标记录。可以把它理解成一张任务卡：

所属会话：这一次结账接口优化
目标：p95 低于 120ms，正确性测试全部通过
状态：正在执行
Token 预算：如果设置了，就记录上限
累计消耗：已经用了多少 Token、花了多少时间

源码里的表叫 thread_goals，以会话 ID 为主键，一个会话对应一条当前目标记录。它还保存一个独立的 goal_id，用来区分目标实例。这样，即使用户替换了目标，旧目标延迟到达的结算也可以通过 ID 检查，避免记到新目标头上。

目标大致会处于下面这些状态：

状态 通俗解释
active 目标仍在执行，可以自动续跑
paused 已暂停，等用户恢复
blocked 当前无法继续推进
usage_limited 遇到账户用量限制
budget_limited 达到这个目标的 Token 预算
complete 已标记完成

删除目标则会清除记录。

这层存储解决的是“目标还在不在”。恢复会话时可以重新加载目标，但保存了任务卡，不代表关闭 Codex 后还有一个进程替它工作。实际执行仍需要运行中的宿主程序。数据结构与状态、数据库表结构

第二件事：程序替你安排下一轮“继续”

目标存好了，谁来让 Codex 接着干？

负责这件事的是运行 Codex 的程序，也就是宿主。模型处理当前轮的分析和行动，宿主负责调度下一轮。

在 Goal 的扩展实现中，有一个重要的触发点：会话进入空闲状态。 一轮结束后，宿主会检查当前目标，如果它仍然是 active，就尝试发起新的轮次。

过程可以画成这样：

用户设置目标 → 保存到数据库
                    ↓
              执行一轮工作
                    ↓
              结算用量与状态
                    ↓
         会话空闲，目标仍可继续？
              ├─ 否 → 等待或停止
              └─ 是 → 注入目标与续跑提示
                            ↓
                      执行下一轮工作

这里的“可以继续”有实际门槛：不能同时还有一轮正在执行，不能抢在已排队的用户输入前面，自动工作不能在 Plan 模式下启动，服务进入关闭流程时也不能再接新一轮。

所以它是一种由事件触发、经过条件检查的续跑。用户发来了新要求，程序要先处理用户输入；用户暂停了目标，程序也不能拿旧状态偷偷再开一轮。

源码用锁保护“读取目标到启动续跑”的过程，正是为了处理这些操作同时发生的情况。空闲续跑实现、新轮次启动检查

第三件事：每次续跑，都重新提醒“什么才算做完”

如果程序只给模型发一句“继续”，模型仍然可能忘记原来的约束，或者围着已经做好的部分打转。

Codex 为此准备了一份续跑提示词。宿主把目标、已消耗的 Token、预算和剩余预算填进去，再送给模型。

把这份提示翻成日常语言，大致是：

继续追求原来的完整目标。先看当前文件、测试和运行状态，再决定下一步。不要为了尽快结束而缩小任务范围。宣布完成前，把每项要求和能证明它的证据对一遍。

回到性能优化的例子，“延迟降到了 110ms”只能证明一半。还需要检查正确性测试是否通过，以及测试是不是覆盖了这次修改影响的功能。

这里可以区分两种信息：数据库里的目标记录负责让目标持续存在，续跑提示词负责让模型在下一轮知道该怎样围绕目标工作。 提示词本身并不承担持久化和调度。

源码中的目标正文还会经过转义，模板也明确说明它属于用户任务数据，不应获得更高的指令优先级。完整续跑提示词、提示词构造代码

谁来判断“真的完成了”？

这是理解 Goal 最值得注意的地方：完成判断主要由模型根据证据作出。

模型可以调用三个目标工具：

create_goal：创建目标
get_goal：查看当前目标和用量
update_goal：将目标标记为完成、阻塞或按用户要求暂停

模型认为已经做完后，调用 update_goal，把状态设为 complete。后续空闲检查发现目标已经完成，就不会再自动开启下一轮。

但在本文检查的实现里，update_goal 的参数没有要求附带一份结构化测试报告，处理器也不会替模型再运行一次测试。处理器主要负责结算用量、校验状态和保存结果。

这意味着，提示词要求模型认真验收，而程序没有给每个目标配一位独立的验收员。模型如果误读结果、漏掉要求，仍可能过早标记完成。

因此，写目标时要尽量提供容易核对的完成条件：

较难判断：优化一下这个接口。

更容易判断：将结账接口的 p95 延迟降到 120ms 以下，
使用现有基准测试验证，并保持正确性测试全部通过。

第二种写法让模型知道该拿什么证明完成，也让人更容易复查。如果自己实现类似系统，并且对正确性要求高，可以在模型请求完成时增加独立验收，例如自动运行指定测试。这属于可以借鉴的设计建议，并非本文所查 Goal 工具已经提供的通用能力。目标工具定义、状态更新处理器

第四件事：目标没完成，也要知道什么时候停

持续工作需要边界。一个任务暂时做不完，并不意味着应该无限消耗资源。

预算到了，先收尾

Token 是模型处理文本时使用的计量单位。Goal 可以设置 Token 预算，宿主会在工具结束、轮次结束等时机累计用量。

本文源码中的计算口径是：

目标用量增量 = 输入 Token 增量 − 缓存输入 Token 增量 + 输出 Token 增量

如果主 Agent 派生了子 Agent，子 Agent 的用量也会汇入根目标。多个工具并行结束时，程序通过锁和计量基线避免把同一份消耗记两次。这个计量口径不直接等同于 API 账单金额。

达到预算后，程序把目标改为 budget_limited，并提醒模型尽快收尾：说明已经做了什么、还缺什么、下一步需要什么。

预算耗尽不等于任务完成。 假如接口只优化到 135ms，就应该如实汇报这个结果。当前轮收尾期间仍会产生用量，所以最终消耗可能超过预算；它不是精确到最后一个 Token 的硬切断。用量计算、预算结算、收尾提示词

卡住了，要区分临时困难和无法推进

比如测试环境暂时不可用，模型应先检查能否恢复，或者能否推进其他必要工作。续跑提示要求：同一个真实阻塞连续出现至少三轮，且已经无法取得有意义进展时，再标记 blocked。这部分主要是对模型行为的要求。

程序还会检测一些更具体的运行问题。在本文的源码基线中，连续三轮符合条件的自动空响应，或者连续三轮特定执行失败且没有成功工具调用，会让目标进入阻塞状态。不可重试或重试耗尽的轮次错误也可能直接阻止续跑；账户用量限制则对应 usage_limited。

这些检测各有自己的条件，不能概括成“失败三次就停止”，也不能把“说了一段话”当成真的推进了任务。程序能检测部分运行异常，语义上有没有进展仍需要模型审查。

官方 Cookbook 与这份源码在防空转描述上也有差异：文档写的是无工具调用时抑制后续续跑，源码已经采用更细的活动与失败判断。遇到具体行为差异时，需要对照实际版本。活动与失败检测、错误停止处理

怎么写一个好用的 Goal

一个有用的目标，至少应该让 Codex 知道三件事：最后要达到什么结果，用什么验证，以及哪些东西不能被改坏。

例如，迁移任务可以这样写：

/goal 将指定模块迁移到新的配置格式，保持现有对外行为不变。
完成后运行该模块的测试与构建，确认旧格式兼容策略符合项目要求。
如果缺少必要的配置样例，说明缺失项及其影响。

官方文档给出的生命周期命令包括：

/goal <目标描述>    设置目标
/goal              查看当前目标
/goal pause        暂停目标
/goal resume       恢复目标
/goal clear        清除目标

具体可用性仍取决于安装版本和功能配置。官方使用说明

对于只改一行代码、解释一个报错这样的短任务，普通请求已经足够。需要反复尝试、根据新结果调整方向，并且有明确终点的工作，才能更充分地用上 Goal。

Goal 的实现也展示了一种清楚的分工：模型负责想下一步、动手和查证，程序负责保存目标、安排续跑和限制资源。 理解了这层分工，就能看懂它为什么可以跨轮次持续工作，也能知道哪些地方仍然需要检查证据。
