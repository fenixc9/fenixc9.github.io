OpenSandbox 调研：AI Agent 沙箱的架构、隔离与工程实践

AI Agent 开始执行代码、修改文件和操作浏览器后，应用需要为每次任务准备运行环境。这个环境既要让 Agent 完成工作，也要限制它能够访问的资源。任务结束后，平台还需要回收环境和保存必要的产物。

OpenSandbox 提供一套自托管的沙箱接口，覆盖环境生命周期、命令执行、文件操作和网络控制。它支持从本地 Docker 运行到 Kubernetes 集群部署，也提供可选的 Firecracker microVM 路径。本文分析它的设计、适用场景与需要验证的边界。

资料核对日期：2026 年 10 月 28 日。本文依据官方仓库、架构与性能文档整理，源码参考提交 62a64f0。本文没有独立部署、进行安全测试或复现性能数据；涉及版本和能力时，以实际部署版本为准。

Agent 为什么需要沙箱

考虑一个 Coding Agent：用户要求它修改项目并运行测试。Agent 需要读取源代码、安装依赖、执行构建命令，有时还要访问代码仓库或包管理服务。模型生成的命令可能出错，项目依赖也可能包含不可信代码。

如果直接在应用进程所在机器执行，需要自行解决这些问题：

  1. 执行边界：限制进程能读取、修改和访问的资源。
  2. 环境一致性：为不同项目提供匹配的系统镜像和依赖。
  3. 任务隔离：防止一个任务的文件和进程影响下一个任务。
  4. 资源治理：设置 CPU、内存和任务超时，避免任务长期占用资源。
  5. 网络与凭证：允许必要的外部访问，同时控制密钥的暴露范围。
  6. 规模化管理：评测或训练时批量创建、追踪和回收环境。

OpenSandbox 把这些需求组织成生命周期管理、沙箱内执行、运行时后端和网络控制等组件。它由阿里巴巴贡献，属于 Agentic AI Foundation，采用 Apache 2.0 协议。项目仓库

产品定位和典型场景

OpenSandbox 面向需要给程序分配执行环境的应用。模型推理、任务规划和 Agent 编排仍由应用或 Agent 框架负责。OpenSandbox 提供可被调用的工作空间。

场景 沙箱承担的工作 主要关注点
Coding Agent 读写项目文件、运行构建和测试 工作目录、依赖、代码访问权限
代码解释器 执行生成的代码并返回结果 计算资源、执行超时、产物获取
浏览器或桌面 Agent 运行浏览器、自动化脚本或桌面程序 网络访问、会话数据、交互通道
Agent 评测 为每个测试分配环境 环境一致性、并发、结果回收
强化学习训练 并行运行大量任务或 rollout 创建延迟、容量与资源利用率

官方仓库提供 Coding Agent、代码解释器和浏览器等示例。这些示例说明接入方式；生产场景仍需验证镜像、安全策略和容量。

总体架构：生命周期与执行分离

业务应用 / Agent
       │
       ├── SDK / CLI / MCP
       │
       ├── 生命周期 API ──> OpenSandbox Server
       │                       │
       │                 Docker / Kubernetes 后端
       │                       │
       └── 执行与服务访问 ──> 沙箱内 execd / 应用端口
                               │
                        网络出口策略与凭证代理

一次典型调用先通过生命周期 API 创建沙箱。服务端选择配置好的运行时并等待环境可用。客户端解析沙箱端点后，调用 execd 执行命令或读写文件。任务结束后，客户端销毁沙箱，或者按需要暂停、恢复和续期。

生命周期请求由控制面处理。创建后的执行和服务访问可以走解析出的端点、服务代理或 Kubernetes 网关。这样，执行 API 与环境创建逻辑有明确边界。官方架构

控制面：从 API 到运行时

服务端使用 FastAPI。它校验请求、管理生命周期记录，再把创建和销毁等操作交给运行时后端。公开协议使用 OpenAPI 定义。应用可以通过 Python、TypeScript、Java/Kotlin、Go 和 C# SDK 接入，也可以使用 CLI 或 MCP 服务。

本地部署可以使用 Docker。集群部署可以使用 Kubernetes 容器后端。架构还提供可选的 Fast Sandbox 集成，用于基于模板的 microVM。不同后端支持的功能不完全相同，接入时应核对所用版本的兼容性。

数据面：execd 提供工作空间操作

execd 运行在沙箱环境中，提供命令、代码、终端和文件 API。前台命令可以通过 SSE 流式返回输出；后台命令可以查询状态和日志。交互终端使用 WebSocket PTY，适合运行 REPL、编辑器或 Agent CLI。

代码执行上下文可以使用 Jupyter 内核保留状态。文件 API 支持上传、下载及目录管理。应用还可以解析沙箱内服务的端口，用对应协议访问浏览器服务或其他工作负载。execd 文档

生命周期服务与 execd 的权限都需要保护。若执行端点暴露给未经授权的客户端，攻击者可能获得命令和文件操作能力。部署时要检查端点认证、网关访问和网络边界。

Kubernetes：批量创建和预热池

Kubernetes 后端通过 Operator 将沙箱意图转换为实际 Pod。其控制器使用 Kubernetes 常见的协调循环：观察期望状态和实际状态，再执行必要操作，使资源逐步收敛。Controller 文档

主要资源包括：

  • BatchSandbox：描述一个或多个沙箱，以及可选的任务和过期时间。
  • Pool：维护预先启动且处于可用状态的 Pod。
  • SandboxSnapshot：记录容器沙箱的快照及暂停、恢复状态。

直接创建 Pod 时，请求需要等待调度、镜像准备和容器启动。预热池提前准备 Pod；请求到来后可以领取现有容量。池中的空闲容量低于目标时，控制器继续补充。池耗尽时，请求可能等待或收到可重试的 429。

预热有两个重要代价。第一，空闲 Pod 占用集群资源。第二，Pod 模板在请求前就已确定：池模式不能随请求任意注入卷和网络策略，需要提前配置。资源池适合工作负载形状相对稳定、对启动延迟敏感的任务。

回收策略会改变隔离语义

文档列出三种池回收策略：Delete 删除并替换 Pod；Restart 原地重启容器；Noop 直接保留现有状态。Noop 虽然减少回收开销，但文件系统和进程状态可能进入下一次分配。处理不同用户或不可信任务时，必须将清理策略纳入威胁模型，不能只看创建速度。

容器沙箱的快照机制也有自己的边界。官方文档描述了持久化 rootfs、释放 Pod、再从快照恢复的流程，并限制该暂停恢复路径用于单副本沙箱。不要把它直接等同于所有进程内存状态都能恢复。

Fast Sandbox：预热容量与 Firecracker

Fast Sandbox 是 Kubernetes 上的可选后端。它通过 Fastlet 池提供预热容量，并从模板恢复 Firecracker microVM。模板制品已缓存时，创建过程可以避免每次从头启动内核。microVM 使用独立的 guest 内核，但仍需要配置宿主机、网络、镜像和管理接口的安全边界。Fast Sandbox 架构

这一设计适合大量相似环境的快速创建。代价包括预留容量、模板构建和分发、快照存储，以及更复杂的集群运维。冷制品分发、容量耗尽和跨节点恢复都需要单独测量。

Firecracker 路径支持暂停和恢复内存与磁盘状态。需要区分底层运行时恢复结束和客户端能够再次访问服务：网络、路由和就绪检查都可能增加端到端耗时。

网络控制与凭证

沙箱需要访问依赖仓库、模型 API 或业务服务时，完全禁止网络往往无法完成任务；直接放开公网又会增加数据外发风险。OpenSandbox 的出口组件支持按沙箱设置网络规则。Egress 文档

它提供两层不同的控制：

  1. DNS 过滤：阻止不允许的域名解析。它主要限制名称解析，不能单独视为完整的包级隔离。
  2. dns+nft 模式：结合 nftables 在网络层执行默认拒绝和允许规则。域名解析得到的地址以有限时长加入允许集合。

容器模式可以使用共享网络命名空间的 sidecar。Fast Sandbox 使用每个 Fastlet Pod 的共享出口进程，并区分不同沙箱。预热池需要提前在模板中配置所需的出口组件。

Credential Vault 可配合透明 TLS 拦截，在匹配的出站请求中注入凭证，减少把真实密钥交给沙箱工作负载的需要。文档将部分 TLS 拦截配置界面标为实验性。部署前应验证请求匹配范围、证书信任和失败行为。出口组件与同一网络命名空间中的透明 Service Mesh sidecar 也有兼容性限制；官方文档还指出当前 gVisor 与该出口机制不兼容。

出口策略不是完整的安全证明。文件挂载、容器权限、入口认证、宿主机配置和允许访问的服务本身都可能扩大风险。应根据任务权限设计规则，再用实际请求验证允许和拒绝路径。

本地使用流程

官方快速开始使用 Docker 和 Python 3.10 以上版本。安装和启动服务：

uvx opensandbox-server init-config ~/.sandbox.toml --example docker
uvx opensandbox-server

安装 Python SDK：

uv pip install opensandbox

下面的例子创建 Alpine 沙箱，执行命令，最后销毁环境：

import asyncio
from opensandbox import Sandbox


async def main():
    sandbox = await Sandbox.create("alpine")
    try:
        result = await sandbox.commands.run("echo 'Hello OpenSandbox!'")
        for line in result.logs.stdout:
            print(line.text)
    finally:
        await sandbox.destroy()


asyncio.run(main())

代码来自官方快速开始的调用方式，本文未实际运行。实际部署要结合版本文档配置服务地址、认证、镜像来源和资源限制。快速开始

如何理解官方性能数据

官方在 2026 年 10 月 8 日的双节点 ACK 集群中测试了 Fast Sandbox。测试使用已缓存模板、预热 Fastlet 容量和 Firecracker。SDK 创建计时覆盖到通过网关访问 guest /ping 成功，使用 10 ms 的就绪轮询间隔。测试环境与原始数据

测试 成功数 结果
串行创建，初始批次 100/100 P50 64.0 ms，P99 108.3 ms
10 并发创建 100/100 P50 102.7 ms，P99 125.4 ms
20 并发创建 51/100 成功请求 P50 136.7 ms；其余请求失败或超时
同节点暂停后 SDK 恢复 3 次样本 中位数约 62.66 秒

这些是特定环境下的工程测试，不是生产 SLA。20 并发的延迟分位数只统计成功请求，不能用来证明该并发水平可靠。官方还记录了容量拒绝和清理状态问题。暂停恢复测试中，底层运行时恢复只需数十毫秒，但 SDK 可用时间约一分钟；文档未确定这段差异的具体原因。

评估自己的部署时，应同时记录成功率、创建到可执行的端到端延迟、冷启动、池耗尽、回收时间和资源成本。还要分别测试快照创建、暂停与恢复，避免把内部阶段耗时当成用户可用时间。

选型和落地建议

OpenSandbox 适合需要统一管理 Agent 工作空间、并准备自行维护基础设施的团队。已有 Kubernetes 平台时，批量资源管理、预热池和网络能力值得评估。少量可信任务可以先用本地 Docker 路径验证接口和工作流。

建议按下面的顺序试点：

  1. 用单机环境跑通创建、文件传输、命令执行和销毁。
  2. 确定每类任务的镜像、CPU、内存、超时、存储和网络需求。
  3. 分别测试正常任务、超时任务、失败任务和服务中断后的清理。
  4. 按威胁模型选择容器或 microVM，验证端点认证与出口策略。
  5. 在真实负载下测试预热池容量、峰值并发、回收策略和冷启动。
  6. 对接日志、指标和审计，观察拒绝请求、资源消耗与孤儿资源。

沙箱平台降低了环境管理的实现成本，但安全效果仍来自运行时、权限、网络、凭证和运维策略的共同作用。选型时应将这些配置与任务模型一起验证。
