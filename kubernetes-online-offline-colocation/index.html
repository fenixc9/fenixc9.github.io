图解 Kubernetes 在线离线混部：资源回收、干扰隔离与 SLO 保护

在线服务按高峰需求申请资源，实际负载却随时间变化。离线任务需要计算资源，也通常能够排队或重试。两类工作负载放在同一批机器上，可以利用部分空闲资源。在线流量恢复时，离线任务又必须及时退让。

这项能力涉及调度预算、节点执行、内核隔离和业务观测。只降低 request，或者给在线服务设置一个较高的 PriorityClass，都不能独立完成整个过程。

本文以 CPU 为主线，讨论内存、缓存、I/O 和网络的边界，再比较 Koordinator 与 Volcano 的实现路径。全文配有六张 SVG 图。资料核验日期为 2026-10-23。架构图、容量数字和落地步骤用于解释与设计，没有在真实集群中部署或压测。

1. 先明确混部的范围与业务承诺

“在线”通常指对请求时延、错误率和可用性敏感的服务，例如搜索、推荐、交易接口。“离线”通常指更关注完成时间和吞吐的批任务，例如报表、数据处理、转码和部分训练作业。

这两个名字不能直接决定调度策略。流处理任务可能有严格时效要求。长时间训练任务可能无法频繁重启。一个后台服务也可能持有不能丢失的状态。

先确定每种任务接受什么承诺：

维度 在线服务需要回答 离线任务需要回答
性能目标 P99、错误率、可用性目标是什么？ 完成时限、吞吐或排队时间目标是什么？
资源弹性 突发需要多少资源、持续多久？ 最少可用资源是多少，压制后还能否产生有效进展？
中断容忍 多少副本能同时受影响？ 是否可重试、可检查点恢复、可幂等提交？
退出条件 哪些指标触发停止混部？ 多次失败后怎样停止重试或转入独立资源池？

三种混部深度

第一层是同集群管理，在线和离线仍使用不同节点池。第二层允许它们进入同一节点，开始共享 CPU、缓存、内存和设备。第三层进一步把在线已经申请但暂未使用的部分容量，转化为可回收的离线预算。

每深入一层，都需要增加对应的观测和保护能力。极端时延敏感、无法容忍共享资源干扰的业务，可以保留独立节点池。混部范围应由业务目标与测量结果决定。Koordinator Resource Model

2. Kubernetes 原生能力提供了哪些基础

上一篇调度流程文章解释了 request、队列和正式绑定。本篇继续讨论资源已经被请求、实际却暂未使用时的处理。

Kubernetes 通过 request 进行资源适配。假设节点可供 Pod 使用的 CPU 为 64 核，在线 requests 合计为 48 核。按标准 CPU 请求计算，剩余预算为 16 核。

即使在线实际只用了 20 核，默认资源过滤也不会自动把已有请求改成 20 核。要让离线任务利用这部分差额，需要额外的容量模型或调整资源声明。资源管理文档

原生能力 可以做什么 混部时仍需补足什么
requests / limits 参与调度预算，设置运行时资源约束 动态估算和回收可借用容量
PriorityClass / 抢占 影响调度顺序，必要时尝试让低优先级 Pod 让出位置 已运行任务之间的持续 CPU、缓存和带宽保护
Kubernetes QoS 依据资源声明分类，参与资源管理与压力处理 业务 P99 的直接保证、多维干扰控制
node affinity / taints 限定节点池、控制工作负载进入范围 同节点运行后的细粒度隔离
CPU Manager / Topology Manager 在适用配置下管理核分配和拓扑对齐 完整的离线容量回收与服务保护策略
节点压力驱逐 在内存、磁盘等压力下保护节点 业务退化前的预防控制与温和退让

PriorityClass 不会直接改变 Linux 线程优先级。提高 Pod 优先级也不会自动给它独占 LLC 或内存带宽。调度抢占主要处理等待调度的高优先级 Pod，不能替代节点上的实时资源控制。Priority and Preemption

Guaranteed、Burstable、BestEffort 是 Kubernetes 的资源分类。Guaranteed 也不等于端到端业务时延保证。共享缓存、内存带宽和外部存储仍可能成为瓶颈。Pod QoS

3. 动态资源回收怎样形成调度预算

理解混部可以先看一个简化的 CPU 模型。假设可供工作负载使用的容量为 64 核，已经扣除了系统预留。在线实际使用 20 核，再保留 12 核应对突发与估算误差，那么当前批处理预算可以暂估为 32 核。

批处理 CPU 预算示意
  = 可供工作负载使用的容量
  - 受保护工作负载的需求估计
  - 安全余量

这是解释性公式。具体产品可能使用不同的历史窗口、资源分类、保留比例和容量调整规则。还需要扣除已经计入相应预算的离线请求。不能把同一批已运行离线任务重复扣算，或者遗漏它们的占用。

需求估计也不应只取一个瞬时采样值。需要考虑在线峰值、采集延迟、Pod 启动、滚动发布以及突发相关性。Koordinator 的资源模型区分短期与较长期的需求保留，体现了借用规模与稳定性之间的取舍。Resource Model

batch 资源是另一种记账视图

Koordinator 为批任务提供 kubernetes.io/batch-cpu 和 kubernetes.io/batch-memory 等资源类型。它们可以出现在节点的 Allocatable 中。批任务声明相应请求，调度层据此计算放置条件。

标准 CPU 和 batch CPU 最终使用同一套物理 CPU。 两种资源不能相加成互相独立的硬件容量。调度层允许借用的前提，是运行时有能力压制或回收离线使用量。

在线升载后，容量计算可以降低 batch 预算。但降低 Allocatable 不会直接终止已经运行的 Pod。因此，容量更新与节点侧回收必须配合。Batch Colocation Quick Start

内存不能直接套用 CPU 的思路

CPU 时间通常可以通过减少配额或可用 CPU 来压制。已经分配的匿名内存不能靠暂停进程立即释放。回收文件缓存还可能引入后续 I/O，内存压缩与交换也有成本。

内存混部需要更保守的预算。平台要考虑 RSS 增长、直接回收停顿、PSI、OOM 以及任务退出时间。严重压力下可能需要直接驱逐离线任务。不能先把内存借满，再假设在线需要时总能瞬间拿回。

4. 调度控制与节点执行要形成闭环

混部至少需要两条控制链。

第一条影响后续放置。采集组件报告节点和 Pod 用量。控制逻辑计算可借用容量。调度器依据容量、配额和策略决定是否继续接收离线任务。

第二条控制已经运行的任务。节点 Agent 调整相应 cgroup、CPU 集合或其他资源参数。压力持续时，系统执行允许的驱逐策略。

控制动作 直接影响
下调 batch 调度预算 限制后续新增任务
暂停队列准入或降低并发 减少后续压力增长
收缩离线 CPU 集合或配额 限制已运行任务使用 CPU
内存保护、回收阈值与上限 调整回收和压力行为，依赖内核及配置
驱逐或终止离线任务 释放任务占用，但存在终止、清理和重试成本

两条链的更新周期可能不同。在线突发时，节点侧保护不能完全等待一次全局重新调度。采集和控制也存在延迟，因此仍需要安全余量。

这里还要区分资源指标与业务指标。节点 CPU 低于某个阈值，并不证明在线 P99 达标。产品提供资源保护机制后，平台仍应把真实请求时延、错误率和错误预算接入观测与决策。

5. 干扰来自 CPU 之外的多个维度

CPU：权重、配额与核分配各有作用

CPU 权重影响竞争时的相对份额。CPU 配额限制一段时间内的累计运行时间。核绑定限定进程可运行的位置。

它们解决不同问题。在线服务的 CPU limit 太紧，可能在短时突发时被节流。离线线程很多，也可能增加运行队列和内核路径上的竞争。核绑定如果没有考虑 SMT 同胞核与 NUMA，仍可能留下干扰。

CPU Burst 可以缓解部分配额造成的突发节流，但它不能增加物理 CPU，也不能替代离线压制。是否可用需要检查内核、cgroup 以及相应组件实现。Koordinator CPU Suppress、Volcano v1.14 混部更新

缓存与内存带宽：低 CPU 使用率也会退化

离线扫描、压缩或数据处理可能持续访问内存。它们可以驱逐在线热点数据，或者占满内存带宽。此时 CPU 平均利用率不一定很高，在线时延却可能明显上升。

CAT、MBA 等硬件能力可用于部分缓存和带宽控制。支持范围依赖 CPU 型号、内核接口和平台适配。它们也不能隔离所有共享结构。Koordinator SLO Configuration

磁盘与网络：节点保护覆盖不到所有外部瓶颈

离线任务可能同时争抢本地磁盘、网卡、对象存储、数据库或元数据服务。即使节点 CPU 已被压制，远端系统仍可能受影响。

网络限速需要明确作用方向、协议和计量位置。磁盘控制需要检查块设备、文件系统与 I/O 路径。共享存储还需要服务端配额和容量规划。不能根据一个 cgroup 参数推断端到端 I/O 已隔离。

Volcano 提供基于流量分类与限速的网络保护设计。部署时需要验证网卡和网络模式，以及配置实际覆盖的流量路径。Cloud Native Colocation

6. Koordinator：资源模型、调度扩展与节点 QoS 配合

Koordinator 围绕混部建立资源分类、动态容量和节点控制机制。常见组件分工可以概括如下：

部分 职责
koord-manager 及相关控制器 根据指标与策略维护资源视图、处理控制面逻辑
koord-scheduler 处理相应调度扩展与资源请求
koordlet 节点指标采集、资源协调、压制与适用的驱逐逻辑
NodeMetric / NodeSLO 等对象 承载观测信息或节点级策略，具体字段依版本

QoS 与优先级是两个维度

Koordinator 的 QoS 包括 SYSTEM、LSE、LSR、LS 和 BE。它们表达不同的节点运行质量要求。优先级则表达资源分配和调度顺序等要求。

典型微服务可以评估 LS。需要更确定资源分配的服务可以评估 LSR 或其他隔离策略。可压制、可驱逐的批任务常使用 BE。最终分类仍需要对应业务和部署条件。

Koordinator 的 BE 标签与 Kubernetes 的 BestEffort 分类属于不同的定义体系。 前者表达 Koordinator 的运行策略。后者根据标准 CPU、内存等资源声明计算。即使名称接近，也需要分别检查。Koordinator QoS、Kubernetes Pod QoS

一个批任务配置骨架

下面改写自 Koordinator v1.7 的官方手动配置示例，用于说明字段关系。需要先安装兼容的 Koordinator 组件、创建 namespace 与 koord-batch PriorityClass、启用相应节点策略，并确认节点已经上报 batch 资源。此清单未在本地集群执行。

apiVersion: batch/v1
kind: Job
metadata:
  name: batch-colocation-demo
  namespace: batch-demo
spec:
  backoffLimit: 2
  template:
    metadata:
      labels:
        koordinator.sh/qosClass: BE
    spec:
      schedulerName: koord-scheduler
      priorityClassName: koord-batch
      restartPolicy: Never
      containers:
        - name: worker
          image: busybox:1.36
          command: ["sh", "-c", "echo batch-demo; sleep 30"]
          resources:
            requests:
              kubernetes.io/batch-cpu: "1000"
              kubernetes.io/batch-memory: "2Gi"
            limits:
              kubernetes.io/batch-cpu: "1000"
              kubernetes.io/batch-memory: "2Gi"

这个示例只验证配置意图，不会产生有代表性的批处理负载。batch-cpu: "1000" 在该资源模型下表示 1000 毫核，即一核 CPU 对应的批处理请求，不能按标准 cpu: "1000" 解读。

使用扩展资源名也不会让普通 kubelet 自动把它变成 CPU、内存限制。Koordinator 的节点组件与策略必须正常工作。官方配置示例

运行时的保护边界

Koordinator 的 CPU Suppress 可以随在线用量变化调整 BE 可用 CPU。它还有基于 CPU 满足度的驱逐策略。后者处理大量离线任务被压缩到很少 CPU 后，几乎没有进展却仍在争抢资源的情况。

SLO 配置还覆盖 Memory QoS、缓存和内存带宽等机制。部分增强 CPU QoS 接口依赖 Anolis 等适用内核，硬件资源控制也有平台前提。安装 Koordinator 不代表所有增强隔离特性都能生效。CPU Suppress、CPU Eviction、SLO Configuration

7. Volcano：作业调度体系与混部 Agent 配合

Volcano 的队列、公平分配、Gang 和抢占能力适合组织批任务。混部能力还需要 Volcano Agent 等节点侧组件参与。仅安装调度器、启用一个 overcommit 参数，不能等同于获得完整的在线运行时保护。

官方混部设计包含动态资源超卖、资源分类、CPU 与内存保护，以及网络带宽控制。资源上报方式可以有不同模式。调度层的超卖、队列间资源回收与节点运行时回收也应分别理解。Cloud Native Colocation、Queue Resource Management

操作系统限制必须按功能和版本核对

官方旧式混部指南仍保留了 Agent 只支持 openEuler 特定版本的说明。然而，v1.14 发布说明已经明确加入 Ubuntu、CentOS 等通用操作系统支持、cgroup v2 适配、CPU 动态压制和 Memory QoS。

因此，不能把“Volcano 混部只能使用 openEuler”当作当前所有版本的结论。也不能根据通用系统支持，反推旧指南中的每个增强内核接口都存在于普通发行版。

落地时分别核对 Agent 版本、cgroup 模式、驱动管理方式、内核参数与目标功能。本文以发布说明作为版本变化依据，没有验证任意操作系统组合。Volcano v1.14 Release

同时使用多个系统要明确控制权

如果平台已有 Volcano 队列，也准备引入 Koordinator 的节点治理，需要先划清调度与资源模型的所有权。不要让两个控制器同时改写同一组 batch 容量或 cgroup 参数。

任务选择哪个 scheduler、谁管理队列准入、谁负责节点预留、谁驱逐、谁控制重试，都需要明确。本次调研没有验证 Volcano 与 Koordinator 的具体组合版本，不能把它们的功能列表直接拼成可部署方案。

8. 怎样选择实施路径

9. 在线保护应快速收缩、缓慢恢复

这张图是平台设计建议。它没有宣称安装任一项目后，就自动获得相同的业务 P99 控制器。

在正常阶段，平台限制离线准入与并发，同时保留安全余量。在线升载时，应及时压制已经运行的离线负载，并减少新增任务。压力持续时，再按策略终止允许重试的任务。严重内存压力等紧急情况可以直接触发驱逐，不能假定总能按温和步骤完成。

恢复阶段需要稳定窗口和增量限制。刚驱逐任务就全量补回，可能触发连续的创建、驱逐和重试循环。离线调度器和工作负载控制器必须一起限制恢复速度。

故障或变化 建议的预设行为
节点指标过期 停止扩大借用，不用旧低负载数据持续增加预算
节点 Agent 异常 验证已有 cgroup 状态与实际控制是否保留，必要时撤回离线负载
在线突发超过估计 优先保护在线，限制离线并发或驱逐可重试任务
大规模离线任务同时失败 对重试限速，避免镜像、存储和控制面出现第二轮峰值
驱逐后在线仍未恢复 检查共享缓存、远端存储、网络或在线自身问题，必要时退出混部

还有一个常见误区：PDB 不能作为所有驱逐路径的统一保护。kubelet 的节点压力驱逐不受 PDB 约束。scheduler 抢占和平台主动驱逐也有各自行为。离线任务必须从应用层支持中断与恢复。Node-pressure Eviction

10. 用在线 SLO 与离线有效产出共同验收

先建立隔离基线

固定在线流量模型，记录吞吐、P95/P99、错误率和资源使用。再测一组代表性离线任务的完成时间、资源消耗和恢复成本。保留独立资源池作为对照。

比较时应固定有效业务量。把更多请求排在应用外部，可能让服务内部 P99 看起来更好，却降低整体服务质量。

从影子计算进入小范围试点

先只采集和估算可回收预算，不立即投放更多任务。检查缺失指标、异常尖峰和容量抖动。

再选择少量低风险节点与可快速重试的任务。先验证 CPU 控制，谨慎加入内存和 I/O 压力。观察结论不能自动外推到长时训练、数据库或其他硬件池。

Koordinator 环境可以先使用只读命令检查对象：

kubectl get node <node> -o yaml
kubectl get nodemetric <node> -o yaml
kubectl get nodeslo <node> -o yaml
kubectl get pod <pod> -n <namespace> -o yaml
kubectl describe pod <pod> -n <namespace>

NodeMetric、NodeSLO 等 CRD 需要对应组件已经安装。检查对象只能证明配置或观测存在，不能单独证明内核参数已经生效。还需要核对 Agent 日志与节点实际资源控制状态。

压测必须覆盖突发、故障与恢复

维度 需要覆盖的场景
在线业务 阶跃升载、短时突发、滚动发布、扩容和依赖变慢
离线负载 CPU 密集、内存带宽密集、RSS 增长、磁盘与网络压力
平台故障 指标延迟、Agent 重启、API 不可用、节点状态变化
恢复路径 任务退出耗时、检查点恢复、幂等输出、重试限速与回收震荡

验收指标不能只有 CPU 利用率

目标 需要观察的指标
在线保护 同等流量下的 P99、错误率、可用性与错误预算消耗
资源干扰 CPU throttling、运行队列、PSI、回收停顿、OOM、I/O 和网络压力
离线有效产出 完成任务数、完成时长、排队时间、重试次数与检查点损失
平台稳定性 指标新鲜度、预算更新与抖动、驱逐频率、恢复速度
总成本 在线与离线资源成本、失败重算成本、额外组件和运维成本

判断收益时，使用单位有效产出的总成本。CPU 利用率升高，但在线错误预算恶化、批任务不断重算，不能据此认定混部成功。

本文没有给出统一的超卖比例或全行业收益百分比。可接受的借用规模需要通过业务基线、节点能力、控制延迟和任务恢复成本共同确定。
