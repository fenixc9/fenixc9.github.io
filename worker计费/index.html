【cloudflare】Cloudflare Workers 计费模型

调研日期：2026-10-09。金额均为美元，按官方公开价格估算，不含税费、汇率及第三方服务费用。本文针对普通 Workers 的 Standard 模型，不适用于 Enterprise 合同或 Workers for Platforms。

1. 核心价格

Workers 的计算费用是 订阅费 + 超额请求费 + 超额 CPU 时间费，不是按服务器台数收费。[1]

项目 Workers Free Workers Paid / Standard
基础费用 $0 每个账户每月最低 $5
请求额度 每天 100,000 次 每月包含 10,000,000 次
超额请求 受免费额度限制，不是自动按量付费 $0.30 / 百万次
CPU 额度 每次调用 10 ms 上限 每月包含 30,000,000 CPU-ms
超额 CPU 受单次执行限制 $0.02 / 百万 CPU-ms
等待 / 墙钟时间 不按持续时间收费 不按持续时间收费
出站流量、带宽 Workers 无额外流量费 Workers 无额外流量费

付费额度按账户共享理解，不能给每个 Worker 分别套一次包含额度。Pages Functions 也按 Workers 计费。[1][5]

2. CPU 时间与响应耗时的区别

CPU time 是代码实际占用 CPU 的时间。等待 fetch()、KV 或数据库返回，不计入 CPU time；解析 JSON、渲染、计算等执行工作会消耗 CPU。[2]

例如某请求总耗时 1 秒，其中等待上游 990 ms、执行代码 10 ms，估算 CPU 用量应使用 10 ms，而不是 1,000 ms。这是示意模型，实际应读取平台测量值。

运行限制 Free Paid
单次 HTTP 请求 CPU 10 ms 默认 30 秒，可配置至 5 分钟
Cron CPU 10 ms 间隔小于 1 小时：30 秒；间隔至少 1 小时：15 分钟
内存 每个 isolate 128 MB 每个 isolate 128 MB

HTTP 调用没有固定墙钟时长上限，但要求客户端连接保持；断开连接或响应结束后，相关任务可能被取消。ctx.waitUntil() 最多额外延长 30 秒。因此“不按等待收费”不等于可以无限运行后台任务。[2]

免费请求额度在 UTC 00:00 重置，即台北时间每天 08:00。超额后，普通 Worker 路由按 fail-open / fail-closed 配置绕过 Worker 或报错，不应假设自动升级。[2]

3. 请求如何计数

场景 计费边界
外部请求调用 Worker 计入 Workers 请求量
Worker 向普通上游发出子请求 不额外收 Workers 子请求费；上游费用另算
WebSocket 建连时的 Upgrade 计一次请求；消息不计作 Workers 请求
Static Assets 直接返回资源 默认请求免费、无限量，资源存储无额外费用
run_worker_first 让资源请求先执行代码 发生 Worker 调用，不能当作纯静态免费请求
Service Bindings 调用同账户其他 Worker 绑定本身不增加费用；执行代码仍消耗 CPU
通过公开 URL 调用另一个 Worker 发起端不加子请求费；若实际触发目标 Worker，目标端计一次入站请求

依据：[1][3][4]。子请求不另收 Workers 请求费，不意味着 KV、D1、R2 等操作免费。

3.1 Worker 请求外部服务

以下针对普通 Workers Standard 模型，不包含 Workers Caching 的特殊计费路径：[1]

用户 → Worker A → fetch("https://api.example.com")
项目 计费方式
用户调用 A 计 1 次 Workers 请求
A 请求普通外部 API 不额外收 Workers 子请求费
等待外部 API 返回 不计 CPU 时间，也不按等待时长收费
A 校验参数、解析 JSON、处理结果 累计实际 CPU 时间
Workers 出站带宽 不额外收带宽 / egress 费
外部 API、源站、数据库 上游自己的请求费、流量费或数据操作费另算

例如用户调用 A 一次，A 再访问 10 个普通外部 API，仍是 1 次 Workers 请求 + A 的实际 CPU 时间，不是 11 次 Workers 请求。上游返回很慢会增加响应耗时，但不因此增加等待部分的 CPU 费用。[1]

3.2 Worker 之间使用 Service Bindings

用户 → Worker A ──Service Binding──→ Worker B ──Service Binding──→ Worker C

同账户使用 Service Bindings 时，内部绑定调用不增加请求费；被调用 Worker 的执行时间仍计入 CPU 用量。[1][4]

例如 A、B、C 分别使用 2、5、3 CPU-ms，这条调用链按 1 次入口请求 + 合计 10 CPU-ms 估算，而不是 3 次请求。[1]

绑定本身不加费用，不代表 KV、D1、R2、Durable Objects 等服务操作免费；这些费用仍应分别预算。

3.3 Worker 之间通过公开 URL 调用

用户 → Worker A → fetch("https://worker-b.example.com") → Worker B

这里分别看发起端与接收端：[1]

  • A 发起端：fetch() 是子请求，不额外收子请求费。
  • B 接收端：如果该 HTTP 请求实际进入并触发 B，属于 B 的一次入站调用，计入请求量。
  • CPU：A、B 实际执行的 CPU 均计入对应账户用量。

因此，按官方入站请求与子请求规则推导，这条链路应按 2 次 Workers 请求 + A/B 的实际 CPU 理解，不能套用 Service Bindings 的计费规则。若 B 属于另一个账户，则其入站调用与 CPU 计入 B 所属账户，不是全部记到 A。[1]

同一次用户访问的调用链 计费请求数 CPU 用量
A → 10 个普通外部 API 1 A 的实际 CPU
A → B → C，内部均使用 Service Bindings 1 A + B + C
A → B → C，内部均使用公开 URL 且实际触发目标 Worker 3 各 Worker 的实际 CPU，按账户归属累计

建议：同账户拆分 Worker 服务优先使用 Service Bindings；第三方 API 使用普通 fetch()。 表中的请求数不含启用 Workers Caching 后的特殊路径。

3.4 缓存的特别注意事项

启用 Workers Caching 后，缓存命中仍按 Workers 请求单价计费，包括该机制涉及的静态资源请求和 Worker-to-Worker 调用；只有实际执行 Worker 的缓存未命中 / 绕过请求消耗 CPU。[1]

不要将它与“直接由 Static Assets 返回文件”混淆，也不要把“命中缓存”一概理解为零请求费。若代码先运行再调用 Cache API，同样不能认为该次调用没有执行成本。

特别是 Service Bindings：普通内部调用不增加请求费，但涉及 Workers Caching 的 Worker-to-Worker 请求应按其专门规则核算，不直接沿用上面“整条绑定调用链只有一次请求”的简化估算。[1]

4. 月费估算公式

以下公式根据 [1] 的单价推导，只计算普通 Workers 运行费：

R = 月度计费请求数（包含适用的 Workers Caching 命中请求）
C = 月度实际累计 CPU 时间，单位 ms

请求超额费 = max(R - 10,000,000, 0) / 1,000,000 × 0.30
CPU 超额费 = max(C - 30,000,000, 0) / 1,000,000 × 0.02
Workers 月费 = 5 + 请求超额费 + CPU 超额费

无缓存、每次请求均执行时，可以近似 C = R × 平均 CPU-ms。有缓存或调用链时，应累计实际执行部分，不能直接用全部访问量乘单个 Worker 的平均值。

注意单位：100 万 CPU-ms = 1,000 CPU 秒，不是 100 万秒。

月度计费请求 平均 CPU / 执行请求 CPU 总量 请求超额费 CPU 超额费 月费

免费版不能简单视作“每月 300 万次”：它是每日限制。某天有 20 万次、其他天几乎没有，也会触及当天上限。[2]

5. 完整账单还要算什么

服务 额外计量维度 依据
Workers KV 读、写、删除、列举操作及存储 [1]
D1 读取行数、写入行数、数据库存储；不是只按 SQL 条数 [8]
R2 存储、Class A / B 操作；不同存储类别有不同规则 [9]
Durable Objects 请求、计算时长及存储；不能套普通 Worker 的 CPU 公式 [10]
Workers AI 模型推理用量，不能只算外层 Worker [11]
Workers Logs 日志事件写入量 [6]
Workers Builds 构建分钟数，与运行时 CPU 分开 [7]

这些服务可能有包含额度，但不代表开通 $5 套餐以后可以无限使用。

日志费用：一个请求不一定只有一条日志

截至调研日，Workers Logs 免费版包含每天 20 万事件、保留 3 天；付费版包含每月 2,000 万事件，超额 $0.60 / 百万事件，保留 7 天。[6]

例如每月 1,500 万请求，每次有 1 条 invocation log 和 1 条 console.log，100% 采样会写入 3,000 万事件，日志超额费为 $6；加上上述 $8 运行费，合计 $14，尚未计入其他服务。

已公告但尚未生效的变更：2026-12-01 起 Workers Logs 改用 Cloudflare Observability 定价。 在此日期前仍使用上述事件定价；跨过该日期后需要重新核价，不能沿用本节估算。[6][12]

官方公告的新模型改按数据摄入量与存储量计费，相关日志 / traces 共享账户额度：[12]

项目 新 Free 新 Paid
包含摄入量 0.5 GB / 天 50 GB / 账单周期
超额摄入 不提供，达到额度后停止摄入 $0.25 / GB
包含存储 含 7 天保留，不单独计量 10 GB-month / 账单周期

摄入量按压缩前数据计算；摄入与存储是两个独立计量项，不能互相抵扣。Enterprise 按合同续约时间迁移。此表是未来生效规则，不用于 2026-10-09 的账单估算。[12]

构建费用

Workers Builds 免费版每月包含 3,000 分钟；付费版包含 6,000 分钟，超额 $0.005 / 分钟。[7] 此项仅针对使用该构建服务的用量。

6. 成本控制建议

以下是基于上述规则的工程建议，不是额外的平台承诺：

  • 看实际 CPU 指标：不要拿接口响应耗时估算 CPU 账单。
  • 区分静态与动态路由：避免无必要地让所有静态资源都先经过 Worker。
  • 同账户服务拆分优先使用 Service Bindings：不要把公开 URL 调用与内部绑定视作同一计费路径。
  • 给单次调用设置合理 CPU 上限：例如简单 API 可先评估 100 ms 是否够用，再根据监控调整。
  • 降低日志采样率：尤其避免高访问量下每个请求输出多条调试日志。
  • 单独预算数据和 AI 服务：数据库扫描、存储操作与模型调用可能比外层 Worker 更贵。
  • 监控用量并限制滥用：单次 CPU 上限不是账户月费封顶，也不能阻止大量短请求累计费用。

可合并到已有 wrangler.jsonc 的配置片段：[6][13]

{
  "limits": {
    "cpu_ms": 100
  },
  "observability": {
    "enabled": true,
    "head_sampling_rate": 0.01
  }
}

这里的 100 是每次调用 CPU 上限 100 ms，0.01 是请求级 1% 日志采样。CPU 配置需符合 Standard 模型规则，运行限制只在部署到 Cloudflare 网络后执行，不在本地开发中强制执行。[13]

选择时可按以下思路判断：低流量项目先检查每日额度与 10 ms CPU 是否够用；需要更高额度或更长 CPU 执行时间时，再预算 Paid。SSR、复杂计算、实时状态与 AI 应分别测量 CPU、Durable Objects 和模型成本，不能只看请求单价。

7. 真实场景：VM 与 Workers 成本对比的证据

补充调研日期：2026-10-09。结论：有真实生产迁移案例，但本次检索没有找到同时控制代码、吞吐、延迟、可用性、地域和全部账单项目的独立 VM / Workers 长期对照。不能把某次迁移的降本比例推广到所有应用。

7.1 值得参考的案例

案例 业务与旧方案 作者报告的变化 能说明什么 / 不能说明什么
DevCycle，2022-11-14 [14] 功能开关 API 和事件摄入；AWS 侧使用 EC2 / EKS、负载均衡、Kafka 和 Snowflake Workers 处理 10 倍以上突发流量，而 AWS 事件管道跟不上，作者计划迁移事件入口 与 EC2 有直接关联的生产架构案例，但没有公开可复算的费用表；不能把扩容收益解释为某个已验证的降本比例

7.2 看起来有数字，但不宜当作成本结论的材料

  • Matrix homeserver 示例 [17]：2026-01-27 的 Cloudflare 文章明确补充说明这是个人概念验证项目；其表格给出 VPS $20–50/月、Workers 活跃时 $3–10/月，但没有公开负载、CPU、数据操作量和实际账单。尤其不能把表中的“闲置低于 $1”理解为整个 Paid 账户月费：Paid 本身最低 $5/月。[1]
  • EmDash / WordPress 测试 [18]：开源报告于 2026-04-15 重生成，记录约 3.5 天、4,732 个样本；比较 Workers + Astro / D1 与 Hetzner 上的 WordPress + PHP / MySQL。未优化时平均 TTFB 为 593 ms 与 132 ms。它提供了不利于 Workers 的真实应用性能证据，但软件栈不同、单个观察点、没有对应成本表，也不是吞吐压测；不能推广成所有 Worker 都更慢或更贵。
  • 只有 RPS 的压测：短时间峰值吞吐不是全天可持续容量；还需核查错误率、P95/P99 延迟、缓存冷热、数据库、持久化和机器配置。

7.3 按同一价格口径估算，不冒充实测

DigitalOcean 官方目前列出基础共享 CPU Droplet：1 vCPU / 1 GiB / 25 GiB SSD / 1,000 GiB 出站额度，$6/月。[19] 这是单台机器价格，不包含备份、负载均衡和托管数据库等可选项目，也不自动提供跨区域高可用。

下面仅比较这个 VM 的固定报价与 Workers 的运行时公式：[1][19]

假设业务量 Workers 运行费 单台 $6 VM 的标价 能否直接判定谁便宜
每月 100 万次，每次 7 CPU-ms $5.00 $6.00 价差只有 $1；需测量 VM 能否满足性能和其他服务成本
每月 1 亿次，每次 7 CPU-ms $45.40 $6.00 VM 若能承载并满足 SLA，则其运行费更低；但容量未实测
每月 1 亿次，每次 50 CPU-ms $131.40 $6.00 CPU 越重，Workers 用量费越高；不能假设最小 VM 扛得住

同一公式还可反推：平均每次 7 CPU-ms、无缓存且无附加费用时，Workers 约在每月 1,045 万次请求达到 $6。这个交点只比较价格，并不证明 $6 VM 能承载该负载。

7.4 从这些案例能得出的判断

以下是基于案例和计费模型的推论，而不是所有应用都成立的结论：

  • 低流量或间歇性服务：Workers 避免闲置机器费用，通常值得先评估；高峰能否运行、每日免费限制是否够用仍需检查。
  • 全球 API、Webhook、接收 / 转发入口：轻 CPU、高 I/O、流量突发的场景与 DevCycle / Baselime 更接近；AWS 网络、对象存储和负载均衡账单可能比计算本身更关键。
  • 持续高流量、单地域业务：VM 固定价有优势潜力，尤其数据库可就近部署时；需要实际压测，而不是把短时最大 RPS 直接乘整月秒数。
  • CPU 密集任务：Workers 的累计 CPU 计费需要重点评估；VM 可把固定资源持续利用，但也需要容量和排队模型。
  • 重数据库 SSR：不能只比较 Worker CPU 与 VM 月租；数据库位置、读取量、缓存命中和用户地域可能同时改变费用与延迟。

实际选型最好拿自己的应用做两端测试：同数据、同缓存策略、同响应大小，约定错误率和 P95/P99 目标；分别记录请求量、CPU-ms、数据操作量、出站量、日志与 VM 资源占用。单机对单机、跨区域高可用对跨区域高可用，最后再把运维时间与云账单分列。

案例与来源 如何使用 Workers 报告的收益 证据与适用边界
Edgemesh [20] 约 95% 客户 API 迁至 Workers + KV / Cache API，替代美国、欧洲、东南亚的多区域部署 全球云计算账单降低 72%，API 响应提升约 5 倍 有负责人引述，缺少完整账单与负载数据；适合参考多区域轻 API，不是单台廉价 VM 对比
Shopify Oxygen，2022-08-23 [21] Gateway Worker 做授权和路由，再分发到商店 Storefront Worker 减少自建全球平台的运维、扩容和安全复杂度 使用方的工程文章，没有费用表；使用 Workers for Platforms，不能套普通 Workers 的套餐报价
Rocket.net [22] 保留 WordPress 后端，Workers 做 ShopShield 流量削峰、SEO 响应头控制；KV 记录访客状态 作者称减少额外招聘需求，每年节省数十万美元人力成本 支持混合架构与运维收益，不代表 WordPress 整体迁入 Workers；CDN 总流量不等于 Worker 调用量
Stack Overflow [23] 入口捕获遥测 HTTP headers，删除敏感 / 内部头，再送集中日志 避免在多个后端分散实现和重新拼接日志 没有 Worker 降本金额；页面中的 DDoS / Bot 防护收益来自其他产品，不应归于 Workers
Volcano Studio [24] 游戏 API / 逻辑使用 Workers；内容分发由 S3 / CloudFront 迁至 R2 / CDN 作者称整体基础设施成本下降 80%，功能上线耗时缩短约 35% 降本叙述重点是存储出站和分发，不是游戏计算迁到普通 Workers 单独省 80%
Silvermine AI，2026-02-09 [25] Next.js 经 OpenNext 迁至 Workers，同时迁移 CI/CD 自述 Vercel 构建费约 $270/月，迁后使用 $5/月套餐内构建额度 主要是构建 / 套餐成本，不是请求计算成本；缺原始发票，文中部分额度描述不准确，以官方为准 [1][7]
Currency Converter Board，2026-04-24 [26] Railway 的 FastAPI API 重写为 Hono / TypeScript，迁移 OAuth、外部 API 和数据访问 移除约 $5/月 Railway 固定费用，以 Workers 免费层为目标；自述约一天完成迁移 附旧账单图片，但无精确新账单与性能数据；小应用案例，不是现成 Python 服务无成本原样迁移

Edgemesh、Rocket.net、Stack Overflow、Volcano Studio 是 Cloudflare 发布的客户描述，有营销偏向；Shopify 是使用方工程记录；另外两篇是使用方自述，仍非独立审计。不能将云账单、构建费、存储出站和人力节省混成一个通用降本比例。

7.6 反例补充：边缘部署不自动消除数据库瓶颈

前述 EmDash 报告还包含优化记录：[18]

  • 原始平均 TTFB：Workers / D1 593 ms，WordPress / MySQL 132 ms。
  • 减少串行查询、批量查询与延迟加载后，EmDash 降至 373 ms；仅有 30 轮后续测试，不能与原始数千样本混为同一统计窗口。
  • 进一步增加整页缓存后，华沙单 PoP 的文章页缓存命中约 110 ms。
  • 作者明确提醒：缓存后的 EmDash 对未缓存的 WordPress 不公平，应在两端都采用可接受的缓存策略后比较。

这不是“Worker 一定慢”的证据，而是“数据路径、查询次数、缓存策略比边缘标签重要”的证据。官方 Placement 文档也说明：依赖后台数据库 / API 的 Worker，靠近后台可能比靠近用户更快。[27]

8. 选型结论：什么情况下应该使用 Workers

以下是基于案例、计费模型和平台约束的工程判断，不是官方性能 / 费用保证。普通 Workers 与 Containers、Workers AI、Workers for Platforms、Durable Objects 等有不同费用和边界。

8.1 一句话结论

优先用 Workers 承载“请求驱动、轻计算、重 I/O、需要全球入口或不想维护闲置服务器”的逻辑；不要因为 $5 起价就默认把完整后端迁进去。

它最有价值的替代目标往往不是一台便宜 VM，而是多区域入口、闲置容量、接入逻辑和部分运维工作。[20][21][22] 等待上游 I/O 不按持续时间收费，是轻计算场景的直接优势。[1][2]

8.2 优先考虑

场景 为什么值得考虑 先验证什么
Webhook、表单、OAuth 回调、轻量 API 访问间歇、接收 / 校验 / 转发，不需要闲置常驻机器 峰值、CPU、可靠入队、幂等和外部服务费
API 网关、签名验证、A/B 路由、请求聚合 独立放入口，不必重写整个后端；Shopify / Stack Overflow / Rocket.net 有对应模式 SDK 兼容、缓存正确性、鉴权；串行上游是否反而增加延迟
全球读多 API、轻量个性化、可缓存内容 不必为全球入口维护多个区域容量；参考 Edgemesh 用户地域、缓存命中 / 失效、数据库与上游位置
低流量 MVP、工具站、小型 SaaS 减少部署运维，避免低利用率机器 免费层与 Paid 分别核算；免费迁移案例不代表 SLA 等价
静态前端 + 少量动态接口 静态资源直接免费返回，只让动态路由执行代码 不要无必要设置 run_worker_first；纯静态内容不需要 Worker 执行 [1][3]
外部 AI 的流式接口 Worker 负责身份校验、编排和转发，推理由上游完成 模型与数据费、取消、连接生命周期、滥用限额；等待免费不等于推理免费 [1][2][11]

没有通用的“每次 CPU 小于多少 ms 就一定划算”阈值。相同 CPU 下，请求量、附加服务和 VM 利用率仍会改变结果。

8.3 可以用，但先验证

  • 完整 Next.js / SSR：测实际功能和依赖，不只测首页；测数据库往返、冷请求和缓存。Shopify 说明完整前台可行，CMS 对照说明迁移不自动提升性能。[18][21][28]
  • 连接区域性 PostgreSQL / MySQL 的 API：减少串行查询，评估 Placement 让计算靠近数据库；也可仅迁入口、保留区域后端。[27]
  • 聊天、协作、轻量房间服务：评估 Workers + Durable Objects；WebSocket Hibernation 可在无事件时免除 DO 时长费，但活跃时长、消息与存储仍需预算。[10][30]
  • 定时 / 后台处理：短任务可尝试；长流程应拆步骤或选任务平台，不能靠 HTTP 响应后无限执行实现。[2]
  • 抓取、内容分发、图片处理：区分转发与重计算，浏览器 / 图片 / AI 服务单独计价；直接对象访问能满足需求时避免多余代理。Volcano 的收益不能脱离 R2 / CDN 解释。[24][31]

8.4 更倾向 VM / 容器

以下是选型倾向，不是宣称技术上绝对无法实现：

  • 持续、高利用率的 CPU 计算：固定容量可能更合算；Workers 累计 CPU 费随计算量增长。[1]
  • 需要完整 Linux、原生二进制、系统进程或机器权限：不要把 Workers 当 VM；Node.js API 是兼容子集，部分模块可导入但不可调用。[28]
  • 大内存、本地状态、本地数据库的现成服务：普通 isolate 内存上限 128 MB，且不是每请求独占额度；为迁移重构可能不划算。[2]
  • 单地域、密集数据库交互：比较现有同地域架构与 Placement 后 Worker，不凭“全球边缘”判断更快。[18][27]
  • 已有廉价 VM、资源有余量、性能符合需求：仅省少量月费却需重写框架或存储，不建议迁移；小型 Hono 案例也包含明确重写工作。[26]
  • 强可移植性要求 / 现有生态高度耦合：计入绑定替换、数据导出和回滚成本，可先只迁入口。[21][22][23]

8.5 默认建议：入口与核心后端分别选

用户 → CDN / Rules / WAF（按需）
     → Workers：鉴权、路由、可缓存读取、轻量编排
     → 区域 VM / 容器：复杂业务、重计算、数据密集逻辑
     → 同地域数据库

这是工程建议，不是所有系统都需要增加一层。Rocket.net 是保留后端、增强入口的参考，Stack Overflow 是抽出特定接入逻辑的参考。[22][23] 如果只是原样代理每个请求，没有鉴权、缓存、路由等收益，会增加调用和排障环节；不要为了边缘而边缘。

固定重定向、响应头、缓存规则等先看 Rules；少量代码且无绑定需求时，再看现有网站套餐是否包含 Snippets。Snippets 在 Pro / Business / Enterprise 上不额外按调用收费，但网站套餐本身不是免费。[29]

8.6 最小决策清单

  1. 功能：验证 SDK / ORM / 框架、并发和生产环境；Node.js 兼容不等于完整服务器兼容。[28]
  2. 性能：从用户所在地测 P50 / P95 / P99、错误率、缓存冷 / 热和数据库往返，不只测首页或一个 PoP。
  3. 成本：分别列请求、CPU、数据库、DO、日志、存储、构建、外部 API 和模型费。
  4. 公平：相同可用性目标、缓存策略、数据和响应大小；单机与多区域高可用不能直接比。
  5. 回收期：一次性迁移成本 / 每月净节省；计入重写、数据迁移和回滚，运维人力单列。若净节省不为正，就不存在纯费用节省的回收期，但其他收益仍可能值得。

最终建议：新建轻量 Web / API 应用把 Workers 放入首选候选；已有复杂后端先迁入口；持续重计算、强本地资源依赖和数据库密集单地域应用默认从 VM / 容器开始，再按实测决定。
