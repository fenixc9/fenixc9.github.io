太抽象了

2026 年 11 月 5 日，Alpine Linux 发布了一则 OpenSSH 密码认证绕过公告。符合条件的机器上，攻击者只需知道一个用户名，就可能用一段很长的密码登录本来只允许密钥登录的账号。

一个星号引发的认证绕过

Alpine 默认使用 musl libc。未启用 PAM 的 sshd 会调用 crypt() 计算密码哈希，再和账号的密码字段比较。

问题出在错误值和账号字段发生了碰撞：musl 的 crypt() 在输入密码超过 256 字节时返回 * 表示错误。而一些没有设置密码的账号，密码字段恰好也是 *。在特定账号配置下，sshd 把这个错误值当成了匹配结果，接受了密码认证。

根据 Alpine 官方公告，可触发的密码长度为 257 到 1024 字节。这里计算的是字节，不一定等于字符数。攻击者还需要能够访问 SSH 端口，并知道目标用户名。

哪些机器受影响

以下条件同时满足时，机器可能受到影响：

  • 使用 Alpine 的 openssh-server，或使用 openssh-server-pam 且设置 UsePAM no。
  • PasswordAuthentication 为 yes。这是 OpenSSH 的默认值。
  • 存在密码字段为 * 的可登录账号，例如没有设置密码的密钥登录账号。
  • 至少有另一个本地账号使用 $5$ 或 $6$ 密码哈希。

默认的 PermitRootLogin prohibit-password 阻止使用密码直接登录 root。但如果受影响的普通账号能够免密提权，攻击者仍可能取得 root 权限。官方 tiny-cloud 镜像中的 alpine 用户就是需要关注的例子：它配置了免密 doas，当机器满足公告中的密码哈希条件后可能受到攻击。

没有运行 sshd 的容器不受这个 SSH 漏洞影响。使用 PAM 且 UsePAM yes，或者关闭密码认证的系统，也不满足上述触发条件。

更新并重启

Alpine 为 3.16 至 3.24 以及 edge 提供了修复包。稳定分支通过补丁回移修复，因此不能只根据上游版本号判断是否安全。以下版本信息以 2026 年 11 月 6 日查阅的官方公告为准：

Alpine 分支 已修复的 openssh 包版本
edge 10.6_p2-r0
3.24 10.3_p1-r2
3.23 10.2_p1-r1
3.22 10.0_p1-r11
3.21 9.9_p2-r1
3.20 9.7_p1-r6
3.19 9.6_p1-r3
3.18 9.3_p2-r4
3.17 9.1_p1-r7
3.16 9.0_p1-r6

官方建议更新软件包，然后重启 sshd：

apk upgrade -U -a
rc-service sshd restart

仅升级包不会替换正在运行的 sshd。较旧的 Alpine 分支虽然获得了此次修复包，仍应计划迁移到受支持的版本。

如果暂时无法升级，可以在 sshd 配置中设置 PasswordAuthentication no，检查配置后重启服务。操作前确认密钥登录可用，并保留当前会话。使用 sshd -t 检查语法，使用 sshd -T 检查生效配置；存在 Match 规则时，还需要针对相应连接条件检查。

排查历史登录

对于曾经暴露 SSH 端口的受影响机器，Alpine 建议检查 /var/log/messages 中无密码账号出现的 Accepted password for 记录。同时检查 doas 使用记录、新建用户、文件和 SSH 授权密钥。如果无法排除异常登录，应按机器可能已被入侵处理。

上游 OpenSSH 10.6p2 发布说明确认了这个影响使用 musl 且禁用 PAM 的 Linux 系统的认证绕过问题。
