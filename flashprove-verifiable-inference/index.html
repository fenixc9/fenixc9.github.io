FlashProve：用零知识证明验证大模型推理

模型 API 声称使用某个型号，用户却通常无法仅凭回答确认实际运行的权重。Anthropic 开源的 FlashProve 尝试解决这个问题：服务端对模型权重作密码学承诺，再为推理结果生成证明。用户无需获得权重，也能验证证明覆盖的计算。

FlashProve 需要服务端配合，不能拿来单方面检查任意中转站。它目前是研究原型。本文依据 2026 年 11 月 3 日查阅的官方资料整理，文中性能数据来自 Anthropic，尚未自行复现。

从承诺到验证

一次验证包含三个步骤：

  1. 承诺：模型提供方发布 commitment ID，绑定一组具体权重。权重本身保持隐藏。
  2. 证明：服务端针对输入和被检查的输出生成证明，声称承诺模型执行约定计算后得到了该输出。
  3. 验证：验证者用可信的 commitment ID、实际请求、输出和证明，在 CPU 上检查结果。

commitment ID 的来源决定验证的意义。假设中转站自行选择一个便宜模型，并发布它的 commitment ID，即使后续证明通过，也只能说明结果符合这组权重。要验证它是否提供了官方承诺的模型，用户需要从可信渠道获得官方权重对应的 ID。

验证者还要确认请求和输出与证明绑定，并检查证明的覆盖范围。只检查部分 token，无法推断整段回答都经过验证。证明通过也不能说明回答正确、安全，或中转站没有记录请求。

零知识证明提供什么保证

FlashProve 使用 zkSNARK。模型提供方可以证明指定计算的结果，同时隐藏权重与中间计算信息。验证者不需要重新运行整个模型。当前方案不隐藏模型架构。

系统针对混合专家模型（MoE）做了优化。MoE 模型每次只激活一部分专家。FlashProve 的证明工作主要随实际激活的专家变化，而不是按所有专家的计算量增长。

项目使用 Lean 描述协议，并证明完整性、可靠性和零知识性质。这些结论依赖形式化的安全假设。形式化陈述也需要审阅，以确认它表达了预期的安全目标。

Anthropic 明确指出，快速 C++ 实现、论文和 Lean 协议之间的一致性没有形式化保证。仓库还提供一个较慢的 Lean 验证器。因此，协议有形式化证明，不等于所有实际运行代码都已得到同等保证。

官方实验的性能口径

Anthropic 在 Llama 4 Maverick 的 4-bit 权重上测试了该系统。模型总参数约 400B，每个 token 激活约 17B 参数。

指标 官方报告的条件与结果
证明端 单张 H100、24 个 CPU 核；24 个请求批量处理时约 110 token/秒
覆盖范围 每个请求为 1,024 token 窗口；每份证明检查一个输出 token
证明大小 每份约 18.78 MB
验证时间 CPU 上约 17 秒（24 线程）或 21 秒（单线程），包含离线检查
GPU 时间 官方对照中约为 vLLM 推理的 70–95 倍

110 token/秒是上述批处理和 prefill 测试条件下的证明吞吐量。它不能直接表示完整聊天回复的实时逐 token 验证速度。数字也不能直接推广到其他模型、硬件和负载。

官方称，离线承诺约需 39 分钟。一次承诺约可用于 1,600 万次请求，之后需要重新承诺。完整回复的证明成本需要结合实际生成长度和覆盖要求评估。

当前能否用来检查中转站

要用 FlashProve 验证中转服务，至少需要服务方提供符合协议的证明。验证者还需要可信的权重承诺，以及与实际请求、输出对应的验证材料。现有 API 如果不提供这些材料，用户就不能只凭地址和 API Key 使用 FlashProve 完成验证。

当前原型还有以下限制：

  • 证明针对整数模型和贪心解码。浮点推理或随机采样可能产生不同 token，不能直接当成相同计算。
  • 官方展示使用 Llama 4 Maverick。本文查阅的材料没有确认线上 Claude API 已部署 FlashProve。
  • 仓库自带的示例使用合成权重。示例验证通过只说明该验证流程能运行，不能证明某个线上服务使用了指定模型。
  • 仓库明确标记为研究成果，不维护，也不接受贡献。

常规推理中的确定性也有独立问题。即使使用贪心解码，浮点运算顺序和执行路径的差异仍可能改变得分接近的候选 token。FlashProve 当前证明的整数计算范围应与这些常规浮点推理行为区分。

Anthropic 还介绍过一个独立的推理验证原型：对流量签名，再在可信服务器上重新计算。FlashProve 采用密码学证明，是另一条技术路线。
