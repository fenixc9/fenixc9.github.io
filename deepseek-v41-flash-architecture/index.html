DeepSeek-V4.1-Flash 架构解析：CED、CSA2 与长上下文推理

DeepSeek-V4.1-Flash 面向长上下文和输入密集型任务，重新设计了历史信息的计算、缓存与读取方式。它将 40 层语言主干分为 20 层因果编码器和 20 层解码器，并结合跨层 KV 共享、稀疏索引和有限窗口重放，降低长输入的处理与缓存成本。

本文整理官方技术报告、模型配置和参考实现中的关键设计。性能数字采用官方口径，不代表独立复测结果。

模型概览

项目 DeepSeek-V4.1-Flash
主干参数 552B，另有约 196B Engram 条件记忆参数
主干结构 40 层：20 层因果编码器 + 20 层解码器
激活参数 官方口径：prefill 约 8B/token，decode 约 16B/token
MoE 每层 384 个路由专家和 1 个共享专家；每 token 选择 6 个路由专家
上下文 最多 1,048,576 token
输入输出 原生文本和图像输入，文本输出
全局 KV 官方口径约 890 bytes/token，约为 V4 Flash 的 1/4

来源：官方模型卡、技术报告。激活参数反映每次计算使用的参数规模，并不等于运行模型所需的权重内存。

为什么要改变 Prefill

自回归模型处理请求时，prefill 负责处理输入并建立历史状态；decode 则逐步生成输出。对常见的 decoder-only 架构，每个历史 token 通常都要经过完整层堆栈，才能生成后续各层需要的历史 KV。即使只需要 prompt 最后一个位置的预测结果，也不能因此跳过前面位置的深层计算。

长文档、代码和工具输出会增加 prefill 的计算量，也会增加 KV 缓存的容量和数据传输成本。V4.1 的 Causal Encoder-Decoder（CED）改变了解码器全局 KV 的来源，让长输入的大部分位置可以跳过解码器的完整计算。

CED：把全局 KV 的来源前移

CED 的前 20 层是因果编码器，后 20 层是解码器。因果编码器的位置只读取当前和更早的 token，适合自回归序列的增量处理。解码器的全局 KV 来自编码器最终隐藏状态的投影，而不是分别依赖每个解码层的历史隐藏状态。

解码器并没有放弃逐层计算：每层仍用自己的隐藏状态生成 Query 和局部滑动窗口注意力（SWA）所需的 KV，也有自己的输出投影和 MoE。共享全局 KV 不等于共享每层的全部计算。

报告给出的一般 CED 形式使用带层下标的投影，但具体 Flash 配置还结合了 CSA2：解码器第一层建立共享全局 KV，后续层复用这份缓存。因此，不能把一般公式理解为 Flash 的 20 个解码层各自保存一套全局 KV。

长输入如何执行

在报告描述的优化路径中，长 prompt 的处理过程可以概括为：

  1. 全部输入经过前 20 层编码器。
  2. 从编码器输出构建解码器需要的全局 KV。
  3. 取末尾最多 128 个位置，通过后 20 层恢复解码器局部窗口状态。
  4. 用最后位置的输出产生 logits，采样第一个生成 token。
  5. 后续每个生成 token 仍经过全部 40 层，并更新相关缓存。

用 token 经过的层数粗略估算，设输入长度为 NNN：

C普通≈40N,CCED≈20N+20min⁡(N,128)C_{\text{普通}} \approx 40N, \qquad C_{\text{CED}} \approx 20N + 20\min(N,128)C普通​≈40N,CCED​≈20N+20min(N,128)

当输入远长于窗口时，这个简化模型中的工作量接近一半。但它没有计入各层成本差异、KV 投影、索引、通信和调度，不能直接预测 FLOPs 或实际延迟。对于短输入，或者前缀缓存命中后只新增少量 token 的请求，窗口重放的相对开销可能明显。

CED 受到 YOCO 的启发。它不同于典型的双向源编码器加目标解码器结构：V4.1 使用统一的自回归序列，生成新 token 时仍会运行前后两部分。

SWA Bounded Replay：用近似恢复局部状态

全局 KV 可以从编码器输出建立，但解码器每层的 SWA KV 仍依赖该层的历史状态。多层滑窗的依赖会逐层向前扩展，因此精确恢复深层状态所需的历史范围可能远大于单个 128-token 窗口。

Bounded Replay 将重放限制在最近的窗口。重放片段开头的位置看不到窗口之前原本可见的局部状态，得到的结果因此是近似值。全局 KV 仍可读取因果可见的历史，但这不能证明局部状态完全相同。官方报告称实验中质量影响很小，并在后训练中模拟这一过程；这不是对任意输入的等价性证明。

报告区分两种用途：

  • Decoder SWA Bounded Replay：在优化的 prefill 路径中重放末尾窗口，恢复后续 decode 所需的解码器局部状态。
  • Encoder SWA Bounded Replay：全局前缀 KV 命中但编码器局部状态丢失时，重放前缀末尾的窗口，再处理新增后缀。

这种设计允许持久缓存优先保存全局 KV，而局部状态可以短期保留或在缺失时重建。不同的缓存命中和恢复路径可能产生不同的近似状态；做质量回归时，应固定缓存路径或将其作为比较条件。

CSA2：跨层共享缓存和索引

Compressed Sparse Attention 2（CSA2）沿层维度共享全局 KV，同时允许不同层复用或重新选择稀疏注意力位置。每层静态选择一种模式：

模式 全局 KV 与索引键 Top-K 选择
Full 创建 重新计算
Reindex 复用已有缓存 使用本层索引查询重新选择
Reuse 复用已有缓存 复用已有选择结果

无论哪种模式，本层仍计算主注意力 Query 和局部 SWA KV。缓存共享和索引结果共享是两个不同决策。

按配置文件的 0-based 层号，编码器第 0、1 层只使用 SWA；第 2–19 层分为三组，每组一个 Full 层和五个 Reuse 层，序列压缩率为 2。解码器第 20 层为 Full，随后按组使用 Reindex 和 Reuse，序列压缩率为 1。主干的全局 KV 来源层为 2、8、14、20。具体配置见官方 config.json。

解码器还使用分层稀疏索引：第一层 Full 从因果可见的全局范围构造候选池，后续 Reindex 层在最多 16,384 个候选位置中选择 Top-512。这样可以限制后续索引层的搜索范围，但第一层仍需扫描可见的全局范围，不能说整个索引过程都与上下文长度无关。

KV 精度和存储层级

V4.1 的主 KV 使用 FP4：E2M1 数据格式，每 16 个通道对应一个 E4M3 scale。局部 SWA KV 使用 FP8。官方通过量化感知训练适配主 KV 的低精度表示。

官方给出的全局 KV 成本约为 890 bytes/token。按 1,048,576 token 直接相乘，约为 0.87 GiB。这只是该口径的全局 KV 数据量，不包括模型权重、局部状态、临时激活、并发请求、内存分配开销或并行复制。

另一个数字是持久化 KV 约为 V4 Flash 的 1/8。它还包含通过 bounded replay 减少 SWA 持久化的贡献，与全局 KV 的 1/4 不是同一个统计口径。两项结果也不能单独归因于 CED：跨层共享、压缩、精度和缓存策略共同影响最终大小。

Engram、残差流与多模态

Engram 提供约 196B 参数的条件记忆。它根据 token 的 2、3、4-gram 确定查表位置，再通过上下文相关门控将读取结果融入网络。两个模块位于第 1、14 层，按 0-based 编号。稀疏查表减少每次访问的数据量，但表本身仍需存储。官方部署方案利用确定性寻址，通过后台 RDMA 从主机内存预取。

Single-Pass mHC 调整残差流混合的数据依赖，让融合 kernel 可以减少激活读写。报告还介绍了 Mega-mHC kernel。实际收益依赖实现和硬件，不能仅凭结构推断特定机器上的加速比。

视觉输入由 DeepSeek-ViT 和投影层转换为视觉 embedding，再与文本 embedding 一起进入语言模型。模型支持图像和文本输入、文本输出；这些能力不意味着它支持语音输入或图像生成。

模型还包含 DSpark 投机解码相关组件。草稿生成和验证需要推理引擎支持；模型包含组件不意味着任意部署都启用了完整的投机解码路径。

从架构到部署，还差什么

官方公开的 minimal inference 适合阅读模型结构。2026 年 9 月对参考代码的检查显示，它实现了缓存共享，但 Transformer.forward() 对传入序列遍历全部主干层；生成循环没有单独接入报告中的 bounded-replay prefill 调度。该观察针对当时的代码版本，不能推断后续实现状态，也不能用参考实现的速度代表报告中的优化系统。

生产引擎若要兑现 CED 的 prefill 收益，需要处理编码器提前结束、解码器全局 KV 构建、窗口重放的绝对位置和因果掩码，以及前缀命中时的状态恢复。这些都需要结合具体引擎验证。

容量也必须单独核算。2026 年 9 月核对的官方 48 个权重分片合计约 510.3 GB，已经包含混合精度存储。两台各标称 128 GB 统一内存的 DGX Spark 无法把官方原版权重完整常驻；缩短上下文或将 Engram 移到同机 CPU 侧，都不会增加统一内存总量。更激进量化和外部存储属于可能的实验路线，需要重新验证质量、内核和性能。

总结

V4.1-Flash 将长上下文优化拆成几个相互配合的问题：CED 减少长输入的深层计算；CSA2 共享全局缓存和稀疏索引；FP4 降低主 KV 存储；bounded replay 减少局部状态持久化。Engram 则通过稀疏查表提供额外记忆容量。

这些设计也带来明确边界：decode 仍运行完整主干，有限重放是近似恢复，激活参数不等于权重容量，参考实现也不必然包含所有生产优化。评估具体部署时，仍需按模型版本、引擎、硬件、上下文长度和实际负载测量。
