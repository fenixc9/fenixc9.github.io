多 Agent 体系架构：从子任务委派到 Agent Teams

多 Agent 系统要回答几个具体问题：谁拆任务？谁决定下一步？每个 Agent 能看到什么？成员如何交换发现？多个成员修改同一份资源时，系统如何处理冲突？

主流实现提供了子任务委派、工作流、交接、并行汇总、团队协作和群聊等机制。它们可以组合。理解这些机制时，需要同时看模型的决策接口与程序的执行规则。

本文先建立一个架构视角，再比较主流产品，最后用 DeepSeek Harness（DSH）解释 Agent Teams 如何通过工具调用工作。

资料核对日期：2026 年 10 月 27 日。本文依据官方文档和官方仓库整理，未进行跨产品性能实测。产品限制以核对时的文档为准。文中的分层、示例协议和选型建议属于工程归纳，不代表所有框架采用相同实现。

一个 Agent 执行循环如何变成多个

单个 Agent 通常运行在一个循环中：程序组装上下文，模型返回文本或工具调用，程序执行工具，再将结果提供给模型。程序根据结束条件决定是否继续。

多 Agent 在这个基础上增加了多个执行循环。每个循环可以有自己的上下文、工具集合和生命周期。协调者通过工具、消息或工作流启动这些循环，收集它们的产物。

为了分析实现，可以把系统分成四层：

层次 主要责任 典型内容
决策层 决定拆分、委派、交接和收敛 模型、路由规则、工作流节点
协作接口层 表达成员可以执行的协作动作 创建成员、发消息、更新任务、等待
运行时层 执行动作并维护状态 会话、调度、收件箱、任务板、持久化
资源层 提供实际工作环境 文件、Git 分支、终端、浏览器、外部服务

这四层可以部署在同一进程。它们也可以跨进程、机器或服务部署。多 Agent 描述的是多个执行者之间的协作关系，本身不保证进程隔离或分布式执行。

控制权决定协作模式

主 Agent 委派：做完之后把结果交回来

主 Agent 保留对话控制权。它调用子 Agent 完成边界明确的工作，再决定如何使用结果。

用户 → 主 Agent
          ├─ 子 Agent A：分析调用链 ─┐
          ├─ 子 Agent B：检查测试   ─┤→ 主 Agent 汇总 → 用户
          └─ 子 Agent C：调查日志   ─┘

这种模式适合代码探索、文档研究和局部实现。子 Agent 返回摘要，可以减少中间日志进入主上下文的数量。主 Agent 仍需判断子任务是否覆盖目标，以及各个结论是否冲突。

OpenAI Agents SDK 将这类组合称为 agents as tools。专家作为工具被调用。主 Agent 继续负责最终答复。OpenAI 编排文档

交接：下一步由另一位 Agent 接管

Handoff 转移当前流程的控制权。例如，分流 Agent 识别退款问题后，将处理交给退款 Agent。

用户 → 分流 Agent → 退款 Agent → 用户

委派和交接的区别在于返回路径。委派完成后，主 Agent 读取结果并继续处理。交接后，接收者成为当前流程的执行者。

上下文传递需要单独配置。交接可以传完整历史，也可以过滤历史。不能仅凭发生了 handoff，就推断接收者看到全部信息。OpenAI Handoffs 文档

工作流：由程序约束执行顺序

当业务步骤较稳定时，可以用代码或状态图定义顺序、分支和循环。

解析请求 → 检索资料 → 生成草稿 → 校验
                                  ├─ 通过 → 输出
                                  └─ 未通过 → 修订 → 再校验

节点内部可以运行 Agent。节点之间的关系由程序控制。外层流程因此可以明确规定重试次数、人工介入位置和失败分支。

LangGraph 可承载自定义工作流。Google ADK 同时提供图工作流、动态协调和顺序、循环、并行模板。CrewAI 的 Process 则提供 sequential 和 hierarchical 两类任务组织方式。LangChain 多 Agent 文档、ADK 工作流、CrewAI Processes

工作流可以混合固定规则与模型决策。例如，程序要求检索结束后才能写报告，模型负责决定检索哪些资料。

并行分发与汇总：先独立工作，再合并产物

Fan-out / fan-in 描述的是执行结构。系统将工作分发给多个执行者，再收集结果。

它可以采用两种常见拆法：

  • 按问题拆分：分别研究价格、架构和兼容性。
  • 按方案拆分：针对同一个问题，独立提出多个实现方案。

第一种拆法改善覆盖范围。第二种拆法增加候选方案。汇总者需要保留分歧及其依据，不能仅按赞成人数决定正确性。同一个模型、相似上下文和相同资料可能产生相关错误。

主从结构、工作流和团队协作都可以使用并行分发。它与控制权安排是两个维度。

Agent Teams：成员持续存在，通过消息和任务协调

团队模式通常增加具名成员、成员间通信和共享任务状态。负责人可以追加工作。成员可以在后续轮次继续执行。

       Lead
     /      \
成员 A ←消息→ 成员 B
     \      /
    共享任务板

Claude Code Agent Teams 的官方结构包含 team lead、teammates、task list 和 mailbox。成员有独立上下文，可以直接通信。有 Task 工具时，成员还能领取共享任务。该功能在核对时仍为实验性，默认关闭。Claude Code Agent Teams

团队模式适合需要交换中间发现的任务。例如，后端成员先明确接口约定，前端成员再按约定完成页面。负责人需要持续处理依赖、冲突和验收。

群聊与评审循环：决定下一位发言者

群聊模式围绕消息序列组织协作。AutoGen 的 Selector Group Chat 由模型根据共享上下文选择下一位发言者。参与者轮流广播消息。AutoGen Selector Group Chat

轮流发言本身是串行结构。它可以帮助角色交换观点，不能自动带来并行加速。

生成者—评审者循环也是一种常用组合。生成者提交产物，评审者给出问题，生成者修订。实现时需要最大轮数和可检查的结束条件，否则双方可能持续改写，却没有增加有效信息。

Agent Teams 如何成为模型可以调用的能力

模型驱动的团队协作通常通过工具接口实现。运行时提供工具定义和协作说明。模型据此请求创建成员、发消息或更新任务。运行时校验请求，再执行具体操作。

运行时提供工具定义、角色与约束
              ↓
主 Agent 模型请求创建成员
              ↓
运行时检查权限、并发和配置
              ↓
创建子会话并执行成员任务
              ↓
工具结果、成员消息或状态进入上下文
              ↓
主 Agent 模型决定下一步

这里有三个不同的决定：

  1. 用户和配置决定是否允许使用团队能力。
  2. 模型或工作流决定何时请求协作。
  3. 运行时决定请求是否有效，以及如何执行。

因此，工具出现在模型面前，不代表模型拥有无限创建权限。并发上限、工具权限和启动条件可以由程序强制执行。成员收到“不要修改其他目录”的指令，也不等于运行时已经实现目录隔离。

工具结果还需要区分生命周期。创建成功只说明成员已建立。消息发送成功也不一定说明对方已经处理。协调者必须读取任务状态或等待成员结果，才能判断工作完成。

DSH 的官方 Agent Teams 实现

DeepSeek Harness 的官方仓库提供实验性 Agent Teams。当前组合包默认关闭，可在插件页面启用。官方组合包说明

它将实现拆为三部分：

包 责任
dsh-experimental-agent-team-profile 组合启用团队能力、工具和 Web UI
dsh-experimental-tool-agent-team 提供模型可调用的工具和协作说明
dsh-experimental-agent-team 维护团队成员、消息与持久化任务板

工具层提供九个工具：

能力 工具
创建成员 spawn_teammate
发消息 send_message
查看与等待 list_agents、wait_agent
打断成员 interrupt_agent
管理任务板 team_task_create、team_task_list、team_task_get、team_task_update

Lead 和成员获得同一组工具与协作说明。角色约束仍然有效：只有 Lead 可以创建或打断成员。成员可以直接互发消息。官方工具层文档

团队层复用可继续执行的子 Agent。创建时可以选择 fresh 上下文，也可以 fork Lead 已完成的历史。持久化存储支持后续唤醒成员。

这套实现采用单进程和共享工作目录。它不提供 worktree、代码合并或文件系统锁。成员停止执行，也不会自动释放任务所有权。任务板状态和代码资源的并发控制需要分别处理。官方团队层文档

主流实现放在同一张架构表中

产品可能同时支持多种结构。下表列出本次资料中与协作相关的主要入口，不按成熟度排名。

产品或框架 协作入口 架构上应重点检查什么
Claude Code Subagents、Agent Teams 子任务返回与团队通信的区别
Codex 子 Agent 工作流 主线程如何收集结果和发送后续指令
Cursor 子 Agent、隔离项目副本 默认共享 checkout 与主动隔离的区别
OpenAI Agents SDK Agents as tools、Handoffs 当前对话由谁负责
LangChain / LangGraph 子 Agent、路由、交接、自定义工作流 上下文和状态如何沿流程传递
Google ADK 协作工作流、图工作流、模板 动态决策与固定结构的组合边界
AutoGen 群聊、发言者选择、交接 发言顺序、消息可见性和终止规则
CrewAI 顺序任务、manager 管理 任务输入、分配和验收责任
DSH 官方实验性 Agent Teams 工具调用与持久化团队状态的关系

Codex 官方文档强调将探索、测试和日志分析分配给独立子 Agent，再向主线程返回摘要。当前本地客户端的委派也受用户请求和项目指令约束。Codex Subagents

Cursor 子 Agent 默认共享父 Agent 的 checkout。需要隔离时，可以使用独立 Git worktree 或云环境。各成员的修改保留在自己的分支，之后再由父 Agent 合并。Cursor Subagents

这些差异说明，比较工具时，应该分别检查通信、持久化和资源隔离。一个产品显示了多个成员面板，不能据此确认它具备全部团队机制。

决定实际效果的五个工程问题

1. 给成员什么上下文

主流做法包括从空白上下文启动、复制部分历史、传入摘要，以及按需检索共享资料。选择取决于任务对历史信息的依赖程度。

复制历史减少了重新说明的工作，也可能带入无关日志和过时假设。只传一句任务描述成本较低，却容易遗漏约束。实践中可以先定义一个明确的任务输入：

# 架构示例，不对应某个产品的配置格式
task_id: review-cache-invalidation
goal: 检查缓存失效逻辑是否存在并发错误
inputs:
  - 指定提交的差异
  - 当前缓存一致性约定
write_scope: []
deliverables:
  - 问题位置与触发条件
  - 支持结论的代码或测试证据
  - 未能确认的事项

子 Agent 的结果也需要包含证据位置。只有结论的摘要很难被主 Agent 复查。LangChain 将每个 Agent 应该看到哪些信息视为多 Agent 设计的核心问题。上下文设计说明

2. 消息到底表示什么

成员发来的消息可能是进度、问题、结果，也可能是继续工作的请求。运行时需要规定每类消息如何影响执行。

例如，某成员正在执行工具时，消息是立即注入、在步骤边界注入，还是排队到下一轮？成员已退出时，消息是否会唤醒它？发送失败后，调用方是否需要重试？

持久化的任务板不能自动提供可靠消息投递。设计中应分别定义消息入队、处理确认、重复投递和恢复语义。需要可靠执行时，可以记录消息 ID 和处理状态。外部副作用还需要幂等处理。

3. 任务状态和成员状态如何区分

一个 Agent 空闲，可能表示它已完成，也可能表示它在等待依赖。一个 Agent 被打断，也不能说明任务已经失败或可以重新领取。

下面是一种可选的任务状态设计：

pending → ready → running → submitted → verified
                      ├─ failed
                      └─ blocked → ready

submitted 表示成员提交了产物。verified 表示验收条件已满足。这两个状态可以防止成员自报完成后，系统直接宣告整体成功。

如果需要成员自动领取任务，运行时还应实现原子领取。租约与超时回收可以处理成员失联，但必须避免仍在工作的成员与接管者同时写入。具体是否支持这些机制，需要逐个核对框架，不能从“有任务板”推断。

4. 共享目录还是隔离工作区

共享目录让成员立即看到对方的修改。它也允许多个编辑器、终端和格式化工具同时修改同一文件。

独立 worktree 将文件修改放到不同工作目录。它减少直接覆盖，却增加了集成工作。多个成员仍可能分别修改同一接口，直到合并和测试时才暴露不兼容。

对于写代码的任务，可以按以下顺序组织：

  1. 先明确共享接口和验收标准。
  2. 按模块或文件划分修改范围。
  3. 需要并行写入时，为成员准备独立工作区。
  4. 由明确的集成者合并修改。
  5. 在合并结果上运行测试。

任务领取锁只保护任务记录。它不会自动锁住源文件、数据库或部署环境。

5. 谁确认完成，何时停止

评审 Agent 可以发现遗漏。它也可能重复执行者的错误。最终验收应尽量使用可检查的证据，例如测试结果、构建产物、复现步骤或已核对的来源。

系统还需要明确停止条件：必要任务是否完成？依赖是否解除？结果之间是否冲突？是否有成员仍在执行？预算耗尽后输出的是完整结果还是部分结果？

运行轨迹应记录父任务、成员会话、工具调用、消息和最终产物。否则，失败发生后很难确认哪个决策导致了错误。

多 Agent 的成本和加速边界

并行可以缩短独立工作的等待时间。它仍需要拆分和集成。

总耗时 ≈ 任务拆分时间
       + 最长依赖路径上的执行时间
       + 协调、合并与验收时间

这个表达式只用于解释结构，不是性能预测公式。模型服务并发、工具限流和环境资源都会影响实际耗时。

总 token 则包含主 Agent、所有成员、重复上下文和重试。对小任务，多 Agent 的启动和汇总可能超过执行本身的成本。对共享状态变化频繁的任务，协调也可能抵消并行收益。

评估时应固定任务集与验收标准，比较完成率、耗时、总成本、返工次数和人工介入次数。仅看创建了多少成员，无法判断架构是否有效。

如何选择起点

工作特征 建议起点 需要先确定的约束
单次、短小、上下文足够 单 Agent 工具和完成条件
多个独立调查方向 主 Agent＋并行子 Agent 问题边界与结果格式
明确的专家接管 路由＋Handoff 控制权与历史过滤
步骤稳定、需要恢复 图工作流＋局部 Agent 状态、失败分支与检查点
成员需要持续交换发现 Agent Teams 消息、依赖和验收责任
并行修改多个模块 委派或团队＋独立工作区 接口契约与集成者
需要质疑和修订方案 生成者—评审者循环 证据标准与最大轮数

对于开发和调研，可以先从只读并行开始。让成员调查不同模块，由主 Agent 汇总证据。确认收益后，再加入并行实现、共享任务板和持久化成员。

多 Agent 架构的设计重点是明确控制权、信息边界和状态语义。模型可以通过工具请求协作。运行时负责让这些请求形成可执行、可恢复、可验收的工作过程。
