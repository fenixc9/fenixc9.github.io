没有 unsafe，也能访问失效内存？读懂 Rust 的一次生命周期漏洞

Rust 的一个重要承诺是：在正确实现的编译器和底层库支持下，安全代码不应该访问已经失效的内存。但 2026 年 10 月 13 日提交的 issue #164250 展示了一个漏洞：程序没有写任何 unsafe，却能把局部变量的引用保存到全局，等变量销毁后继续读取。

问题出在编译器漏掉了生命周期约束检查。理解它不需要先钻进编译器源码，只要抓住三个概念：引用、'static 和析构函数。

本文依据截至 2026-10-14 查阅到的 issue 和修复 PR 整理。文中的运行结果来自报告者，未在本地独立复现；修复进展也是该日期的快照。

引用像一张地址纸条，纸条还在不代表东西还在

假设你把一件物品放在临时储物柜里，再把柜子的地址写在纸条上。纸条可以保存很久，但储物柜一旦清空，纸条就不能再证明原来的物品还在那里。

程序中的引用也有类似的问题：

let text = String::from("hello");
let borrowed = &text;

text 拥有字符串，borrowed 只是借用它。复制引用不会让原来的字符串多活一会儿。 一旦 text 销毁，引用就不能继续用于访问它。

Rust 的生命周期检查要保证：所有使用引用的地方，都发生在它指向的数据仍然有效的时候。正常情况下，试图让引用逃出局部变量的有效范围，编译器就会拒绝。

'static 是约束，不是给变量续命

漏洞中的结构体可以先简化为：

struct Q<T: 'static>(Option<T>);

Option<T> 表示里面可以有一个 T，也可以没有。T: 'static 则对允许放进去的类型提出要求。

这里最容易误解的是：'static 并不意味着所有值都必须活到程序结束。一个拥有自己数据的 String 可以满足 T: 'static，但它仍然可以正常销毁。

如果 T 是引用，情况就不同了：它不能借用一个只在局部范围内有效的对象。 因而，本例里的 &text 不能作为满足 'static 要求的引用放进 Q。

这个约束也不会把局部变量变成全局变量，更不会延长它的实际寿命。

编译器放过了哪一步

issue 中的关键步骤非常短：

let text = String::from("hello");
let mut value = Q(None);
value.0 = Some(&text); // 本应因生命周期不满足而被拒绝

.0 是访问元组结构体的第一个字段。先创建一个空的 Q，再给它的字段赋值，这条路径竟然能绕过结构体的生命周期要求。

正常检查应当同时确认两件事：字段装进去的值能否匹配，以及包含这个字段的类型是否仍满足声明的约束。本例通过了前面的匹配，却漏掉了后面的要求。

标题里的“协变字段赋值”与生命周期转换有关：一个能长期使用的引用，通常也可以交给只在较短时间内使用它的代码。这样的转换本身合理，但转换之后，其他类型约束仍然必须成立。本漏洞的问题就是这条边界没有守住。

这并不表示 Rust 正常允许短命引用变成长命引用。这是编译器错误接受了本应非法的程序。

真正让引用逃出去的是 Drop

只把引用放进 Q，还不足以解释后续的失效内存访问。关键在于 Q 的析构函数。

Rust 的 Drop 用来在值销毁时执行清理代码。它可以关闭资源，也可以执行其他逻辑。原帖里的实现选择把字段中的值移到一个全局容器里。

下面是原帖的完整复现，增加了少量注释：

use std::sync::Mutex;

// 保存到这里的值可以在局部作用域结束后继续取出。
static KEPT: Mutex<Vec<Box<dyn std::any::Any + Send>>> =
    Mutex::new(Vec::new());

struct Q<T: 'static + Send>(Option<T>);

impl<T: 'static + Send> Drop for Q<T> {
    fn drop(&mut self) {
        if let Some(t) = self.0.take() {
            KEPT.lock().unwrap().push(Box::new(t));
        }
    }
}

fn main() {
    {
        let l = String::from("hello world, this is long enough");
        let mut q = Q(None);
        q.0 = Some(&l); // 漏洞：接受了不满足 'static 的引用。
    }

    let _z = String::from("XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX");
    let k = KEPT.lock().unwrap();
    println!("{}", k[0].downcast_ref::<&'static String>().unwrap());
}

暂时不用研究 Mutex、Box 和 Any 的每个细节。它们在这里承担的作用是：提供一个可以保存不同类型值、之后再取出的全局容器。它们没有为局部字符串延长寿命。

代码发生的顺序是：

  1. 创建局部字符串 l，再创建 q。
  2. 编译器错误地允许把 &l 放入 q。
  3. 离开内部作用域时，q 先析构。它的 Drop 依据 T: 'static 的承诺，把引用放进全局容器。
  4. 接着 l 销毁，字符串占用的资源被释放，原引用失效。
  5. 后续代码从全局容器取出引用，仍把它当作有效引用读取。

问题不是 Drop 太晚执行。它执行时 l 还在。问题是它保存了一份能在 l 销毁后被再次使用的引用。

从析构函数的视角看，使用 T: 'static 是有依据的，因为结构体和实现都写了这个约束。漏洞发生在调用侧：编译器让一个不符合承诺的值进入了这个类型。

为什么读出了后来的字符串

作者报告，这段程序读出了后面创建的字符串中的 XXXX…；启用 AddressSanitizer 后，则报告 stack-use-after-scope，即访问了作用域结束后已失效的栈上对象。见 原帖复现与结果。

可以把它理解为：地址纸条仍指向原来的位置，但那个位置已经不再属于原来的对象，甚至可能被后来的对象复用。

这里还有一个细节：&l 指向的是 String 对象本身，String 再管理堆上的字符串数据。因此，既不能因为字符串数据在堆上就忽略局部对象的寿命，也不能因为输出看起来正常就认为引用有效。

发生未定义行为后，输出没有保证。 读出 XXXX… 是报告者观察到的一种表现；其他环境中可能输出不同内容，也可能崩溃。

没有 unsafe，为什么依然会出问题

safe Rust 的安全性依赖编译器正确执行类型和生命周期规则，也依赖底层库正确实现内部的 unsafe。程序没有显式 unsafe，并不能抵消编译器自身的错误。

官方给这个 issue 标了 I-unsound。这里的“unsound”可以理解为：规则本来应该阻止危险行为，但实现让一个危险程序通过了检查。

这个例子的重要性在于，它给出了具体反例，证明安全检查存在缺口。它并不能说明所有 Rust 程序都有同样的问题；但对这一条路径，原本应有的保证确实失效了。

社区怎么修：补查整个类型的约束

社区已提交 PR #164277，标题是 require MIR local types to be well-formed。

MIR 是编译器处理程序时使用的一种中间表示。Well-Formed 可以直观理解为“这个类型是否满足它自己声明的要求”。候选补丁在借用检查阶段，对 MIR 中被分类为 LocalKind::Temp 的局部声明增加这项检查。

这样，检查器看到 Q<T> 时，就不能只接受字段的类型匹配，还必须证明 T 满足 'static 等约束。对于局部变量的引用，这个证明应当失败。

补丁中的回归测试预期原来的赋值报错：

error[E0597]: `text` does not live long enough
assignment requires that `text` is borrowed for `'static`

也就是：text 活得不够久，而这次赋值要求借用满足 'static。

测试覆盖了自动析构和显式调用 drop，并分别配置当前与下一代 trait solver。这里说的是 PR 的代码与测试预期，不代表本文已经独立构建编译器或验证全部 CI。

截至 2026-10-14 查阅时，PR 尚未合并，已经转交 Types Team，由 lcnr 接手。评审者还提出一个范围问题：类型转换和用户显式类型标注，是否也应该补做 WF 检查？ 因此，最终补丁仍可能调整，不能据此认定某个已发布版本已经修复。

这个漏洞严重吗

从技术性质上看，它很严重：安全代码可以产生悬空引用，突破了 Rust 要提供的内存安全保证。

从日常程序的触发概率看，维护者给出了较谨慎的判断。讨论中的变体被报告能追溯到 Rust 1.4，也就是 2015 年；lcnr 在原帖补充说明中认为，漏洞存在约 11 年才被发现，实际造成内存不安全需要刻意构造的 Drop 实现，因此优先级从 P-critical 调整为 P-high。见 维护者说明。

这个判断表达的是修复优先级与实际风险评估，并没有否认漏洞，也不能作为某个具体项目一定不受影响的证明。

对于正在跟踪这个问题的开发者，最有价值的后续信息是：最终补丁是否合并、进入哪个 nightly，以及哪个正式版本包含修复。本文查阅时这些发布信息尚未确定。

这次漏洞也让生命周期的作用变得具体：引用只记录访问关系，不负责让数据存活；类型约束只有被编译器完整检查，才能成为其他代码可以依赖的承诺。
