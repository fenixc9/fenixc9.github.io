图解 Kubernetes 调度：从资源预算、队列重试到 Assume 与 Bind

一个 Pod 已经创建，节点的 CPU 使用率也很低，它为什么还停在 Pending？调度器选中了节点，为什么 API 中的 spec.nodeName 仍然为空？Bind 请求超时后，这个 Pod 到底有没有绑定成功？

这些问题分别落在资源预算、调度队列、本地预占和 API 持久化的边界上。把它们串起来，才能解释 Pod 为什么等待、什么时候重试，以及节点选择何时成为正式结果。

本文用五张图说明主要流程。实现细节以 Kubernetes v1.37.1 为基准。引用来自 2026 年 10 月已核验的官方文档和对应版本源码。文中的资源数字是说明性示例，没有进行集群压测。其他版本和自定义调度器需要核对各自实现。

1. 调度器负责把 Pod 分配给节点

用户向 kube-apiserver 创建 Pod。通过 Deployment 创建应用时，相关控制器会先创建 ReplicaSet 和 Pod。未绑定的 Pod 通常还没有 spec.nodeName。

kube-scheduler 观察这些 Pod，处理由自己的调度配置负责的对象。它读取节点、已有 Pod、卷等信息。它先筛选节点，再比较候选节点，最后提交绑定请求。

正式绑定完成后，目标节点的 kubelet 继续工作。它执行节点侧准入，协调卷、网络和容器创建。因此，选出节点、绑定成功、容器运行是三个不同的时点。

时点 主要执行者 能确认什么
节点选择完成 kube-scheduler 本轮调度找到了目标节点
绑定持久化完成 kube-apiserver / etcd Pod 的 spec.nodeName 已正式记录
容器启动 kubelet / 容器运行时 节点侧已经推进实际执行

调度器主要依据缓存进行计算。它不需要在每次过滤节点时重新请求 apiserver。普通单 Pod 路径中的调度周期按序推进，绑定周期可以并发执行。这个设计减少了远端写入对调度吞吐的影响。Scheduling Framework、v1.37.1 调度流程源码

2. request 决定调度预算，limit 约束运行时使用

先看一个容器资源配置片段：

resources:
  requests:
    cpu: "500m"
    memory: "256Mi"
  limits:
    cpu: "2"
    memory: "1Gi"

500m 表示 0.5 个 CPU。调度器会把有效 request 纳入资源适配计算。CPU request 也会影响运行时竞争时的 CPU 分配权重。

limit 描述运行时边界。在常见 Linux 容器中，kubelet 和容器运行时将相应配置落实到 cgroup。内核执行 CPU 节流和内存限制。内存分配触及边界且回收不足时，可能触发 OOM kill。

配置 对调度和运行的影响
CPU request 参与调度预算，通常还影响 CPU 竞争时的权重
内存 request 参与调度预算，也影响节点压力下的部分处理决策；不等于立即锁定物理内存
CPU limit 限制 CPU 时间使用，配额耗尽时通常节流
内存 limit 约束容器内存使用，回收失败时可能触发 OOM

为什么使用率低也放不下

假设节点的 Allocatable 是 4 核，已有 Pod 的 CPU requests 合计为 3 核。新 Pod 请求 2 核。

资源检查主要比较的是有效请求与可分配容量：

已有有效资源请求 + 新 Pod 的有效资源请求 ≤ Node Allocatable

节点的实际 CPU 使用量降到 0.1 核，也不会自动把原先的 3 核 request 改成 0.1 核。kubectl top 展示实时使用量，调度预算则来自资源请求及相关状态。

实际的 Pod 有效请求还需要考虑 init container、Pod overhead、原地资源调整和启用的功能。上面的加法只用于解释基本关系。

Node Allocatable 也不会随着每个 Pod 的绑定而被逐笔扣减。 scheduler 在本地维护节点上已经计入的请求，再与 Allocatable 比较。资源管理文档、NodeResourcesFit 源码

3. Filter 判断能否放置，Score 比较候选节点

一次调度由多个扩展点组成。插件可以实现其中一个或多个阶段。

阶段 要回答的问题
PreEnqueue Pod 是否具备进入活跃队列的条件？
QueueSort 多个等待的 Pod，先处理谁？
PreFilter 需要预先计算哪些共享数据？是否可以提前拒绝或缩小候选范围？
Filter 当前候选节点能否运行这个 Pod？
PostFilter 没有可行节点时，能否通过抢占等方式改善条件？
PreScore / Score 可行节点中，哪些更符合偏好？
Reserve 插件是否需要预留资源或状态？
Permit 能否继续绑定，还是需要等待？
PreBind 绑定前的依赖是否准备完成？
Bind / PostBind 提交绑定，执行绑定成功后的通知

Filter 处理硬条件。Score 表达偏好。评分插件可以先通过 NormalizeScore 处理自己的分数，再按配置权重参与汇总。高分无法抵消硬条件不满足。

例如，Pod 的硬亲和要求 disk=ssd。某个 HDD 节点即使 CPU 余量很大，也不能靠高资源分数重新变成候选节点。

调度器还会通过候选节点采样等机制控制计算成本。不能据概念流程断言每个 Pod 必然完整扫描、打分集群中的所有节点。

把常见插件放回具体阶段

插件 主要阶段 作用
SchedulingGates PreEnqueue gate 未解除时，暂缓进入活跃队列
PrioritySort QueueSort 默认按优先级与队列时间排序
NodeResourcesFit PreFilter、Filter、PreScore、Score 检查资源，并按资源分配策略评分
NodeAffinity PreFilter、Filter、PreScore、Score 实现 nodeSelector、节点硬亲和与软亲和
TaintToleration PreFilter、Filter、PreScore、Score 检查污点容忍，处理软性污点偏好
NodePorts PreFilter、Filter 检查 Pod 声明的 hostPort 冲突
PodTopologySpread PreFilter、Filter、PreScore、Score 控制拓扑域间的 Pod 分布
InterPodAffinity PreFilter、Filter、PreScore、Score 实现 Pod 亲和、反亲和
NodeResourcesBalancedAllocation PreScore、Score 偏好不同资源分配比例较均衡的节点
ImageLocality Score 考虑节点已有镜像，降低拉取成本
VolumeBinding PreFilter、Filter、PreScore、Score、Reserve、PreBind 协调 PVC/PV、节点选择和卷绑定；相关阶段受配置及适用条件影响
DefaultPreemption PreEnqueue、PostFilter 协调异步抢占，以及没有可行节点时的抢占尝试
DefaultBinder Bind 通过 API 提交 Pod 到节点的绑定

表格列出理解主流程需要的部分插件，省略组调度扩展点。Reserve 插件还需要实现 Unreserve，用于失败清理。

NodeResourcesFit 的节点评分支持 LeastAllocated、MostAllocated 和 RequestedToCapacityRatio。它们可以分别表达分散、装箱或自定义资源比例偏好。这里主要使用资源请求形成的分配比例，不能直接理解为实时负载均衡。

NodePorts 检查的是 Pod 的 hostPort。Service 的 nodePort 分配不属于这个插件的职责。VolumeBinding 负责协调卷绑定，实际挂载由节点侧组件完成。插件实现目录、默认插件配置

4. 三个队列决定什么时候再试

资源不足后，Pod 通常需要等待条件变化。调度器用不同的数据结构管理待执行、退避和暂时不可调度的对象。

队列 保存的对象 主要作用
activeQ 已准备好参与调度的 Pod 按 QueueSort 顺序提供下一次调度任务
backoffQ 值得重试、但需要限制重试频率的 Pod 管理指数退避
unschedulableQ 暂时无法调度的 Pod 等待相关事件或定时兜底

unschedulableQ 是习惯名称，实现上更接近不可调度对象集合。它不会持续取队头、无条件重复运行调度。

这张图突出资源不足后的典型路径。若相关事件在 Pod 正在调度时到达，调度器会记录事件以避免错过唤醒。失败后的 Pod 因此不一定先停留在 unschedulableQ。

什么事件可以唤醒资源不足的 Pod

NodeResourcesFit 注册资源相关事件。QueueingHint 回调进一步判断变化是否可能改善条件。

事件 可能产生的影响
已调度的其他 Pod 删除 释放计入节点的资源预算
新增节点 增加可选容量
节点 Allocatable 增加 增加可供 Pod 使用的资源
其他已调度 Pod 的有效请求降低 可能减少该节点已有资源请求
目标 Pod 自身请求降低 可能降低其放置门槛

请求降低涉及版本、API 支持和资源状态更新，不能假定所有集群都允许任意修改 Pending 或运行中 Pod 的资源字段。

事件发生后，Pod 仍需要通过相关入队检查。如果需要退避，它进入 backoffQ。如果退避已结束，它可以进入 activeQ。重新入队仅表示值得再试，其他硬条件可能仍然不满足。

新增节点也不一定唤醒所有 Pod。如果新节点连目标 Pod 自身的请求都容纳不了，QueueingHint 可以跳过这次重试。删除一个没有绑定、也没有提名节点的 Pending Pod，通常不会释放节点资源预算。

退避与兜底是两套机制

默认退避时长大致按 1s → 2s → 4s → 8s → 10s 增长，随后封顶。初始值和最大值可以配置。

v1.37.1 的等待区兜底逻辑约每 30 秒扫描一次。超过默认 5 分钟等待阈值的对象会被重新评估。30 秒是扫描周期，不能理解为所有失败 Pod 每 30 秒都重新调度。

退避期结束也不会单独唤醒仍留在 unschedulableQ 的 Pod。它通常还需要相关事件或兜底机制。

另一个版本相关的优化是 SchedulerPopFromBackoffQ。v1.37.1 默认开启时，activeQ 为空可以直接从 backoffQ 取对象。此时不必始终等满退避时长。调度队列源码、NodeResourcesFit 事件与回调

5. Assume 先在本地预占，后续调度才能继续

假设某节点剩余预算为 2 核，两个 Pod 各请求 2 核。第一个 Pod 已选中该节点，但远端绑定尚未完成。如果本地不记录这次分配，后续计算就可能重复使用同一份剩余预算。

AssumePod 负责把这次选择计入本地缓存：

// 机制示意，省略实际函数签名、检查和错误处理。
assumedPod := pod.DeepCopy()
assumedPod.Spec.NodeName = selectedNode
err := sched.Cache.AssumePod(logger, assumedPod)

节点的 NodeInfo 会包含这笔资源请求。后续 Pod 的调度快照因此可以看到预占结果。

在本文版本中，相关顺序是：

选定节点 → Assume → Reserve → Permit
                            ↓
                 后续绑定周期等待许可
                            ↓
                       PreBind → Bind

Assume 更新 scheduler 的基础资源缓存。Reserve 是调度框架的扩展点，用来让插件管理卷、设备等自己的预留状态。两者的职责不同。assumeAndReserve 源码

6. Bind 把节点选择写成正式结果

默认绑定请求通过 Pod 的 binding 子资源提交：

POST /api/v1/namespaces/{namespace}/pods/{name}/binding

DefaultBinder 把目标节点放进 Binding 请求。apiserver 检查 Pod 尚未绑定，再更新 Pod 的 spec.nodeName。存储更新成功后，正式绑定关系已经进入 etcd。

这里有三个容易混淆的对象：

  • Pod 在创建时已经存在于 API 存储中。
  • Assume 只修改 scheduler 本地副本和资源账。
  • Binding 请求推动原 Pod 更新，不会额外留下一个持久化的 Binding 对象。

绑定前也可能有其他 API 写入，例如状态、提名节点或 PVC/PV 更新。只有“正式节点分配关系”在这里通过 Bind 持久化，不能把它扩大为 Bind 前没有任何 etcd 写入。DefaultBinder、BindingREST

Assumed 什么时候转成 Added

Assumed 和 Added 是理解缓存实现的状态名称，API 中没有 phase: Assumed。

缓存概念状态 本地资源账 正式 API 关系
尚未预占 尚未计入目标节点 通常 nodeName 为空
Assumed 已计入目标节点 可能未绑定，也可能已绑定但事件尚未到达
Added 按正式对象维护 已观察到正式绑定
预占已回滚 撤销本次本地预占 仍需要结合真实绑定结果判断

Informer 观察到已绑定 Pod 后，事件处理会调用 Cache.AddPod。缓存用正式对象更新已有预占，避免再重复累计一次请求。Assumed 只说明本地尚未通过正式对象确认，不能证明 etcd 一定还没写入。

在 v1.37.1 中，不能把 finishBinding 理解为清除 assumed 标记的入口。这个函数在成功时记录 Scheduled 事件。正式对象的观察路径负责缓存确认。缓存实现

失败回滚与网络超时

Reserve、Permit、PreBind 或 Bind 失败后，错误处理会清理插件预留。它也会尝试通过 ForgetPod 撤销仍处于 assumed 状态的预占。

Bind 超时需要额外判断。请求可能尚未提交成功，也可能已经写入 etcd，只是响应丢失。

观察到的情况 应如何理解
Bind 失败，正式对象仍未绑定 清理预占，按失败原因重试
Watch 早于 Bind 响应 可以先确认 Added，再收到请求结果
超时后才观察到正式绑定 可能先回滚本地预占，再由迟到事件加入正式对象
Watch 已确认 Added，随后错误处理运行 ForgetPod 会检查 assumed 状态，不能无条件删除正式记账

失败处理还会检查 Informer 中的 Pod。普通 Pod 已有 nodeName 时，不应再加入未绑定 Pod 的选节点队列。由于 Informer 也可能暂时滞后，排障应综合 API 真实对象、事件和调度器日志。

Assume 只能协调本实例的预占。多个独立调度器不共享这份内存。apiserver 拒绝同一个 Pod 的重复绑定，也不等于它为不同 Pod 提供了全局节点资源锁。绑定失败处理

7. Gang 和 GPU 拓扑调度增加了哪些要求

普通 Pod 调度主要围绕单个 Pod 选择节点。分布式训练还需要表达整组约束，例如 8 个 worker 至少同时获得放置条件，否则已运行的一部分可能一直等待其他成员。

v1.37 中，原生 Gang Scheduling 为 Beta，默认关闭。相关路径依赖 GenericWorkload 和 PodGroup API。调度器需要先检查组成员条件，再评估是否能满足 minCount。达到要求后，才允许相应成员推进绑定。

它不会保证容器在物理时间上同时启动。运行中的 Pod 后续仍可能被删除或驱逐。补调度也需要按组策略重新评估。Gang Scheduling

GPU 作业还需要拓扑信息。整组资源数量足够，并不能保证 GPU 间通信路径合适。跨节点的网络域放置、节点内 GPU 组合、CPU/内存/网卡对齐，需要分别处理。Volcano HyperNode、KAI Topology 等可以表达网络域要求，具体设备分配仍需相应组件支持。

如果上层还有 Karmada，多集群编排先决定资源进入哪些集群。成员集群再执行本地调度与绑定。不要把集群选择、节点选择和具体设备分配混在一起。Volcano 网络拓扑调度、NVIDIA 拓扑集成路径、Karmada 架构

8. 按阶段排查一个等待中的 Pod

先查看对象与事件：

kubectl get pod <pod> -n <namespace> -o yaml
kubectl describe pod <pod> -n <namespace>
kubectl describe node <node>

然后按观察结果缩小范围：

观察 优先检查
nodeName 为空，存在 FailedScheduling 有效 request、节点约束、污点、端口和卷等拒绝原因
节点使用率低，但提示 Insufficient cpu / memory Allocatable 与已计入请求，不能只看 top
工作负载等待且 gate 未解除 schedulingGates 与负责解除 gate 的控制器
调度器日志显示已选节点，但尚未正式绑定 Permit 等待、PreBind、卷与设备准备、Bind 请求
Bind 报超时 API 中 nodeName 的实际值、Informer 观察进度与错误处理
nodeName 已有值，Pod 仍 Pending 节点侧准入、卷、网络、镜像和容器创建

activeQ、backoffQ、unschedulableQ 是 scheduler 内部结构，Pod YAML 不直接显示自己在哪个队列。需要结合 scheduler 日志与队列指标判断。Assumed 同样只存在于本地缓存机制中。

阅读源码时，可以依次查看以下入口。固定版本有助于避免把不同版本的函数和状态混用：

  • schedule_one.go：选节点、Assume、Reserve、Permit 与绑定错误处理。
  • scheduling_queue.go：队列、事件判断、退避和超时兜底。
  • cache.go：AssumePod、AddPod、ForgetPod 等缓存转换。
  • NodeResourcesFit：资源过滤、打分与重新入队事件。
  • Pod BindingREST：正式节点分配的存储更新。
