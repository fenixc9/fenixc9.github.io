没有教师 Logits，如何蒸馏大模型？拆解 Qwopus 的推理蒸馏实现

拿不到教师 logits，仍然可以把教师生成的文本当作标签，使用学生自己的 logits 计算交叉熵，再反向传播更新学生。 本案例属于离线的输出序列蒸馏；训练目标是模仿教师给出的“推理文本 + 最终答案”，实现手段是 response-only SFT 和 LoRA。所谓“没有 logits”，准确说是没有教师 logits，学生预测下一个 token 时仍然产生 logits。

本文研究对象：Jackrong/Qwen3.5-27B-Claude-4.6-Opus-Reasoning-Distilled。除模型卡，还核对了作者关联的公开 notebook、2026-04-05 PDF，以及 TRL、Unsloth 的实现。资料核对日期为 2026 年 10 月 18 日。下文从公开实现讲到交叉熵与梯度，再给出可运行的教学实验和工程训练骨架。

1. 蒸馏、SFT 与 LoRA 分别负责什么

问题 本案例的答案
知识从哪里来？ 已有模型生成的可见推理文本和答案
用什么训练目标？ 学生对这些文本的 next-token 交叉熵
更新哪些参数？ 主要更新 LoRA 适配器，冻结基础模型权重
为什么称为蒸馏？ 监督信号由教师生成，知识通过教师输出迁移
为什么同时称为 SFT？ 优化方式就是对标注序列进行监督微调
4-bit 的作用是什么？ 减少学生基础权重的加载成本，不提供教师概率

“蒸馏”描述监督来源，“SFT”描述训练方法，“LoRA/QLoRA”描述参数和显存策略。这几个词可以同时成立，不是互斥的算法名称。

从机制上，本案例接近广义的 sequence-level / response distillation：先取得教师输出，再让学生学习该输出。经典序列蒸馏论文讨论的是机器翻译，不能据此认定本案例复现了论文里的所有解码和筛选策略。Sequence-Level Knowledge Distillation

3. 没有教师 logits，训练信号从哪里来

3.1 有教师 logits 的传统做法

设某个上下文为 h_t = (x, y_<t)，其中 x 是问题、y_<t 是当前 token 之前的输出，教师和学生的词表 logits 分别是 z_T(h_t)、z_S(h_t)。以温度 τ 转换为概率：

q_T(v | h_t) = softmax(z_T(h_t) / τ)[v]
p_S(v | h_t) = softmax(z_S(h_t) / τ)[v]

常见蒸馏损失为：

L_soft = τ² × Σ_t KL(q_T(· | h_t) ‖ p_S(· | h_t))

教师告诉学生的不只是“下一个词选 A”，还包括“B 也有一定可能，C 很不可能”。这类软目标保留了候选项之间的相对关系。这里给出的是典型形式；实际系统还可能混合硬标签交叉熵。Hinton 等：Distilling the Knowledge in a Neural Network

这通常需要教师概率信息。直接按词表位置对齐时，还要求教师和学生的 token 空间兼容；异构 tokenizer 的概率对齐要另行处理。

3.2 只有教师文本的做法

教师返回文本：

问题：一件商品原价 100 元，打八折后多少钱？
推理文本：八折表示支付原价的 80%，所以计算 100 × 0.8。
最终答案：80 元。

我们把教师输出保存为字符串，用学生 tokenizer 转换成 token 序列 y* = (y*_1, …, y*_T)。每个 token ID 就是一个离散标签。

学生独立计算：

p_θ(y*_t | x, y*_<t) = softmax(z_θ(x, y*_<t))[y*_t]

损失是：

L_hard = −Σ_t log p_θ(y*_t | x, y*_<t)

如果某个位置的目标 token 是“80”，学生给它的概率是 0.1，这个位置的损失就是 −log 0.1 ≈ 2.303；提升到 0.8 后，损失约为 0.223。

计算过程只需要两个东西：正确 token 的 ID、学生自己预测的概率。 不需要知道教师当时给“80”分配了 0.6 还是 0.99。

3.3 为什么字符串标签能产生梯度

对单个位置，交叉熵相对于学生 logit 的导数为：

∂L / ∂z_v = p_θ(v) − 1[v = y*_t]

其中 1[条件] 表示条件成立时取 1，否则取 0。目标 token 对应位置的导数为 p_θ(y*_t) − 1，梯度下降会提高其 logit；其他候选位置则相应调整。

教师输出不需要可微。它只是固定标签，和人工写的答案一样。可微路径在学生内部：学生参数 → 学生 logits → 交叉熵。

实际库通常用 fused cross-entropy，直接吃学生 logits 和整数 labels；无需手工构建 one-hot，也无需先显式计算 softmax。

3.4 “采样文本”为什么也可以叫蒸馏

下面是通用原理推导，不是作者额外公开的一种 loss。

把教师在文本序列空间的分布记为 q(y | x)，学生分布为 p_θ(y | x)。若能从教师分布采样：

y^(k) ~ q(· | x)

则序列交叉熵可以写为：

H(q, p_θ) = E_(y~q)[−log p_θ(y | x)]
          ≈ (1/K) × Σ_(k=1…K) [−log p_θ(y^(k) | x)]

又因为：

H(q, p_θ) = H(q) + KL(q ‖ p_θ)

教师固定时，最小化期望负对数似然也会推动学生拟合教师分布。于是，可以访问教师的样本，而不用直接读取教师的整张概率表。

但不能把这个推导夸大成“拿一条答案就等价恢复教师 logits”：

  • 有限数据只是有限样本近似，一个问题一条回答的信息很少。
  • 贪心、beam search、top-p、温度采样得到的序列分布各不相同。
  • 过滤拒答、按正确性筛选后，学生学习的是筛选后的分布，而非原始教师分布。
  • 序列求和的 NLL 与逐样本做长度归一化并非同一加权目标；要核对框架实际 reduction。
  • 不同 tokenizer 时，上式可理解为对文本分布的拟合；实现中只计算学生对重新分词后序列的概率，不能声称进行了跨词表的逐 token KL。

本案例最稳妥的表述是“对筛选后的教师输出序列进行 SFT”，不是“无损恢复 Claude 概率分布”。

4. 为什么把推理过程也写进训练标签

只训练答案，监督样本形如 (x, a)，优化 −log p_θ(a | x)。

加入可见推理文本 r 后，样本变成 (x, r, a)，目标为：

−log p_θ(r, a | x)
  = −log p_θ(r | x) − log p_θ(a | x, r)

学生既学习如何从题目生成中间步骤，也学习如何在这些步骤之后给出答案。监督可以覆盖拆解问题、计算、检查约束、修改方案等可见行为，而不是只有最后几个答案 token。

需要把三个概念分开：

概念 能否从本项目数据得知
教师公开输出或数据集记录的推理文本 可以作为字符串读取和训练
教师每一步的完整概率分布 当前训练链路没有使用
教师真实内部计算、隐藏状态或未公开的思考 不能从这些文本恢复

数据里有 thinking 字段，不等于已经证明它完整、忠实地记录了教师内部机制。即便接口提供的是推理摘要，技术上也能做这种文本蒸馏，但监督内容应准确称为可见推理或解释文本。

如果接口只返回最终答案，也可以蒸馏答案；不能把编造的 thinking 字段当作真实教师轨迹。请求教师输出可公开的解题步骤，是另一种解释文本监督。

推理文本监督的收益应通过评测确认。模型写出“先分析，再检查”的格式，并不能单独证明它获得了同等的推理能力。

5. 作者的数据处理具体做了什么

5.1 把不同 schema 统一成对话

第一类输入大致是：

{
  "problem": "商品原价100元，打八折后多少钱？",
  "thinking": "八折对应支付原价的80%，计算100乘0.8。",
  "solution": "80元。"
}

统一后：

{
  "conversations": [
    {"role": "user", "content": "商品原价100元，打八折后多少钱？"},
    {
      "role": "assistant",
      "content": "<think>八折对应支付原价的80%，计算100乘0.8。</think>\n80元。"
    }
  ]
}

这是自拟示例，展示 schema，不是原数据的逐字摘录。

第二类将 human/gpt 映射到 user/assistant；第三类合并独立的 reasoning 和 content 字段，必要时先解析以 JSON 字符串存储的消息。

原 notebook 在缺少推理时使用空 <think> 块。这只是格式兼容，不会凭空生成推理监督。第三类数据处理还会移除 system 消息，只保留 user/assistant；如果 system 定义了不可缺少的规则，这会改变原始任务。新实验应先确认语义再决定是否移除。

5.2 应用学生聊天模板

对话不是直接拼成“问题 + 答案”。模型通常还要看到角色边界、换行和结束标记。作者选择 qwen3-thinking，再调用 apply_chat_template(..., add_generation_prompt=False) 生成训练文本。

可将最终序列理解为下面的结构示意，具体空行以实际模板输出为准：

<|im_start|>user
商品原价100元，打八折后多少钱？<|im_end|>
<|im_start|>assistant
<think>
八折对应支付原价的80%，计算100乘0.8。
</think>

80元。<|im_end|>

训练时已有完整回答，所以不需要额外添加一段等待生成的 assistant 前缀。推理时没有回答，才需要生成前缀来启动续写。

模板属于训练数据的一部分。 原始 JSON 正确，不代表模板处理后的序列和 loss 标签正确；必须检查后者。

5.3 长度与格式过滤

notebook 先把数据合并、全局 shuffle，再对模板化文本计算 token 长度，保留不超过 8192 的样本，并检查 assistant 文本是否存在推理边界。

这里有两个事实值得单独记录：

  1. 虽然文字说明提到去重，所核对的数据处理 cell 没有显式的内容去重操作。不能把 shuffle 或 concatenate_datasets 当作去重。
  2. “存在 <think> 和 </think>”只是结构检查，不能证明题目完整、推理正确、答案通过测试。

这些观察来自 notebook 的数据处理 cell 7；代码才是判断具体执行行为的依据。固定版本 notebook

6. 最关键的实现：只在回答上计算 loss

6.1 输入和标签是两份不同用途的数据

假设 token 序列是：

[用户前缀] [问题] [assistant前缀] [推理] [答案] [结束]

input_ids 保留全部内容，而 labels 类似：

input_ids: [用户前缀] [问题] [assistant前缀] [推理] [答案] [结束]
labels:      -100     -100       -100      原ID   原ID   原ID

-100 是交叉熵常用的 ignore index。它意味着这个位置没有直接监督目标，不是删除输入，也不是禁止关注该位置。学生仍能读取用户问题；回答产生的梯度也会经过处理问题上下文的计算路径。

attention_mask 则主要控制 padding 等注意力可见性，不能替代 labels=-100。

6.2 原作者的回答边界包含 <think>

notebook 的 train_on_responses_only 使用两个边界：

  • instruction：<|im_start|>user\n
  • response：<|im_start|>assistant\n<think>

含义是从识别到回答前缀之后的内容开始监督。由于 <think> 本身包含在前缀中，它通常也落在被屏蔽的前缀区域；推理正文、闭合标签和答案才是主要监督内容。精确边界要看 tokenizer 分词及所安装 Unsloth 版本生成的 labels。

这与推理时由模板预填 <think> 是相容的：模型只需从已经打开的推理块继续生成。不能笼统地说“每一个 <think> 标签 token 都一定被训练”。

Unsloth 的实现会生成以 -100 为默认值的 labels，再按找到的回答区间恢复 token ID。当前源码可用于理解机制，但不能当作作者当时未锁定依赖版本的证明。Unsloth 掩码实现

6.3 next-token 的 shift 必须正确

模型在位置 i 的输出用于预测位置 i+1 的 token，而不是复述当前位置。手写 loss 的核心形式如下：

# logits: [batch, seq_len, vocab_size]，来自学生模型。
# labels: [batch, seq_len]，非回答区及 padding 已设置成 -100。
next_logits = logits[:, :-1, :].contiguous()
next_labels = labels[:, 1:].contiguous()
loss = torch.nn.functional.cross_entropy(
    next_logits.reshape(-1, next_logits.size(-1)),
    next_labels.reshape(-1),
    ignore_index=-100,
)

调用标准 causal LM 的 model(..., labels=labels) 时，模型或训练框架通常已经负责 shift，不能再提前把 labels 移一次，否则会错位。

6.4 Teacher forcing：训练不是边猜边调用教师

训练时完整的正确回答已经在 input_ids 中，通过 causal mask 保证每个位置只能看到前文。

例如学习预测“80”时，前面的推理使用的是数据集中的正确 token；不是学生现场生成一遍推理后再判断。多个位置可以在一次前向中并行得到预测。

推理时学生使用自己生成的前缀。它可能写错中间步骤，进入训练中没见过的上下文。这种分布差异也是离线 SFT 的局限之一，不能靠增加 <think> 标签自动解决。

7. 为什么使用 LoRA，不更新整个 27B 模型

对原本的线性层权重 W₀，LoRA 写成：

W = W₀ + (α/r) × BA

其中 r 是秩、α 是缩放参数。W₀ 冻结，只训练低秩矩阵 A、B。交叉熵的梯度沿学生计算图传播到这些适配器参数，不会传播到远端教师。

在本案例中：

配置 notebook 中的值或行为
基础权重 4-bit 加载，非全参数微调
LoRA rank / alpha 64 / 64
dropout / bias 0 / none
标准注意力目标 q、k、v、o 投影
其他目标 gate、up、down、out 投影
梯度检查点 Unsloth 模式
micro batch / 累积步数 6 / 6
单卡名义有效 batch 36 个序列
学习率 / 优化器 2e-4 / AdamW 8-bit
epoch / warmup ratio 2 / 0.05，PDF 示例分别为 1 / 0.03

不要把“4-bit 训练”理解为所有中间结果、梯度和优化器状态都使用 4-bit。冻结的量化权重、适配器、激活值各有自己的存储和计算精度。

27B 规模基础权重按纯 4-bit 理论下界就约 13.5 GB，尚未包含量化元数据、未量化模块、适配器、梯度、激活和工作区。模型名还是近似参数规模。能以 Q4 做推理，不等于同一显卡能按 batch 6、8K 长度训练。 PDF 推荐 A100/H100 类 CUDA GPU；没有在本文实验中实际测量该训练配置的峰值显存。

另外，Qwen3.5 是混合注意力架构，不能假设只挂 q/k/v/o 就覆盖了所有主要模块。应查看实际匹配模块和可训练参数，而不是仅照搬普通 Transformer 的命名习惯。Transformers Qwen3.5 文档

数据过滤 8192 进入训练集之前允许的完整序列长度

notebook 安装 TRL 0.22.2。该版本上游 SFTConfig.max_length 默认值是 1024，并在数据准备阶段用于截断。 Unsloth 可能在运行时修补训练器，因此不能仅靠上游默认值就断言原实验一定只训练了 1024；但同样不能根据模型加载参数就断言 Trainer 使用了 32768。TRL 0.22.2 配置源码 · Trainer 截断实现

实际复现应显式设置长度，并同时检查：

print("trainer max_length:", trainer.args.max_length)
row = trainer.train_dataset[0]
print("actual sequence length:", len(row["input_ids"]))
print("supervised tokens:", sum(v != -100 for v in row["labels"]))
print("sequence tail:", tokenizer.decode(row["input_ids"][-160:]))
visible_labels = [v for v in row["labels"] if v != -100]
print("supervision:", tokenizer.decode(visible_labels))

尤其要确认最终答案和结束标记还在。一条长推理样本如果被从右侧截断，可能只剩“如何开始推理”，没有“如何得出答案和结束”，这与原本训练意图不同。

9. 不依赖大模型，亲手运行“只有文本标签”的训练

下面是独立编写的教学实验，不是作者模型复现，也不是推理能力评测。它用很小的 GRU 作为自回归学生，字符作为 token，模拟从教师得到一条文本后进行训练。没有教师对象、教师 logits 或远端请求。

只需要已安装的 PyTorch，CPU 即可运行：

import torch
from torch import nn
from torch.nn import functional as F

torch.manual_seed(7)
torch.set_num_threads(1)

# 把这两个字符串视为已经取得的教师样本。
prompt = "User: 2+3=?\nAssistant: "
response = "<think>2 plus 3 equals 5.</think>\n5.<eos>"
text = prompt + response
vocab = sorted(set(text))
stoi = {ch: i for i, ch in enumerate(vocab)}
ids = torch.tensor([[stoi[ch] for ch in text]])
labels = ids.clone()
labels[:, :len(prompt)] = -100

class Student(nn.Module):
    def __init__(self, vocab_size):
        super().__init__()
        self.embedding = nn.Embedding(vocab_size, 24)
        self.recurrent = nn.GRU(24, 48, batch_first=True)
        self.head = nn.Linear(48, vocab_size)

    def forward(self, input_ids):
        hidden, _ = self.recurrent(self.embedding(input_ids))
        return self.head(hidden)

student = Student(len(vocab))
optimizer = torch.optim.AdamW(student.parameters(), lr=0.02)
history = []
for step in range(120):
    optimizer.zero_grad()
    logits = student(ids)
    logits.retain_grad()
    loss = F.cross_entropy(
        logits[:, :-1].reshape(-1, len(vocab)),
        labels[:, 1:].reshape(-1),
        ignore_index=-100,
    )
    loss.backward()
    if step == 0:
        # 输出位置 i 的监督目标是 labels[i+1]。
        ignored = labels[:, 1:].eq(-100)
        ignored_grad = logits.grad[:, :-1][ignored]
        assert ignored_grad.abs().max().item() == 0.0
        assert student.head.weight.grad.norm().item() > 0.0
    optimizer.step()
    history.append(loss.item())

assert history[-1] < history[0]
print(f"loss: {history[0]:.4f} -> {history[-1]:.4f}")
print("student updated using text labels only")

这个实验说明三个独立事实：

  1. 文本转成整数 token 标签后，可以直接计算学生的交叉熵。
  2. 被忽略位置的输出 logits 没有直接 loss 梯度，监督位置会产生梯度并更新学生。
  3. 完整训练过程没有教师概率参与。

单样本 loss 下降只说明模型拟合了这个样本。它不能证明泛化，也不能证明小 GRU 学会了加法，更不能代替对 27B 模型的评测。

在 CPU 上实际运行上述代码，输出为 loss: 3.4134 -> 0.0004；屏蔽位置直接梯度为零、学生参数梯度非零的断言均通过。其余 Python 代码块完成语法检查；第 10 节的大模型训练骨架未实际运行。

10. 接近实际项目的实现骨架

本节是补充的工程示例，目标是展示关键接口如何连接，不是原 notebook 的逐字复制或已经实跑的 27B 配方。运行前需要建立兼容 Qwen3.5 的 Unsloth、TRL、Transformers、CUDA 环境；不要在旧环境里盲目升级单个依赖。

10.1 准备自己的离线 JSONL

每行采用第 5.1 节的 conversations schema。教师采集可以独立于训练作业：

读取种子题目
    → 请求教师输出可见解题步骤和答案
    → 校验请求是否完整成功、答案是否通过验证
    → 保存问题、可见推理、答案、教师版本及采样参数
    → 统一为 conversations JSONL
    → 按题目簇划分 train / validation / test

这是补充流程，不声称作者公开了同样的 Claude 采集程序。保存原始响应便于审计字段含义；没有推理文本时，选择答案蒸馏或剔除样本，不能制造隐藏思考。

建议在渲染模板前完成问题去重和数据划分。同一问题的不同解法、改写、续问应尽量放在同一 split，避免训练集和测试集泄漏。

10.2 连接学生、数据、Trainer 和回答掩码

下面假设 train.jsonl 与 validation.jsonl 已存在，且均包含 conversations 列。使用 TRL 0.22.2 的 processing_class 参数名；Unsloth 安装版本应与该训练栈兼容。

from unsloth import FastLanguageModel, is_bfloat16_supported
from unsloth.chat_templates import get_chat_template, train_on_responses_only
from datasets import load_dataset
from trl import SFTTrainer, SFTConfig

context_limit = 8192
student, tokenizer = FastLanguageModel.from_pretrained(
    model_name="unsloth/Qwen3.5-27B",
    max_seq_length=context_limit,
    load_in_4bit=True,
    full_finetuning=False,
)
student = FastLanguageModel.get_peft_model(
    student,
    r=64,
    lora_alpha=64,
    target_modules=[
        "q_proj", "k_proj", "v_proj", "o_proj",
        "gate_proj", "up_proj", "down_proj", "out_proj",
    ],
    lora_dropout=0,
    bias="none",
    use_gradient_checkpointing="unsloth",
)
tokenizer = get_chat_template(tokenizer, chat_template="qwen3-thinking")

splits = load_dataset(
    "json",
    data_files={"train": "train.jsonl", "validation": "validation.jsonl"},
)
def render(row):
    return {"text": tokenizer.apply_chat_template(
        row["conversations"], tokenize=False, add_generation_prompt=False,
    )}
def fits(row):
    ids = tokenizer(row["text"], add_special_tokens=False)["input_ids"]
    return len(ids) <= context_limit

splits = splits.map(render).filter(fits)
bf16 = is_bfloat16_supported()
config = SFTConfig(
    output_dir="./distilled_adapter_run",
    dataset_text_field="text",
    max_length=context_limit,
    packing=False,
    per_device_train_batch_size=1,
    gradient_accumulation_steps=8,
    num_train_epochs=1,
    learning_rate=2e-4,
    warmup_ratio=0.05,
    optim="adamw_8bit",
    bf16=bf16,
    fp16=not bf16,
    eval_strategy="steps",
    eval_steps=50,
    save_steps=50,
    logging_steps=5,
    report_to="none",
)
trainer = SFTTrainer(
    model=student,
    processing_class=tokenizer,
    args=config,
    train_dataset=splits["train"],
    eval_dataset=splits["validation"],
)
trainer = train_on_responses_only(
    trainer,
    instruction_part="<|im_start|>user\n",
    response_part="<|im_start|>assistant\n<think>",
)

# 先确认每个样本至少还有一个可监督的 next-token 目标。
for split in (trainer.train_dataset, trainer.eval_dataset):
    assert len(split) > 0
    for row in split:
        assert any(token != -100 for token in row["labels"][1:])

# 此处还应按第 8 节人工检查多种样本的监督内容和结束标记。
trainer.train()
student.save_pretrained("./distilled_adapter")
tokenizer.save_pretrained("./distilled_adapter")

该示例主动降低了 micro batch、保留验证集并显式设置长度，因此其有效 batch 和训练过程与作者 notebook 不同。batch=1 也不保证任何显卡都能运行 27B、8K 的训练；首次实验可同时缩短上下文、使用小规模数据验证链路。

验证集上同样使用回答掩码。TRL 支持其他 completion-only / assistant-only 机制，但它们依赖数据表示和模板的 assistant mask 支持；不能把已经渲染的普通 text 列一律视作带有自动角色掩码。TRL 0.22.2 SFT 文档

10.3 多轮对话有一个额外陷阱

本文核对的 Unsloth qwen3-thinking 模板会根据最后一个用户消息的位置，决定是否输出历史 assistant 的推理块。因此，历史轮的 <think> 可能在渲染后被剥离，而前述回答匹配串恰好要求 <think> 存在。

这意味着：原始 JSON 中有多轮推理，不代表每一轮的推理和答案都进入了 labels。新实验应明确选择“只监督最后一轮”还是“监督所有 assistant 轮”，检查实际模板结果和 labels，再选择边界或模板。所核对的 Unsloth 模板源码

这属于对当前源码的机制分析；原 notebook 没有锁定所有动态安装依赖，无法倒推出发布训练时使用了完全相同的模板实现。

11. 训练完成以后，知识到底存在哪里

知识以学生参数变化的形式保存。LoRA 训练时，变化主要存放在适配器的 A、B 矩阵中；加载基础模型加适配器即可使用。也可以在支持的导出路径中合并成单一模型，再转换和量化供推理使用。

这个过程没有从 Claude 把某层权重“拷贝”到 Qwen，也没有要求两者隐藏层维度、层数、attention 架构相同。两者之间传递的是文本，学生通过自己的网络拟合文本的条件概率。

推理时也无需把训练样本全塞进 prompt。相比 few-shot prompting，训练将重复出现的行为模式编码进参数；但具体学到多少、是否过拟合，需要用未见任务评估。

保存适配器时应一起保存 tokenizer 和 chat template。模板变化会影响思考开关、角色边界及工具调用格式。若单独修复 developer 角色兼容性，也应把它视为模板工程变化，不能全部归因于推理蒸馏。

12. 如何证明“学会了”，而不是只是更像教师

作者 notebook 没有建立完整的留出评估流程。模型卡里的社区体验和局部测试，可以作为进一步验证的线索，不能直接替代同条件对照实验。

建议做下面几组对照，均使用相同学生初始化、数据划分和推理预算：

实验 主要回答的问题
原始 Qwen + 原始模板 基线能力是多少？
原始 Qwen + 模板兼容修复 角色适配本身贡献了多少？
只用教师最终答案做 SFT 仅增加高质量答案监督是否已足够？
教师推理 + 答案做 SFT 推理文本带来多少额外收益？
相同数据的不同 epoch / 长度配置 是否过拟合、是否因截断损失答案监督？

至少记录正确率、代码单测通过率、格式有效率、工具任务完成率、平均生成 token 数和失败类型。控制解码配置；最好同时报告固定 token 预算下的结果。CoT 版本训练 token 更多，也应交代比较的是固定数据量还是固定训练计算量。

“推理更短”与“每秒输出更多 token”是两个指标。LoRA/SFT 不会自动让同架构、同量化模型的每一步解码大幅变快；端到端延迟可能因输出缩短而改善，也可能因过度思考而恶化。

13. 常见误解与故障定位

现象或说法 应如何理解或排查
没有教师 logits 就不能蒸馏 文本可以作为硬标签，学生 CE 足以产生梯度
文本训练完全没有 logits 仍然需要学生 logits；缺少的是教师 logits
学生和教师 tokenizer 不同，无法训练 文本由学生重新分词即可；不能直接拿教师 token ID 来当学生标签
教师只返回某个 token 的 logprob 不是完整词表分布；不能直接等同于完整软目标 KL
<think> 就是某种特殊蒸馏算法 它主要是序列结构约定；优化仍是 token 交叉熵
labels=-100 使模型看不到问题 它屏蔽直接 loss，不移除问题上下文
train loss 很低 可能只是在记忆、模仿风格或学习固定前缀
loss 接近 0，但输出没改善 检查有效 labels 数量、数据泄漏、是否只监督了模板或空回答
完全匹配不到回答 检查模板版本、实际换行、前缀中的 <think> 是否存在
模型会开始思考却无法正常作答 检查右侧截断是否删掉答案和结束标记
生成了推理就证明解释忠实 可见解释与内部计算的一致性仍需独立研究和验证
只有几千条样本，所以能复制整个 Claude 学生已有预训练能力；少量 SFT 只能在覆盖范围内改变行为和能力

14. 从教师文本到学生参数的完整链路

  1. 取得教师输出：调用教师或使用已有数据，保存可见推理与答案；无需读取教师权重或 logits。
  2. 筛选与划分：验证题目和答案、去重，按题目簇留出评估集，固定来源版本。
  3. 统一文本格式：把教师内容规范成学生可处理的对话结构。
  4. 应用学生模板与 tokenizer：得到 input_ids，不要复用异构教师的 token ID。
  5. 创建 labels：回答区保留 token ID，其他区域与 padding 设为 -100。
  6. 学生前向：在正确前缀和 causal mask 下产生 next-token logits。
  7. 计算 CE：对有效回答 token 做交叉熵，处理正确的 shift。
  8. 反向更新：梯度只沿学生计算图传播，本案例主要更新 LoRA 参数。
  9. 留出评估：同时衡量任务能力、格式、长度与稳定性，区分模板修复和训练收益。
  10. 保存与推理：保存适配器及模板，按实际部署需求合并、转换和量化。

真正跨越教师与学生边界的信息是教师生成的文本样本。这是“无教师 logits 蒸馏”能够实现的关键；而不是某种从最终文字反推出教师全部内部参数的技巧。
