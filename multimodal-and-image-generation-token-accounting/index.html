多模态推理与生图：Token 怎么统计，费用怎么计算？

一张图片进入模型后，到底消耗了多少 token？同样尺寸的图片，为什么不同平台返回的用量不同？生图模型又是否按生成的像素计费？

这些问题需要先区分三个口径：模型处理的序列长度、API 返回的 usage、平台用于收费的数量。三者可能接近，也可能不同。模型、预处理、接口和价格规则都会影响结果。

本文讨论图片、视频、音频输入，以及图片生成的常见计量方式。平台规则以 2026 年 10 月 27 日前的讨论和所列文档为背景。具体价格、模型限制与字段定义请以接入时的官方文档和账单为准。文中的计算是示例，没有实际调用或账单验证。

先区分三个计量口径

口径 用途 需要注意
模型侧序列长度 判断上下文限制，支持调度和 KV Cache 管理 多模态特征的表示取决于模型架构，也不能覆盖全部编码计算
API usage 向调用方报告输入、输出和可能的模态明细 字段和细分程度取决于接口及模型
计费用量 按价格表计算费用 平台可能使用倍率、尺寸档位、时长、张数或缓存折扣

文本 token 通常来自 tokenizer 对文本的编码。视觉 token 这个名称覆盖的含义更广。它可能表示图像特征占用的序列位置，也可能表示平台定义的计费单位。

同样，媒体文件的字节数、URL 长度和 Base64 字符数通常不能直接换算成用量。它们描述的是传输或存储形式。图片解码后的尺寸、预处理方式与模型规则才是主要输入。

图片输入：缩放、切块和视觉编码

常见的图片输入链路如下：

图片文件或 URL
    ↓
解码与缩放
    ↓
按模型规则切分 patch 或 tile
    ↓
视觉编码器生成特征
    ↓
模型处理特征，接口返回 usage

模型可能先对图片缩放或限制最大像素数。之后，它会按自己的规则切块或分配视觉特征。最终用量与处理后的尺寸、模型和请求参数有关。图像细节档位也可能影响计量。

平台或模型 文档中的典型方式 边界
OpenAI 部分模型 使用处理后图像的 32×32 patch，并按模型规则应用倍率 不同模型与 detail 档位采用不同规则
Claude 文档描述按 28×28 patch 估算视觉 token 应先考虑模型的缩放与尺寸限制
Gemini 部分模型 按图片尺寸及 tile 统计 模型和 media_resolution 会影响分配
百炼部分视觉模型 按处理后的像素或图像块估算 模型和像素限制会影响结果

例如，假设某个使用 28×28 patch 规则的模型收到一张 1024×1024 图片，且图片无需缩放，视觉 token 数的示意计算为：

ceil(1024 / 28) × ceil(1024 / 28)
= 37 × 37
= 1369

这个结果只展示公式如何工作。实际请求还应检查具体模型的预处理限制、特殊 token 和返回的 usage。它不能用于推断其他模型的账单。相关规则见 OpenAI 图片输入文档、Claude 视觉文档、Gemini token 文档和百炼视觉模型文档。

视频与音频：不能只看文件大小

视频常见的处理方式是先抽帧，再对每一帧进行缩放和视觉编码。如果请求包含音轨，模型还可能处理音频。以下因素都会影响用量：

  • 视频时长和实际抽取的帧数。
  • 抽帧率，以及每帧处理后的分辨率。
  • 是否处理音轨，以及音频处理策略。
  • 模型是否按需加载视频内容。

有的平台提供基于时长或帧的估算。这个估算只适用于对应模型和处理模式。将某个接口的“每秒 token 数”推广到所有视频请求会产生偏差。

音频也存在多种计量方式。接口可能报告音频 token、转写文本 token，或者直接按输入或输出时长计量。使用时需要区分音频输入、语音输出和文本转写。接口没有返回模态明细时，应记录为未知。未知值不能自动当作零。

自部署引擎统计了什么

推理引擎一般会根据实际构造的输入报告 usage。具体字段与实现取决于引擎版本、模型和 API。某些多模态模型会将图片占位符展开为多个位置，再用视觉编码器输出的特征填充相应位置。其他架构可能使用不同的数据路径。

例如，接入 vLLM 时，应检查部署版本的 Chat Completions 实现和对应模型处理逻辑。该链接指向 main 分支，不能代替对已部署版本的检查。

模型序列长度也不能代表全部计算成本。图片解码、视觉编码、视频抽帧和音频编码都可能消耗 CPU 或 GPU 资源。容量规划还需要观察排队时间、模型延迟、显存和 GPU 使用情况。

流式请求需要额外处理 usage。接口可能只在最后一个数据块返回完整统计。客户端中断或连接失败时，最终 usage 可能不可用。平台应保留服务端观测数据，或将请求标为待对账。

生图模型如何统计输出

一次图片编辑请求可能同时包含文本、参考图和生成图片：

输入：文本提示词 + 参考图
输出：生成图片 + 可选的文字响应

文本输入、图片输入和图片输出可能使用不同的计费单价。有的平台按图片输出 token 计量。有的平台按生成张数、尺寸和质量计量。多轮编辑还可能把历史上下文作为输入。

云端生图：按模型和规格计量

部分 GPT Image 模型公开按图片输出 token 计费的规则。具体数量取决于模型、输出尺寸和质量。不同代模型的规则不能直接混用。中间预览图、输入参考图和缓存折扣也需要按接口文档单独确认。OpenAI 生图文档列出了相应规则。

部分 Gemini 生图模型也按模型和分辨率档位列出图片输出 token。档位之间的计量不一定与像素数等比例增长。具体数值应查询对应模型的生图文档和价格表。

**图片输出 token 是平台公布的用量口径。**它不能单独证明模型在内部以什么顺序生成图像，也不能作为不同厂商 GPU 成本的统一度量。

自部署扩散模型：通常看资源和规格

扩散或 flow 类生图流程通常先处理文本条件，再在 latent 空间进行多步生成，最后将结果解码为图片。提示词可以使用文本 tokenizer。图片生成过程不必然逐个生成离散 token。

自建平台可以记录以下指标：

指标 作用
图片数量、宽高、batch size 描述输出规模
实际生成步数、采样器和模型 区分推理路径
参考图与其他条件输入 解释额外预处理和模型计算
GPU 时间、延迟和峰值显存 观察资源消耗和容量

平台也可以定义图片积分或等价 token，统一配额和收费。应明确标注这种数量是平台折算值。折算规则需要记录版本，并用实际资源消耗校准。不能把宽高乘积直接称为模型生成的真实 token 数。

推理平台如何设计用量与对账

统一平台需要同时支持上游 API 和自部署模型。建议把原始用量、媒体规格和内部计费结果分开保存：

数据 建议字段
请求身份 request_id、供应商、模型及版本、API、引擎版本
上游 usage 输入、输出、缓存、思考及模态明细；保留原始响应
媒体信息 图片数量与尺寸；视频时长、抽帧数和 FPS；音频时长
生图信息 图片数量、尺寸、质量、预览数量、步数和 GPU 时间
计费与对账 计费单位、数量、价格版本、金额、对账状态

一个可实施的流程是：

  1. 请求进入时，按具体模型的 processor 或上游计数接口预估输入用量。
  2. 根据额度和输出上限进行预检查。
  3. 请求结束后保存原始 usage 和媒体规格。
  4. 按模型、API 和价格版本计算费用。
  5. 与供应商账单对账，处理缺失 usage、缓存折扣和中断请求。

计费时需要检查字段包含关系。例如，某些接口的缓存 token 是输入 token 的子项。如果先用总输入量计费，再把缓存量全部相加，就会重复计算。正确算法应遵循接口和价格表的定义。

对外展示也应区分“未返回”和“零”。上游未提供 output_image_tokens 时，平台不应编造精确值。使用内部规则估算时，应同时展示单位、规则版本与估算状态。

总结

图片输入的用量通常取决于处理后尺寸和模型的切块方式。视频还受抽帧与音轨影响。音频可能按 token 或时长计量。生图输出则可能按图片 token 或图片规格计费。

平台设计的重点是保留每个数字的来源和单位。模型序列长度用于理解上下文和调度。API usage 用于记录请求消耗。计费用量用于按照指定价格版本对账。把这些数据分开，才能解释模型间的差异，也能处理接口升级和账单异常。
