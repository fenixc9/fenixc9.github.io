T3 Code 与新版 Herdr 调研：Agent 控制台、开源范围与自建隐私边界

2026年11月8日
9.8k 字 82 分钟

T3 Code 与新版 Herdr 调研：Agent 控制台、开源范围与自建隐私边界

T3 Code 适合希望统一使用多家编程 Agent，并通过电脑、浏览器和手机接管任务的开发者。新版 Herdr 将终端运行时 herdr-core 与桌面应用 herdr-app 分开，更适合保留原生 CLI、组织 Agent 协作和定制工作台。

隐私要求会改变选型结果。T3 Code 支持不登录 T3 云账号的本地使用和直接配对。官方 T3 Connect 则引入云端身份服务、授权中介和托管隧道。相关代码公开，但这不能证明运营方在技术上无法访问环境。

核查日期：2026 年 11 月 8 日。本文依据官方仓库、GitHub API、项目文档及部分认证源码整理。本次调研未安装实测，未验证商店安装包与公开源码的一致性，未测试线上服务。后文包含一次用户报告的唤醒后无响应现象，以及源码与社区提案分析。本文未独立复现该现象，也未进行性能、连接稳定性或任务成功率的对照测试。

T3 Code 提供什么

T3 Code 自称 agent harness control surface。底层的 Agent 执行机制仍由 Claude Code、Codex、Cursor 等工具提供。T3 Code 统一展示项目、线程、消息、工具调用、审批和开发结果。用户继续使用自己的订阅或 Provider 凭据。

它采用客户端与服务器分离的结构：

桌面客户端 / Web 客户端 / 手机客户端
                  ↓ 认证 RPC
             T3 Code Server
                  ↓ Provider 适配器
       编程 Agent、终端、Git 与项目文件

项目文件、Provider 进程和凭据归执行服务器所有。客户端切换设备，不会把执行环境切换到手机上。手机承担远程操作功能，服务器必须保持运行。项目说明、架构文档

主要卖点与代价

能力 实际价值 需要接受的代价
多 Provider 统一交互 减少切换不同 Agent 界面的成本 功能完整度取决于适配层
桌面、Web、iOS、Android 随时查看结果、答复问题和继续任务 仍要维护执行机器及其登录状态
T3 Connect、直接配对、SSH 提供多种远程接入路径 每条路径有不同的信任边界
worktree、变更检查、PR 关联 将并行任务与代码交付连起来 worktree 不提供进程沙箱
MCP 与线程 CLI 外部 Agent 和脚本可以管理线程 分工、验收和失败处理仍需设计
MIT 开源 可以修改、部署和 fork 外部云服务不随源码自动变成自托管服务

T3 的架构文档要求 Provider 差异留在适配器内部。这个设计有利于统一界面。它也带来持续跟进 Provider 协议变化的成本。不同 Provider 的权限模式仍有差异。权限文档

T3 Code 已提供对外控制入口。外部 MCP 客户端可以读取项目和线程，也可以获得启动、发送和停止线程的权限。本机脚本可以使用 t3 thread。这些能力适合接入自动化系统，但不能直接推导出完整的多 Agent 调度能力。外部 Agent 接入

生态需要分层判断

T3 Code 的生态优势主要集中在三个方面：

  • 分发渠道丰富。官方列出了 npm、桌面安装包及多个系统包管理器。
  • 用户反馈渠道齐全。项目提供 Issues、Ideas Discussions 和 Discord。
  • 可程序化接入。项目已有 Provider 适配、MCP 和线程 CLI。

本次未确认有类似 Herdr 的成体系第三方插件市场，也没有取得可信的月活、留存或 Discord 活跃用户数据。README 对贡献的限制，应与发布记录中的外部贡献分别理解。README、贡献规则

新版 Herdr App 与 Core 是独立的新仓库。不能把原有 TUI 的近五万 Stars 当成新架构已具备相同成熟度的证据。

新版 Herdr 的执行和界面分层

Herdr 当前包含原有 TUI，以及基于 herdr-core 的新桌面应用。官方说明，新 App 与原有 TUI 不共享 Agent 会话。本文主要比较新架构。Herdr 官网

herdr-app / 自制客户端 / Shell 脚本 / 其他 Agent
                         ↓ CLI 或 JSON-RPC
                     herdr-core
                         ↓
               持久终端、进程、状态与事件
                         ↓
           Agent CLI / Shell / 测试 / 开发服务器

herdr-core：独立运行的终端与协作运行时

Core 没有图形界面。它可以运行任意终端程序。用户通过 hc 启动、读取和接管终端。自制客户端可以使用 JSON-RPC API。hc schema 提供 OpenRPC 和 JSON Schema 描述。

Core 在 Unix 上使用本地 socket，在 Windows 上使用 named pipe。hc connect 可以通过标准输入输出承载协议，也可以通过 SSH 连接远端机器。Core README、API 文档

新 Core 的状态机制需要单独说明：它只记录程序通过 OSC 7501 主动上报的状态。它不根据屏幕内容猜测 Agent 品牌和工作状态。

因此，“能运行某个 CLI”和“能显示其 working、blocked、done 状态”是两种能力。没有状态上报的程序仍能运行，但没有这些状态。模板可以等待输出安静后发送初始消息。官方明确指出，输出安静不能证明程序已经准备好。Agent 模板

herdr-app：可修改的桌面工作台

App 组织 space、tab 和 pane。它汇总 Core 中的 Agent。用户可以查看子任务，接管终端，也可以连接 SSH 机器。

它的定制能力超出主题配置。layout 决定窗口排列。JavaScript mods 绘制面板、菜单和对话框。用户保存个人修改后，App 会重新加载。错误修改会保留上一个可用版本并报告错误。

这适合增加运行计时、审查队列或项目面板。具体实现成本仍取决于 mod API。Mods 可以运行程序、读文件和访问网络，属于可信代码。App README、Mods 文档

T3 Code 与 Herdr 的关键差异

维度 T3 Code herdr-core + herdr-app
核心抽象 项目、线程、结构化消息与工具事件 终端、进程、父子关系、程序状态
Agent 交互 通过适配器统一展示 保留 Agent 原生 TUI
扩展兼容性 取决于适配器或协议支持 任意 CLI 可运行，状态能力需协议支持
跨设备体验 已有桌面、Web 和手机客户端 当前 App 以桌面为主，Core 可供自制客户端使用
自动化 MCP、线程 CLI、RPC CLI、JSON-RPC、事件和父子终端
界面改造 修改源码及已有扩展接口 layouts 和 JavaScript mods
开发结果管理 已有 checkpoint、diff 和 PR 等结构化工作流 可通过工具和界面扩展组织，不能假定与 T3 等价
API 成熟度 项目快速变化 Core API 明确标记为 preview、0.x

实时终端与本地聊天输入

Herdr App 的终端会持续把输入字节发送给 Core。远端 Shell 或 Agent CLI 处理输入，然后返回终端输出。用户看到的字符通常来自远端回显。粘贴和中文输入法提交的文本也可以作为一批字节发送，不能把这个过程理解为一个字对应一个网络包。连续输入也不要求等待上一个字的回复。App 输入与传输实现

T3 Code 的聊天输入框在客户端维护草稿。用户发送后，客户端提交完整消息，由服务器启动或继续 Agent 工作。这里讨论的是聊天输入框。T3 Code 的内置终端仍属于实时终端。聊天输入实现

Herdr 远程终端
按键或已提交文本 → 本地 Core → SSH → 远端 Core → 程序
屏幕显示       ← 本地 Core ← SSH ← 远端 Core ← 终端输出

T3 Code 聊天
输入 → 客户端编辑草稿
发送 → T3 Server → Provider → Agent
维度 Herdr 实时终端 T3 Code 聊天输入
打字反馈 通常依赖远端回显，受网络往返延迟影响 客户端编辑草稿，不需要等待远端回显
网络暂时不可用 远程程序无法及时反馈输入 草稿编辑与远端执行分开，提交和接收回复仍需要网络
交互范围 可直接操作 Shell、Vim、Agent CLI 和交互菜单 使用客户端与 Provider 适配器提供的结构化交互
输入与展示 保留原生终端行为，编辑能力取决于远端程序 容易提供长文编辑、附件、消息状态和工具调用展示
接入成本 程序能在终端运行即可操作，状态上报另有要求 需要适配各 Provider 的协议和功能

终端客户端无法仅凭输入字符，可靠判断程序正在接收提示词、密码还是菜单操作。把所有输入改成本地编辑，再一次性发送，会改变这些程序的交互语义。需要针对输入场景设计独立入口。

Herdr 的优势在于通用终端控制。T3 Code 的优势在于结构化 Agent 工作流。T3 Code 包含终端入口，但不能据此判定它覆盖了 Herdr 的全部会话管理、多机器操作和运行时协作能力。Herdr 能运行同一个 Agent CLI，也不代表它具有 T3 Code 的结构化交互。两者没有经过验证的严格超集关系。

Mac 唤醒后的无响应与探活机制

本次讨论中，用户报告了一个具体问题：Mac 唤醒后，在 Herdr App 中敲字没有反馈，界面也没有显示重连提示。用户怀疑当时 Tailscale 尚未恢复。该现象未在本次调研中独立复现，实际原因仍待日志或复现确认。

这个现象与“连接暂时失效，但程序尚未确认断线”的状态相符。系统可能仍保留旧连接。写入成功也可能只表示数据进入本地缓冲区。远端没有回复，不一定立即产生 EOF 或连接错误。这是依据传输机制和相关 PR 描述作出的推断。

当前 Core 有定期探活。默认心跳间隔为 15 秒。远程连接连续没有收到任何数据，达到 machine_timeout 加心跳间隔后，Core 才放弃连接。machine_timeout 默认是 30 秒，因此默认静默判定阈值约为 45 秒。普通数据同样可以刷新存活判断。心跳实现、远程连接判定

45 秒是静默阈值。它不代表每次打开屏幕后都恰好等待 45 秒。检测后的重试退避还可能增加等待时间。Core PR #139 明确指出，Mac 唤醒后可能先保持约 45 秒的假在线状态，也可能处于最长 30 秒的重试退避。

Herdr App 已有连接丢失后的重连提示。问题发生在连接尚未被判定为丢失的阶段。客户端可以提前显示“远端未响应”或“正在验证连接”。实时终端对网络的依赖，不妨碍客户端提供这种反馈。

社区修复分别处理哪一层

截至 2026 年 11 月 8 日，下列两个 PR 均处于 Open 状态，尚未合并。另一个本地回显方案仍是 Issue 提案。它们不能当作正式版已经具备的能力。

社区工作 处理的问题 方案与限制
Core PR #139 Mac 唤醒后旧 SSH 连接假在线，或停在重试退避 监听系统唤醒完成事件，立即探测旧连接；3 秒内无回复就关闭旧传输，保留远端程序和查看会话，再重新连接
App PR #633 远程无响应时没有解释，用户误以为界面卡死 增加无响应提示、待发送输入数量、断线原因与立即重连入口；不包含 Core 的假在线修复
App Issue #305 连接可用但延迟较高，字符显示慢半拍 提议预测本地回显；作者称 fork 已有实现，目前该入口仍是提案

Core #139 在唤醒后设置一个 30 秒的快速恢复窗口。每次连接尝试最多持续 3 秒。重试间隔从 250 毫秒增加到最多 1 秒。这个设计可以覆盖网络比系统唤醒稍晚恢复的情况。它也避免复用可能失效的 SSH ControlMaster。作者注明，真实合盖和唤醒流程尚未完成硬件验证，不能承诺打开屏幕后固定几秒恢复。

App #633 通过“输入后没有输出”和“往返探测也慢”共同判断无响应，避免把正常安静的程序误报为断线。它拟在 6 秒无响应时显示提示。确认机器不可用后，界面显示状态、持续时间、原因和 Reconnect now 按钮。远程新建终端也改为后台执行，超过 0.7 秒显示启动提示。发往无响应程序的滚动事件会被限速，减少输入堆积。

Issue #305 借鉴 mosh 的预测本地回显。方案只预测光标后空白位置中的简单可打印字符。程序先确认会回显后，客户端才继续预测。远端输出与预测不符，或者 1.5 秒内没有确认，客户端就撤销预测。中文和输入法组合、粘贴、行中编辑、方向键等不在该方案的预测范围内。

这三个方向分别改善恢复速度、连接状态反馈和高延迟下的打字手感。本地预测回显仍需远端程序确认，不能提供聊天输入框那样的离线草稿语义。

频繁睡眠、通过 Tailscale 操作远端 Agent 时，可以优先验证聊天输入与终端组合的工作方式。长提示词在客户端编辑，需要原生 CLI 交互时再使用终端。Herdr 用户则应重点关注 #139 与 #633 的合并和发布进展。

多 Agent 协作

Core 将父子关系放入运行时。在一个 hc 终端内启动的程序可以成为其子终端。Agent 可以通过 hc send 交换消息，也可以通过 hc wait --children all 等待子任务。父 Agent 会收到子任务需要关注或结束的通知。

子终端默认随父终端结束。--outlive-parent 可以改变这一行为。Unix 上正常结束终端主要挂断程序及前台作业，刻意脱离的程序仍可能存活。它不能替代完整的进程隔离和清理策略。Core 生命周期说明

T3 Code 提供启动和继续线程的接口。它适合把不同 Provider 的会话作为任务入口。本文核查的文档没有展示与 Core 同等明确的父子终端生命周期。

两者都需要上层流程决定任务拆分、验收、重试和合并策略。运行多个 Agent 本身不构成完整调度系统。

持久化和恢复

Herdr App 关闭后，Core 中的任务继续运行。关闭 pane 或 tab 则会结束对应终端。Core 的 holder 进程允许更新或受支持的重启交接保留终端程序。

机器重启不能保留原进程。保留的终端在程序丢失后恢复为新 Shell，不自动重跑原任务。Core 持久化与信任说明

T3 Code 更强调线程状态、命令去重和重连恢复。它先提交执行意图，再处理副作用。命令被接受，不代表 Agent 或后续工作已经完成。Provider 进程丢失后，相关执行也不能简单重放。

所以需要分别评估会话记录恢复、网络重连、进程保活和任务重跑。一个“支持持久化”的标签不足以表达这些差异。

主仓库采用 MIT 许可证。Herdr 的 App 与 Core 使用 Apache-2.0。各项目依赖仍应按自身许可证处理。T3 许可证、移动端源码、Relay 源码

自编译移动端需要注意更新来源

移动端 README 提供 iOS 和 Android 构建步骤，并明确说明 T3 Connect 可选，新克隆仓库默认不启用它。

但当前 app.config.ts 默认启用 Expo OTA 更新，并指向官方更新项目。自建时应检查这项配置。若希望自己控制客户端代码，可以在构建配置中关闭官方更新：

T3CODE_MOBILE_UPDATES_ENABLED=0

这个设置控制 OTA。它不等于关闭诊断，也不移除所有官方域名和云服务配置。严格自建还需检查登录域名、应用链接、推送、诊断和构建渠道。移动端构建说明、移动端配置

官方 Connect 能否看到 Agent 交互

这个问题需要区分正常数据流、主动发布的数据和授权能力。

正常聊天流不经过 relay Worker 转发

根据官方架构，客户端完成连接引导后，普通 HTTP 和 WebSocket 流量通过环境的隧道域名访问执行服务器。Relay Worker 不转发普通会话流量。自动化 webhook 是一个例外。

这里的“直接访问”仍经过 Cloudflare Tunnel。源码为托管隧道配置了指向本机 loopback HTTP 服务的入口。因此，不能把它理解为绕过云基础设施的设备直连。Connect 架构、隧道配置源码

本次核查的链路没有提供足以确认的应用层端到端加密保证。HTTPS 和隧道加密本身，不能证明云基础设施无法读取应用内容。

Relay 掌握连接引导的签名权

服务器的 mintCredential 会验证 relay 签名。它检查目标环境、关联用户、有效期和防重放信息。验证通过后，服务器创建绑定客户端证明密钥的短期连接凭据。

DPoP 可以防止其他人拿到凭据后直接重复使用。它不排除掌握 relay 签名权的一方，使用自己的客户端密钥请求新的凭据。官方文档明确承认 relay 是可信授权中介，也承认签名密钥被攻破有实际影响。凭据签发源码、环境认证设计

由此可以作出一个有条件的安全推断：当环境仍与该 relay 关联、网络可达且接受其签名权时，控制该签名能力的一方可能建立获授权的客户端连接，进而访问其权限允许的数据。

这属于信任模型分析。本文没有验证线上利用路径，也没有证据表明 T3 正在这样访问用户会话。公开源码同样无法证明线上服务运行的版本、配置和日志保留策略。

遥测与手机活动发布是独立通道

官方数据文档声明，产品事件不包含提示词、回答、文件内容和认证令牌。事件包含模型、用量、运行结果及哈希账号标识等信息。

以下开关需要分别检查：

通道 数据及控制边界
服务端产品事件和 relay 追踪 可设置 T3CODE_TELEMETRY_ENABLED=false
独立浏览器与手机连接追踪 不受服务端环境变量控制，文档称没有独立的 relay tracing 开关
手机崩溃报告 手机诊断设置控制，不能据此认为连接追踪也关闭
Publish agent activity 会发布项目名、线程标题、模型和状态；遥测退出不关闭它
离线 webhook 暂存 显式启用后，relay 会保存原始请求，属于另一条数据通道

错误报告中的错误文本可能包含当时处理的值。隐私评估不能只检查是否上传完整提示词。遥测说明

能否不登录并完全自建

可以不登录 T3 官方账号使用。首先要区分 Provider 登录、设备配对和云账号登录。

Provider 凭据用于执行 Agent。设备配对用于授权客户端访问自己的服务器。T3 Connect 账号用于机器发现、云端连接引导和相关服务。这三者可以分开。

路径 T3 官方账号 Clerk 开发工作
本地桌面或本地服务器 不需要 不需要 常规安装配置
自管网络、SSH 或 HTTPS 入口，加直接配对 不需要 不需要 维护自己的网络与证书
按官方方案自部署 Connect relay 不需要 默认需要自己的 Clerk 实例 部署云资源，配置并构建客户端
自部署 Connect，替换 Clerk 不需要 可移除 需要适配客户端和 relay 认证代码

最简单的自管路径

若目标是让交互和授权留在自己的控制范围，优先使用直接配对：

自管手机或桌面客户端
          ↓ 自管 VPN / SSH / HTTPS 入口
      自管 T3 Server
          ↓
     Provider 与项目文件

官方提供 t3 pair 和配对链接。桌面客户端也能添加 SSH 环境。这条路径不需要部署 T3 Connect relay。自行提供的反向代理或隧道负责可达性，T3 Server 负责设备认证。远程连接文档

这仍保留 Provider 自身的数据处理边界。使用第三方 VPN 或反向代理，也需要单独评估其信任关系。要排除官方网页更新带来的影响，应使用自部署 Web 客户端或自编译客户端。

自部署完整 Connect 的工作量

官方提供以下客户端配置：

T3CODE_CLERK_PUBLISHABLE_KEY=<自己的 Clerk 公钥>
T3CODE_CLERK_JWT_TEMPLATE=<自己的 JWT 模板名>
T3CODE_CLERK_CLI_OAUTH_CLIENT_ID=<自己的 OAuth 客户端 ID>
T3CODE_RELAY_URL=https://relay.example.com

客户端构建会嵌入公共配置。Relay 部署还需要云端资源与服务凭据。仓库提供部署脚本，但这不是一个只替换 URL 的单容器方案。

当前认证代码直接使用 Clerk。本次未发现匿名模式或任意 OIDC 服务替换开关。若要用自建身份服务，需要修改认证集成。不能把“中继开源”直接解释成“整套身份服务可原样离线运行”。Connect 部署说明、Relay 部署说明

直接连接不提供官方 Connect 的全部附加服务。手机后台推送依赖 Connect。自建推送需要处理客户端构建和 Apple、Google 的平台凭据。手机通知说明

Herdr 的隐私边界也需要检查

Core 默认使用本地 socket 或 named pipe。远程连接依赖 SSH。它没有额外的云账号授权中介，但它信任能够访问 Core API 的客户端。

官方明确说明，Core 不是沙箱，也不是 Agent 权限代理。连接者能以运行 Core 的系统账号执行命令和操作文件。Core 不提供单独的 API 密码或逐客户端权限检查。不同 session 也不构成安全隔离。Core 安全模型

Herdr App 发布版默认启用使用遥测。用户可以在 Privacy 设置关闭。第三方 mods 是未沙箱化的可信扩展。因此，不能仅凭本地架构就把整个 App 认定为无外连、低权限或不需要检查。

选型与下一步验证

需要现成的多 Provider 交互、跨设备操作和手机接管时，可以优先试用 T3 Code。需要原生终端、Agent 派生 worker 和自定义运行控制时，可以优先评估 herdr-core。需要修改桌面工作流时，再引入 herdr-app。

若隐私要求是不把授权签发权交给 T3，T3 的直接配对与自管连接路径值得优先验证。没有必要为了远程可达性部署完整 Connect。若确实需要云端机器发现和推送，再评估自部署 relay 的运维成本。

正式采用前，仍需完成四项验证：

  1. 固定源码版本，构建客户端和服务器。确认关闭官方 Connect 后，直接配对可以完成实际任务。
  2. 观察客户端、服务端及手机的网络请求。分别检查遥测、诊断、活动发布和 OTA。
  3. 测试网络断开、客户端退出、服务更新和机器重启。记录哪些状态和进程可以恢复。
  4. 用同一个小项目验证任务隔离、人工接管、审批和结果回报。不要用 Stars 代替工作流验证。

T3 Code 与 Herdr 都提供了有价值的控制接口。最终决定权在于执行模型、授权根、客户端更新来源，以及团队愿意承担多少适配和运维工作。
