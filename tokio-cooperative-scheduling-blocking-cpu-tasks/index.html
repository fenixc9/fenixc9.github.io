Tokio 为什么会被一个死循环卡住：协作调度、阻塞检测与 CPU 长任务治理

2026年10月20日
5.5k 字 47 分钟

Tokio 为什么会被一个死循环卡住：协作调度、阻塞检测与 CPU 长任务治理

Tokio 无法抢占一个不返回的 poll。治理的关键是缩短持锁范围、让连续计算有界、限制资源并发，并用运行时监测和进程隔离补足失控场景。 把函数写成 async、增加 .await 或设置 timeout，都不能自动保证执行器线程及时获得控制权。

一个 Rust 服务在低负载时工作正常，增加并发后却出现 P99 飙升、定时器延迟，甚至健康检查无响应。原因可能并非网络慢，而是某段同步代码迟迟没有把线程交还给异步执行器。

本文从单次 poll 的执行边界出发，解释 Tokio 与 Go 的调度取舍，以及如何在开发时发现阻塞、在生产中限制影响。资料核验日期为 2026-10-20。代码为局部示例，未在具体项目中编译、压测；时间预算与并发额度需要根据实际负载确定。

1. 调度边界：为什么单个 poll 的死循环会卡住 worker

执行器调用任务的 poll()；只有它返回，执行器才能继续调度。同步计算、同步阻塞 API、争抢同步锁，都可能让一次 poll 持续很久。

tokio::spawn(async {
    loop {
        std::hint::spin_loop();
    }
});
  • current_thread：唯一执行器线程被占住，其他任务无法继续。
  • multi_thread：占住一条 worker；其他 worker 可以继续，但不能保证所有任务均不受影响。
  • 所有 worker 都被占住：异步任务调度基本停滞。

Work stealing 可以转移等待运行的任务，不能抢走一个正在执行的 poll。Tokio 的协作预算需要代码执行到参与预算检查的操作，无法约束纯 CPU 死循环。

.await 只是潜在暂停点。 如果被等待的 future 一直立即返回 Ready，执行可能一直继续；检查重点是多久真正让出控制权，而非代码中有多少个 .await。

2. 为什么不像 Go 一样异步抢占

Go 的抢占由编译器和运行时共同支持：在支持的平台上通过信号等操作系统机制请求抢占，检查异步安全点，保存寄存器和 goroutine 执行现场，再进入调度器。并非任意指令处都无条件切走。

维度 Go goroutine Rust async / Tokio
执行现场 独立 goroutine 栈及运行时上下文 Future 状态机；执行 poll 时使用 worker 线程栈
暂停与恢复 运行时配合编译器保存和恢复现场 poll 返回后，执行器重新获得控制权
纯 CPU 长循环 通常可以异步抢占 Tokio 无法强制打断
设计取舍 更完整的运行时支持 不为每个异步任务维护独立调用栈，执行器可作为库接入

例如 async 函数调用同步 calculate()，后者的嵌套函数调用现场仍在 worker 的线程栈上，Future 没有自动保存“同步函数执行到一半”的状态。发送一个信号并不等于获得保存、切换和恢复该现场的完整能力。类似 Go 的方案需要更深的编译器支持或其他栈与上下文机制，无法只靠现有 Tokio 调度策略添加。

抢占也不等于取消：它能让其他任务运行，不能修复死循环或释放其中持有的锁。

依据：Go runtime 抢占源码说明、Future 接口、Tokio 协作让出设计。

3. Mutex：缩短临界区，并保证写回一致性

std::sync::Mutex 在竞争时会阻塞线程；适合低竞争、短临界区的普通内存状态。tokio::sync::Mutex 的等待不会阻塞线程，允许 guard 跨 await，但锁仍被占着：慢 I/O 会让其他任务排队。异步 Mutex 没有消除串行瓶颈。

默认模式：锁内获取快照 → 释放锁 → 异步 I/O → 再次短暂加锁写回。

let (url, version) = {
    let guard = state.lock().unwrap();
    (guard.url.clone(), guard.version)
};

let response = fetch(&url).await?;

{
    let mut guard = state.lock().unwrap();
    if guard.version == version {
        guard.result = Some(response);
    } else {
        // 相关状态已变化：按业务选择丢弃、重试或返回冲突。
    }
}

注意：相关状态变更必须更新版本号；多个请求基于同一版本时，仍要定义结果覆盖规则，必要时增加请求 ID。大对象可复制 Arc，避免锁内深拷贝。将锁封装在同步方法中、不暴露 guard，有助于从接口上约束持锁范围。

确实必须独占异步资源完成整个操作时，可以使用 Tokio Mutex，但要接受串行吞吐上限；按场景考虑连接池、分片锁或任务独占资源并通过 channel 接收命令。单任务逐条等待命令仍然串行，不会自动提高并行度。

4. 控制计算粒度与资源并发

工作类型 建议
很短的计算 在 async 内直接执行
可拆分的计算 分批执行，批次之间主动让出
较重、持续的 CPU 计算 专用 CPU 线程池，例如 Rayon
有界同步阻塞 I/O spawn_blocking，并限制并发
长期后台循环 专用线程，并设计退出机制
必须可强制终止的失控计算 独立进程

分批处理：软时间预算

以下为局部示例，Item、process_one 由业务提供：

use std::time::{Duration, Instant};

async fn process(items: Vec<Item>) {
    let budget = Duration::from_micros(500);
    let mut started = Instant::now();

    for item in items {
        process_one(item); // 单次操作本身也必须有界
        if started.elapsed() >= budget {
            tokio::task::yield_now().await;
            started = Instant::now();
        }
    }
}

500μs 是示例目标，不是通用标准或硬性上限。若一次 process_one() 运行两秒，仍会占住 worker 两秒。yield_now 提供让出机会，不保证每个其他任务都先运行。

tokio::task::coop::consume_budget().await 可以按操作消耗协作预算，但不测量实际 CPU 时间，也不能中断已经开始的同步计算。

计算移出 worker：额度跟随实际计算生命周期

let permit = cpu_slots.clone().acquire_owned().await?;
let result = tokio::task::spawn_blocking(move || {
    let _permit = permit;
    heavy_compute(input)
})
.await?;

先获取额度，再提交计算；让闭包持有额度。即使请求方取消等待，仍在执行的计算也不会提前释放额度。否则可能出现“请求取消、额度归还、后台计算继续”，导致实际并发突破限制。

这只限制已提交计算；等待额度的请求还需要入口限流、有界队列或拒绝策略，防止无限堆积。CPU 线程池也要按部署 CPU 配额配置，避免与 async worker 争抢全部 CPU。

依据：spawn_blocking、consume_budget。

5. 开发阶段：静态检查、慢 poll 和采样

Clippy 与编辑器

在 crate 根部开启：

#![warn(clippy::await_holding_lock)]
#![warn(clippy::await_holding_refcell_ref)]
#![warn(clippy::disallowed_methods)]

项目根目录 clippy.toml：

disallowed-methods = [
    { path = "std::thread::sleep", reason = "异步代码请使用 tokio::time::sleep" },
    { path = "std::fs::read", reason = "异步代码请使用 tokio::fs::read" },
    { path = "std::fs::read_to_string", reason = "异步代码请使用 tokio::fs::read_to_string" },
    { path = "std::fs::write", reason = "异步代码请使用 tokio::fs::write" },
]
cargo clippy --workspace --all-targets -- -D clippy::disallowed_methods -D clippy::await_holding_lock

此黑名单同时作用于同步与异步代码，不自动豁免 spawn_blocking 内调用；合法阻塞操作应集中封装，在必要的小范围使用 #[allow(clippy::disallowed_methods)]。它不能全面分析第三方依赖内部的间接阻塞，也不能判断任意 CPU 计算的耗时。锁相关 lint 也不代表所有 Tokio guard 跨 await 的性能问题都会被发现。

VS Code .vscode/settings.json：

{
  "rust-analyzer.check.command": "clippy"
}

依据：Clippy 配置、rust-analyzer 诊断。

运行时检测的边界

  • tokio-console：交互查看任务运行、等待及资源状态。
  • tokio-blocked：通过 Tokio tracing 检测单次 poll 耗时并告警；文档所述接入需要 tracing 和 --cfg tokio_unstable，主要定位到 spawn 调用点。
  • CPU 采样 profiler：进一步定位具体 CPU 热点和调用栈。

必须实际运行到问题路径。请求耗时长不等于 poll 长：异步等网络两秒可以不占 CPU；poll 长也不一定是 CPU 忙，可能是同步锁、I/O 或线程被操作系统停调度。

基于 poll 结束事件计算耗时的工具，无法仅凭结束事件及时识别一个永不返回的 poll。 需要额外的心跳、外部观测和线程采样。任务总耗时的 tracing span 也不能直接当成单次 poll 耗时。

工具来源：tokio-console、tokio-blocked 及其限制。

6. 生产监控与处置

信号 用途与限制
单次 poll 耗时分布、慢 poll 次数 发现不及时让出的任务；已结束样本不能覆盖未返回的死循环
调度延迟、定时心跳延迟 发现执行器响应迟缓
各线程 CPU 使用率与采样栈 区分 CPU 忙循环、阻塞等待等原因
就绪任务队列、计算队列、等待额度耗时 判断计算能力与背压是否足够
请求 P99、超时与拒绝数 衡量用户影响

Tokio 提供运行时指标；poll 耗时直方图需要显式启用，部分 API 受版本及 tokio_unstable 限制，接入前按项目锁定版本确认。不能仅看平均值或进程总体 CPU。

生产处理顺序：

  1. 限制影响：入口限流、计算并发上限、有界队列，过载时拒绝或降级。
  2. 保留证据：外部采样抓线程栈和 CPU profile，确认热点或阻塞位置。
  3. 协作取消：在批次边界检查取消标志或 deadline，主动退出。
  4. 隔离失控代码：必须强制终止的计算放独立进程，超时由进程外控制器终止和回收。
  5. 服务已卡死时兜底：摘流后由外部管理器重启，避免所有监控和健康检查都依赖同一个 runtime。

CPU 计算即使移到同进程线程池，仍然会竞争 CPU；线程隔离解决 worker 被直接占住的问题，不保证负载隔离。需要更强边界时使用进程及资源配额。

timeout 和 abort 的真实边界

  • timeout 需要执行器获得控制权，不能强行打断不返回的 poll。
  • JoinHandle::abort() 不能立即终止正在执行的纯 CPU 死循环。
  • 已开始运行的 spawn_blocking 闭包通常不能通过 abort 停止；请求超时并不表示后台计算结束。
  • 取消本地 future 不保证远端副作用消失；支付等重试需考虑幂等性。

依据：RuntimeMetrics、timeout、spawn_blocking。

7. 其他并发实践

  • 独立 I/O 用 join! / try_join! 并发等待；它们在当前任务内轮询分支，不自动为分支创建线程。try_join! 出错会丢弃其他分支，需考虑取消安全。
  • 批量任务用 buffer_unordered(N) 限制同时在途数量；需要输入顺序时用 buffered(N)，代价是可能被前面的慢任务阻挡结果交付。
  • 共享下游用 Semaphore 控制全局在途数；限制并发不等于限制 QPS。
  • 有界 channel 传递背压；使用 try_send 时明确满队列后的拒绝、丢弃或合并策略。
  • 用 JoinSet 管理受控数量的任务并收集错误。丢弃普通 JoinHandle 不会停止任务；丢弃 JoinSet 会请求中止其中任务，但仍受协作取消边界约束。
  • 简单独立计数可用原子类型；多个字段的一致性通常用锁更容易写对。读多并不自动意味着 RwLock 更快，应测量。

落地前确定三件事

  • 当前项目的 Tokio 版本、runtime 类型、worker 数量和容器 CPU 配额。
  • 允许的调度延迟、慢 poll 阈值、CPU 并发额度与队列容量，应由代表性压测确定。
  • 哪些任务支持协作取消，哪些必须进程隔离；副作用在取消后如何保证一致性。
