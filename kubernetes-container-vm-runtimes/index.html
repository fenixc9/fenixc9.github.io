图解 Kubernetes 容器与虚拟机运行时：containerd、Kata、gVisor 与 KubeVirt 怎么选

为 Kubernetes 选择运行时时，常会同时看到 containerd、CRI-O、runc、crun、Kata、gVisor、Firecracker 和 KubeVirt。这些项目覆盖不同层级。把它们放在同一个性能排行榜里，容易忽略真正需要解决的问题。

普通容器业务通常先评估 containerd 与 runc，或沿用发行版支持的 CRI-O 与 crun。容器需要额外隔离时，可以比较 gVisor 与 Kata。需要把完整虚拟机作为 Kubernetes 工作负载管理时，应评估 KubeVirt。自建 microVM 平台还需要另外选择 VMM 和集成层。

本文用六张图解释这些层级、执行路径与取舍。资料核验截止 2026-10-26，文章整理于 10 月 27 日。范围以 Linux 工作节点为主，KubeVirt 的 guest 可以包括 Linux、Windows 等系统。性能比较来自架构分析，没有进行统一压测。

1. 运行时选型从五个层级开始

层级 代表项目 主要职责
CRI 容器管理 containerd、CRI-O 对接 kubelet，管理镜像、Pod sandbox 与容器生命周期
普通 OCI 执行器 runc、crun 建立隔离环境、配置资源约束、启动容器进程
容器沙箱 gVisor / runsc、Kata runtime / shim 用用户态应用内核或轻量 VM 增加隔离边界
虚拟机监控器 VMM QEMU、Cloud Hypervisor、Firecracker 提供虚拟硬件和 guest 执行环境
Kubernetes 虚拟机管理 KubeVirt 管理 VM/VMI、磁盘、启停、迁移等生命周期

CRI 定义 kubelet 与容器运行时之间的接口。OCI 定义容器执行等标准。一个节点可以用 containerd 管理容器，再通过不同 handler 选择 runc、gVisor 或 Kata。

因此，containerd + Kata 是合理组合。Kata 接入后的 VM 仍需要某个适用的 VMM。KubeVirt 则在更上层提供虚拟机 API，它也依赖节点已有的容器运行时。

图中展示概念分工。具体 CRI、shim、VMM 组合是否支持，仍需检查发行版、架构与项目配置。Kubernetes 运行时要求、KubeVirt 架构

2. containerd 与 CRI-O：选择容器管理体系

containerd 提供容器管理能力，其中包括 Kubernetes CRI 支持。它有镜像、存储快照、任务管理和 runtime shim 等扩展接口。CRI-O 则围绕 Kubernetes CRI 组织实现与集成。

维度 containerd CRI-O
项目定位 通用容器运行时，包含 CRI 支持 面向 Kubernetes 的 CRI 实现
生态侧重 镜像、snapshotter、shim 与多种运行环境 Kubernetes 节点与相应发行版集成
版本选择 独立版本线，需要查 K8s 兼容矩阵与维护周期 版本线与 Kubernetes 紧密对应
下层执行 常见 runc，也可配置其他执行器和沙箱 支持 runc、crun 及适用的沙箱配置
优先评估条件 通用自建集群、云节点、多种运行时扩展需求 OpenShift 或明确采用 CRI-O 的发行版

二者的选择主要影响管理、配置、升级和运维路径。容器是否共享宿主内核，还取决于下层执行器与沙箱配置。containerd 维护与兼容政策、CRI-O 官方说明

发行版支持通常比独立二进制版本更重要

生产节点需要同时考虑 kubelet、CRI 服务、OCI 执行器、CNI、CSI、cgroup 与设备插件。单独替换一个二进制，未必属于发行版已经验证的组合。

OpenShift 文档提供了 CRI-O 与 crun 的明确采用路径。GKE 也有 containerd 节点镜像与迁移文档。这些证据说明产品支持的组合，不能用于推断所有厂商内部环境的装机比例。OpenShift 运行时文档、GKE containerd 节点说明

Docker Engine 可以通过 cri-dockerd 等适配层接入 Kubernetes。新建集群通常先评估发行版支持的 containerd 或 CRI-O。Podman 本身也不能直接作为 kubelet 的 CRI 服务。运行时接入说明

3. runc、crun、gVisor 与 Kata 的隔离路径

runc 与 crun：共享内核容器的执行器

这类执行器建立 namespace、cgroup 和权限等运行环境，再启动进程。应用运行后，直接使用节点内核。runc 或 crun 不会常驻在每一次应用系统调用的执行路径上。

crun 使用 C 实现，强调较低的启动和管理开销。runc 具有广泛的兼容与采用基础。OpenShift 4.20 文档将 crun 列为默认容器运行时。已有升级集群的实际默认值仍应查询配置，不能仅按产品版本推断。

创建容器的测试不能直接换算为业务吞吐。一个服务只在启动时经过执行器创建流程，长期运行的性能还受应用、内核、网络和存储影响。OpenShift 容器运行时说明

gVisor：在用户态实现应用可见的系统接口

gVisor 的 OCI 命令是 runsc。其 Sentry 在用户态实现 Linux 系统接口，并限制应用直接接触宿主内核的范围。

这条路径需要兼容性验证。程序依赖的 syscall、ioctl、文件语义、进程行为和设备接口，必须在相应实现范围内。应用能启动，不能证明调试器、文件锁、子进程或全部设备操作都正常。

gVisor 提供不同执行平台，默认 systrap 路径与 KVM 平台有不同要求。它使用 KVM 时，也不能直接按一个完整 Linux guest VM 理解其架构。gVisor 架构

Kata：用 guest kernel 承载容器

Kata 通过轻量 VM 为容器增加硬件虚拟化边界。常见 Kubernetes 配置按 Pod 建立 VM，Pod 内容器通常共享 guest kernel。Kata shim 管理宿主侧生命周期，kata-agent 在 guest 内管理容器。

它需要维护 guest kernel、VMM、agent 和宿主集成。文件系统共享、设备直通、主机网络、特权和资源调整都有对应条件。云 VM 节点还可能需要支持嵌套虚拟化。

普通 Kata 提供的边界也不自动包含防宿主管理员读取 guest 数据的能力。若需要机密计算，还要核对 TEE、远程证明、镜像与秘密交付方案。Kata 项目说明、Kata VMM 支持

三条路径的工程取舍

维度 runc / crun gVisor Kata
系统接口 直接使用节点 Linux 内核 取决于 Sentry 实现的 ABI 与代理接口 主要由 guest Linux 内核提供
基础资源 通常较少，适合建立基线 有 Sentry 与相应代理开销 有 VMM、guest、agent 等开销
文件与网络 路径直接，节点侧优化成熟 一些操作需要额外的沙箱处理 受 virtio、文件共享和网络后端影响
硬件前提 通常无需硬件虚拟化 依执行平台而定 需要适用虚拟化支持
诊断方式 宿主进程、eBPF、perf 较直接 需要沙箱视角与专用诊断 宿主与 guest 两侧均需观测
运维重点 宿主内核与运行时组合 ABI、平台、代理与兼容验证 host/guest、VMM、设备与生命周期

这些是定性取舍。纯计算、系统调用密集、小文件 I/O 和大流量网络可能得到不同性能结果。没有统一测试时，不应给出固定的快慢排名。gVisor 性能指南

4. Kata 和 KubeVirt 管理不同的工作负载

Kata 以容器工作负载为入口。轻量 VM 用于提供容器执行环境。KubeVirt 则把虚拟机本身作为管理对象，通过 VirtualMachine 和 VirtualMachineInstance 等 API 描述它。

问题 Kata KubeVirt
用户提交什么 Pod、Deployment 等容器资源 VirtualMachine、VMI 等虚拟机资源
镜像与系统形态 通常使用 Linux 容器镜像 guest OS、虚拟磁盘与设备配置
VM 的作用 容器隔离环境 用户需要长期管理的工作负载
生命周期重点 容器创建、退出、重建与 Pod 生命周期 VM 启停、持久身份、磁盘、设备和迁移
典型需求 某些 Pod 需要独立内核 在 K8s 上运行 Linux 或 Windows VM

KubeVirt 使用 virt-launcher Pod 承载 VM 执行组件。常见执行路径使用 QEMU/KVM。调度、网络与存储会与 Kubernetes 体系结合。因此，安装 KubeVirt 后，节点仍然需要已有的 CRI 容器管理服务。KubeVirt 架构

热迁移有前提

KubeVirt 提供 VM 热迁移能力，但存储、网络、CPU 模型、宿主能力与设备配置都会影响可迁移性。GPU、直通设备或不同存储后端，需要核对专门的支持范围。

节点升级时也应一起考虑 guest 用户空间、QEMU/libvirt 与宿主内核之间的兼容。KubeVirt 官方文章讨论过这类依赖对启动和迁移的影响。

因此，“支持热迁移”不能解释为任意 VM、任意设备组合都能迁移。迁移条件、宿主内核与用户空间依赖

5. VMM 怎么选：QEMU、Cloud Hypervisor 与 Firecracker

VMM 定位与优势 主要取舍
QEMU + KVM 通用虚拟化与广泛设备集成；KubeVirt 常见路径 功能与配置面较广，需要管理设备后端和组合兼容
Cloud Hypervisor Rust 实现，面向现代云 VM，精简硬件模拟 需要核对目标架构、guest、设备、迁移与上层集成
Firecracker 精简 microVM，面向 Serverless 与短生命周期平台 设备与功能取舍明确，完整平台仍需镜像、网络、存储和恢复机制

Kata 官方文档列出不同 VMM 的功能差异。QEMU 是 NVIDIA GPU 与部分机密计算场景中支持较完整的选项。Cloud Hypervisor 提供现代云 VM、设备直通和迁移等能力，但具体条件仍依配置和版本。Firecracker 面向精简 microVM，需要接受其设备模型与集成方式。

Firecracker 本身没有提供完整的 Kubernetes CRI 服务。它需要 Kata 或其他经过验证的集成层。一个 RuntimeClass 对象也不会自动完成网络、guest 引导、镜像准备、存储与回收。Kata VMM 对比、Cloud Hypervisor、Firecracker

本文没有采用 VMM 项目首页上的启动与内存数字作为横向性能结论。VMM 启动、guest 就绪、容器进程启动和业务就绪是不同测量终点。镜像、文件系统、预热与快照也会改变结果。

6. GPU 和 RDMA：必须核对实际设备路径

普通容器通常通过设备注入或 CDI 等机制，使用节点的 GPU 设备与驱动。gVisor 可以通过 nvproxy 代理访问指定的 NVIDIA 接口。Kata 的适用直通方案则需要核对 VMM、设备分配、guest 驱动与硬件条件。

gVisor 已有 GPU 与 RDMA 支持

截至本次核验，上游文档提供以下路径：

  • nvproxy：为适用的 NVIDIA 驱动和设备提供 GPU 访问。
  • rdmaproxy：为沙箱应用提供 RDMA 设备接口。
  • 组合使用 GPU 与 RDMA 支持时，可以使用 GPUDirect RDMA。

这不代表任意 GPU、驱动和网卡都可用。RDMA 文档注明该能力仍在积极开发，支持范围包括特定 Mellanox ConnectX 和 AWS EFA 路径。它还限定宿主内核与现代 uverbs 接口；GPUDirect 使用 dma-buf，旧的 nvidia-peermem 路径不在该文档支持范围。

nvproxy 也不会模拟完整 NVIDIA 内核驱动。它会将适用的 ioctl 转发给宿主驱动。因此，需要单独评估设备共享、宿主驱动和固件边界。gVisor GPU、gVisor RDMA 与限制

云产品支持与上游能力要分别看

产品 本次官方资料确认的路径 重要边界
GKE Sandbox gVisor，以及 Kata + Cloud Hypervisor microVM 两条路径支持范围不同；文档中的 microVM 路径不支持 GPU/TPU
AKS Pod Sandboxing Kata + Cloud Hypervisor，结合 Azure 平台虚拟化能力 有宿主 OS、节点机型、网络和资源管理限制
OpenShift 普通容器 CRI-O + crun 的发行版路径 实际默认值与支持组合应按集群配置和版本确认

GKE 的某条 microVM 产品路径不支持 GPU，不能用来推断 Kata 上游不支持 GPU。上游支持某个接口，也不能反推某个托管产品已经开放该能力。GKE Sandbox、AKS Pod Sandboxing、OpenShift 运行时

可信训练与推理可先使用普通容器建立性能基线。运行用户代码、模型代码、notebook 或 Agent 工具时，再按具体隔离要求评估沙箱。验证应覆盖真实框架、NCCL、RDMA、多卡拓扑和故障恢复，单卡 CUDA 示例成功远远不够。

7. RuntimeClass 连接 Pod 与节点上的运行配置

RuntimeClass 提供一个选择入口。管理员在节点运行时中预先配置 handler，再创建指向它的 RuntimeClass。Pod 使用 runtimeClassName 选择该配置。

下面只说明对象关系。handler 名称是环境约定，需要实际配置存在；清单没有在本地集群执行。

apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: sandboxed-workload
handler: kata

Pod 中引用它：

spec:
  runtimeClassName: sandboxed-workload

创建 RuntimeClass 不会安装 Kata，不会启用嵌套虚拟化，也不会把没有该 handler 的节点变成可用节点。需要结合节点选择、污点容忍与运行时配置限制放置范围。

沙箱还有额外的资源开销。RuntimeClass 可以声明 Pod overhead，让调度与资源核算考虑相应开销。具体值应来自目标配置的测量或产品文档。宿主侧 shim/VMM 与 guest 内核、agent 的资源消耗也需要分别理解，不能对所有沙箱统一写一个常量。

Linux 节点还需要检查 kubelet 与 CRI 的 cgroup 配置是否一致。采用 systemd 和 cgroup v2 时，应遵循对应发行版的集成方式。RuntimeClass、容器运行时配置

关于资源请求与节点放置的完整流程，可以继续阅读调度机制文章。

9. 分场景选择与验证

场景 优先评估的方案 首要验证项
通用自建 K8s、可信微服务 受支持的 containerd + runc 发行版支持、cgroup、镜像与网络存储集成
OpenShift 平台 厂商支持的 CRI-O + crun 实际节点配置与升级支持
用户代码、插件、Agent 执行 gVisor 与 Kata 做工作负载级对比 ABI、I/O、设备与任务完整执行
Pod 需要独立 guest kernel Kata VMM、guest、宿主能力与资源开销
Linux/Windows VM 与 VM 生命周期 KubeVirt + QEMU/KVM 磁盘、网络、设备、备份与迁移条件
自建 Serverless/microVM 平台 Firecracker 或 Cloud Hypervisor 镜像、快照、网络身份、存储与回收集成
GPU 训练与推理 普通容器建立基线，再评估沙箱 驱动、CDI、NCCL、RDMA 与拓扑

这些建议用于筛选候选方案，没有给出统一性能排名，也没有全行业装机量数据。

用同一套工作负载做比较

维度 需要固定与测量的内容
冷启动 固定镜像缓存、存储与网络；区分进程启动、guest 就绪和业务就绪
内存与密度 同时计算宿主与 guest 开销，观察空闲与稳态使用量
CPU 区分纯计算、频繁 syscall、线程与同步负载
文件与网络 覆盖真实文件系统、挂载方式、小文件、连接数与流量形态
服务质量 在相同有效请求量下比较吞吐、错误率与 P99
设备 使用完整框架链路验证 GPU、RDMA 和设备恢复
运维 覆盖日志、监控、宿主与 guest 排障、节点维护和升级
生命周期 验证重启、超时、失败回收、快照或迁移等目标能力

引入 VM 边界后，CPU、LLC、内存带宽、网卡和存储仍可能共享。更换运行时不能代替节点资源治理。如果平台还要同时运行在线与离线工作负载，需要继续验证混部的资源回收与 SLO 保护。

一个示例容器能够启动，只能证明基本执行路径可用。最终选择应由真实业务兼容性、隔离需求、性能与长期维护成本共同决定。
